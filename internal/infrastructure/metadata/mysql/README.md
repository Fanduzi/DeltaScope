# MySQL Metadata Provider Module

MySQL-protocol metadata provider used for optional metadata-aware DeltaScope audits against MySQL and TiDB.

## Files

| File | Responsibility |
|------|---------------|
| provider.go | Opens MySQL-compatible metadata connections and loads normalized dialect, schema, instance-fact, and target-table snapshot data from information schema, including preserved per-index cardinality facts and per-member plain-key knownness (`SUB_PART`/`COLLATION` plus NULL `COLUMN_NAME` classification into `PrefixParts`/`DescParts`/`UnmodeledKeyParts`/expression marks). Instance facts carry explicit known bits: MySQL reads `innodb_page_size` and `innodb_large_prefix` (5.7), TiDB banners additionally read the `max-index-length` and `alter-primary-key` tidb-server configs via `SHOW CONFIG`, verifying every matching row (one per tidb-server instance): disagreeing, unparsable, non-positive, or absent values stay unknown, while query/scan/iteration failures propagate as provider errors rather than degrading into gaps (issue #83 T04-B/R2, issue #89 T10-R3 — `alter-primary-key` is the config fact `int_only` clustered mode defers to). MySQL banners also read `restrict_fk_on_non_standard_key` — the 8.4-only refusal of foreign keys backed by a non-unique referenced key (6125); the variable does not exist on pre-8.4 MySQL or TiDB, so an absent row stays an unknown fact and the eligibility answer defers to dialect/version instead of a guessed default (issue #90 T11-R1). Expression members read the same `COLLATION` direction fact column members do — `D` lands `Descending`, `A` stays ascending, and an unproven or unrecognized direction keeps the member's expression identity with `DirectionUnknown` marked rather than demoting it to unmodeled or guessing ascending (issue #89 T10-R3/R4). Column rows carry T07 advanced facts from the same COLUMNS select: `GENERATION_EXPRESSION` plus `EXTRA` tokens yield generated storage + expression facts (`VIRTUAL`/`STORED GENERATED`), `DEFAULT_GENERATED` yields parsed expression-default facts with verbatim `DefaultValue` bytes preserved plus `DefaultParenthesized=true` (catalog-stored expression defaults are always parenthesized syntax), and `INVISIBLE` yields effective visibility (absence on a complete row = effective visible; the catalog never proves `VisibilityExplicit`). Undecodable catalog expression text stays an explicit unknown fact via `ParseCatalogExpressionFacts` (issue #86 T07). The T08-R1/R2 `DefaultLiteral` identity fact carries the verbatim decoded `COLUMN_DEFAULT` bytes with a kind domain from the column's own base type (parameters/attributes stripped; numeric bases → `numeric`, else `string` — the recorded encoding is the catalog's own, e.g. scale-normalized `1.00`, and cross-source comparability is the rule's domain check), `DefaultIsCurrentTimestamp` asserts only on temporal base types (`timestamp`/`datetime`, including parameterized forms), and expression/temporal defaults never carry a literal identity (issue #87 T08-R1). T10 adds an `information_schema.STATISTICS.IS_VISIBLE` capability probe (a backticked `information_schema`.`columns` existence check counted in provider call totals): on capable catalogs (MySQL 8.x, TiDB) the index select carries the column and each named member lands effective `Visibility` (`YES`→visible/`NO`→invisible), while uncapable catalogs (MySQL 5.7 or a zero-count probe) omit the column and leave member visibility empty — a real probe failure propagates as a load error rather than degrading into a guessed shape; `INDEX_TYPE` also classifies `SPATIAL`/`FULLTEXT` into `spec.Index.Kind` (issue #89 T10). T10-R1 adds member-level facts: an `EXPRESSION` capability probe selects the catalog's functional key-part text (parsed into `ExpressionFacts` + multi-valued marks via `ParseCatalogExpressionFacts`/`CatalogExpressionIsMultiValued`), members accumulate into `spec.Index.KeyParts` (ordinal, kind, column, prefix length, descending, expression identity), `information_schema.PARTITIONS` loads `Partitioned` (an unanswerable probe keeps the fact unknown rather than guessing false), and TiDB's `information_schema.TIDB_INDEXES.CLUSTERED` resolves `PrimaryKeyClustered` for any member shape (the TiDB DROP PRIMARY KEY 8200 refusal covers PKIsHandle and common-handle clustered primaries alike) while `CLUSTERED` plus the single-integer member shape separately resolves `PrimaryKeyIsHandle` (STATISTICS synthesizes a PRIMARY row even for handle tables, so index presence alone cannot prove an operable PRIMARY object — a missing CLUSTERED row sets both `PrimaryKeyClusteredUnknown` and `PrimaryKeyHandleUnknown`, and an unmatchable member shape sets `PrimaryKeyHandleUnknown`, rather than defaulting the object into existence), and the TiDB instance-fact probe additionally reads the `tidb_enable_clustered_index` session variable so declared-but-unstated primary keys resolve through the observed mode (empty means unprobed → the handle answer stays unknown; never populated on MySQL). R2 fixes member classification for TiDB's literal-`'NULL'` `COLUMN_NAME` on expression members: SQL NULL or literal-with-expression-text stays an expression member, a literal matching a loaded real column name stays a plain column (a backticked `` `NULL` `` column is legal MySQL), and neither-provable stays `UnmodeledKeyParts` (issue #89 T10-R2). R4 adds `resolveTiDBPrimaryName`; R5 rebinds it to the actual stored object name: a `primary`-fold catalog row is not self-evidently the constraint object on TiDB (a secondary can literally own `primary` — `RENAME … TO primary` is legal on PK-less and PKIsHandle tables — and a renamed PK object survives under `pk2`/`pk3`), so constraint presence is proven independently by the `information_schema.table_constraints` `PRIMARY KEY` row (tidb_pk_type cannot answer it — NONCLUSTERED covers both PK-less tables and real nonclustered primaries, verified on the TiDB v8.5.0 anchor) while object attribution is proven separately: a proven constraint with exactly one unique candidate fold promotes it to `snapshot.PrimaryKey` under its stored name, multiple candidates disambiguate through `TIDB_INDEXES.CLUSTERED` (exactly one clustered candidate owns the object) and then the `KEY_COLUMN_USAGE` primary-column list, a proven constraint with no attributable object keeps a name-unknown `PrimaryKey` placeholder with every unique candidate demoted to `IndexKindUnknown` so member comparisons never treat a maybe-PK fold as a proven UNIQUE, and a proven-absent constraint keeps folds as members. `loadTiDBPrimaryKeyHandle` probes `CLUSTERED` on the object's actual stored name rather than the literal `PRIMARY`. Per issue #79 every probe distinguishes clean absence (withheld facts stay unknown) from an actual query/scan/connection failure, which propagates as a load error even under a clean catalog read — context cancellation keeps its own semantics (issue #89 T10-R4/R5). T11 adds `loadForeignKeys`: `information_schema.KEY_COLUMN_USAGE` joined to `REFERENTIAL_CONSTRAINTS` folds ordered local/referenced column pairs into `spec.Constraint` members grouped by constraint name (stored slice indexes, never pointers into a growing slice), DELETE_RULE/UPDATE_RULE normalize to the shared lowercase refer-action vocabulary (`restrict`/`cascade`/`set_null`/`no_action`/`set_default`), a non-`NONE` MATCH option counts as an unmodeled refer action, a clean empty result is a proven empty collection (`Constraints=[]`, not nil-withheld), and query/scan/iteration failures propagate as provider errors — UNIQUE stays index-side per spec convention and is never folded into constraint rows (issue #90 T11). R6 closes the attribution contract: candidate folds match the `KEY_COLUMN_USAGE` primary list by ordered sequence, not set equality (`[a,b]` never binds `[b,a]` — verified on the v8.5.0 anchor where a renamed `pk2(a,b)` coexists with `aa(b,a)`), multiple same-sequence candidates withhold object identity under a name-unknown `PrimaryKey` placeholder rather than promoting the first STATISTICS hit (verified: `aa(id)` and `pk2(id)` coexist with ordered KCU `[id]`), `TIDB_INDEXES.CLUSTERED` reads as a tri-state (YES/NO/unproven — a missing, NULL, or unrecognized row never counts as a proven NO, so NONCLUSTERED publishes only when every candidate proved NO — verified: only the PK object's row reads YES; case-variant names folding to one key merge YES over unproven over NO regardless of read order so a sibling NO never covers an unproven row), and an inconsistent `pkCount > 1` demotes every potentially-PK unique candidate while unvouching all primary facts (issue #89 T10-R6). T12 adds `loadCheckConstraints` over two probed catalog shapes: MySQL reads `TABLE_CONSTRAINTS` (`constraint_type='CHECK'` + `ENFORCED`) joined to `CHECK_CONSTRAINTS` on catalog+schema+name (that table has no `TABLE_NAME`), while TiDB reads `TIDB_CHECK_CONSTRAINTS` (the only catalog with `TABLE_NAME` attribution — TiDB stores no CHECK rows in `TABLE_CONSTRAINTS` and exposes enforcement only through SHOW CREATE, so TiDB members load `Enforced`-unvouched); each shape is gated by its own information_schema capability probe, clauses parse into `ExpressionFacts` (raw text never retained), a clean zero is a proven empty set, and any `constraint_type` the projection cannot represent unvouches the collection rather than posing as complete (issue #91 T12). The T13-R1 partition catalog probe reads `partition_method`/`partition_name` rows from `information_schema.partitions` on BOTH dialects: partition rows publish `Partitioned=true` with the normalized method and ordinal-ordered member names, an empty answer publishes `Partitioned=false` with an observed-empty member set, and only an unanswerable probe keeps every fact nil — never a guessed non-partitioned verdict (issue #92 T13-R1) |
