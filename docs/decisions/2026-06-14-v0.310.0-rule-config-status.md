## Context

DeltaScope now has three user-facing pieces around rules:

- `deltascope audit` tells users which findings fired.
- `deltascope rules explain <rule_id>` explains what one shipped rule means.
- `deltascope config lint` validates whether a YAML config file is syntactically and semantically valid.

The missing question is narrower and more practical:

> Given my current config file, is this rule on or off, and what level will it use if it fires?

Users can infer this today by reading `deltascope.yaml`, comparing it with `config show-default`, and then checking `rules explain`. That is too indirect. It also makes it easy to confuse two separate questions:

- Rule meaning: "What does `dml.where.require` check?"
- Config status: "What does my config make `dml.where.require` do?"

The command name must avoid colliding with `rules explain`. `config explain-rule` sounds like it explains rule semantics, so v0.310.0 should not use that name.

## Decision

v0.310.0 will add a focused config inspection command:

```bash
deltascope config status <rule-id> [--format text|json]
```

The command reports the current effective status of one shipped rule under the selected config.

It answers:

- Is this rule currently ON or OFF?
- If it fires, which `level` will it use?
- Did the user's config change `enabled`, `level`, or params from the default policy?
- What is the default value?
- What is the effective value?
- Where should the user go to read rule semantics?

It does not explain rule semantics itself. It points to:

```bash
deltascope rules explain <rule-id>
```

## Config Semantics: Rule-Level Replacement (Audit-Faithful)

`config status` reports the effective policy **exactly as the audit path applies it**.
The "current" snapshot is the output of `internal/infrastructure/config/viper.LoadPolicy`,
unmodified. `config status` never silently merges a partial rule config onto the
defaults, because audit does not do that either.

This matters because of how `LoadPolicy` behaves. It starts from `policy.Default()` and
then unmarshals the YAML file over it via viper/mapstructure. For any rule **mentioned**
in the YAML, mapstructure allocates a fresh `RulePolicy` and decodes only the fields the
file lists, then overwrites that rule's slot. Omitted fields become their zero values:

| Field | Omitted effective value |
|---|---|
| `enabled` | `false` |
| `level` | `""` (empty) |
| `params` | `nil` (empty) |

Rules **not mentioned** in the YAML keep their default `RulePolicy` unchanged.

The audit path consumes this verbatim. In `internal/domain/rule/{dml,ddl}/register.go`,
each `Register` skips any rule whose `RulePolicy.Enabled` is false, so a rule dropped to
`enabled: false` (whether intentionally or by omission) never runs. `Level` and `Params`
have per-rule constructor fallbacks, but `Enabled` does not.

**Consequence:** a user who writes only

```yaml
rules:
  dml.where.require:
    level: warning
```

expecting to soften the level actually **turns the rule off**, because `enabled` is omitted
and therefore replaced with `false`. `config status` must surface this, not hide it. So
when a rule is mentioned but a field is omitted, the status output calls the omission out
explicitly, for example:

```text
Config effect:
  Your config mentions this rule, so it replaces the default rule policy.
  `enabled` is omitted, so the effective value is false.
  `level` changes from blocker to warning.
  `params.required` is removed.
```

To change only the level while keeping the rule on, a user must specify every field so the
replacement leaves the others intact:

```yaml
rules:
  dml.where.require:
    enabled: true
    level: warning
    params:
      required: true
```

`config status` therefore reports what audit will actually do with the file. Whether
`LoadPolicy` should adopt merge semantics instead is a separate, larger decision and is
**out of scope** for v0.310.0; v0.310.0 will not change `LoadPolicy`, audit behavior, or
default policy values.

### Config Source

`config status` uses the existing global `--config` flag:

```bash
deltascope --config ./deltascope.yaml config status dml.where.require
deltascope config status dml.where.require --format json
```

When `--config` is omitted, the command reports the built-in default policy and states that no config override is active.

`config lint --file` remains unchanged. v0.310.0 will not rename or remove it.

## Text Output Contract

For a default-only rule:

```text
Rule: dml.where.require

Current status:
  ON
  Findings from this rule fail as: blocker.

Config effect:
  No override found. This rule uses the default policy.

Default:
  enabled: true
  level: blocker

Current:
  enabled: true
  level: blocker

Rule details:
  deltascope rules explain dml.where.require
```

For a rule whose level is changed cleanly (all fields specified, only `level` differs):

```text
Rule: dml.where.require

Current status:
  ON
  Findings from this rule fail as: warning.

Config effect:
  Your config mentions this rule, so it replaces the default rule policy.
  `level` changes from blocker to warning.

Default:
  enabled: true
  level: blocker
  params:
    required: true

Current:
  enabled: true
  level: warning
  params:
    required: true

Rule details:
  deltascope rules explain dml.where.require
```

For a disabled rule (all fields specified, only `enabled` differs):

```text
Rule: ddl.table.audit_columns.require

Current status:
  OFF
  This rule will not produce findings.

Config effect:
  Your config mentions this rule, so it replaces the default rule policy.
  `enabled` is set to false; your config disables this rule.

Default:
  enabled: true
  level: warning
  params:
    required: true

Current:
  enabled: false
  level: warning
  params:
    required: true

Rule details:
  deltascope rules explain ddl.table.audit_columns.require
```

For a partially specified rule (dangerous: the omitted fields are replaced with zero
values, so the rule ends up OFF):

```text
Rule: dml.where.require

Current status:
  OFF
  This rule will not produce findings.

Config effect:
  Your config mentions this rule, so it replaces the default rule policy.
  `enabled` is omitted, so the effective value is false.
  `level` changes from blocker to warning.
  `params.required` is removed.

Default:
  enabled: true
  level: blocker
  params:
    required: true

Current:
  enabled: false
  level: warning
  params: {}

Rule details:
  deltascope rules explain dml.where.require
```

If params changed (all fields specified, only a param differs), text output includes a
concise params section after `level`:

```text
Config effect:
  Your config mentions this rule, so it replaces the default rule policy.
  `params.limit` changes from 64 to 48.

Default:
  enabled: true
  level: blocker
  params:
    limit: 64

Current:
  enabled: true
  level: blocker
  params:
    limit: 48
```

Text output is intended for humans. It is stable enough for documentation, but automation should prefer JSON.

## JSON Output Contract

`--format json` returns a stable wrapper (full-spec override, only `level` differs):

```json
{
  "version": "v0.310.0",
  "rule_id": "dml.where.require",
  "status": {
    "enabled": true,
    "level": "warning",
    "state": "on"
  },
  "default": {
    "enabled": true,
    "level": "blocker",
    "params": {
      "required": true
    }
  },
  "current": {
    "enabled": true,
    "level": "warning",
    "params": {
      "required": true
    }
  },
  "config_effect": {
    "has_config": true,
    "has_override": true,
    "changed_fields": ["level"],
    "messages": [
      "Your config mentions this rule, so it replaces the default rule policy.",
      "`level` changes from blocker to warning."
    ]
  },
  "rule_details_command": "deltascope rules explain dml.where.require"
}
```

For a partially specified rule, `current` reflects the replaced (zeroed) values and the
messages call out each omitted field, for example:

```json
{
  "version": "v0.310.0",
  "rule_id": "dml.where.require",
  "status": {
    "enabled": false,
    "level": "warning",
    "state": "off"
  },
  "default": {
    "enabled": true,
    "level": "blocker",
    "params": {
      "required": true
    }
  },
  "current": {
    "enabled": false,
    "level": "warning",
    "params": {}
  },
  "config_effect": {
    "has_config": true,
    "has_override": true,
    "changed_fields": ["enabled", "level", "params.required"],
    "messages": [
      "Your config mentions this rule, so it replaces the default rule policy.",
      "`enabled` is omitted, so the effective value is false.",
      "`level` changes from blocker to warning.",
      "`params.required` is removed."
    ]
  },
  "rule_details_command": "deltascope rules explain dml.where.require"
}
```

Required JSON fields:

| Field | Meaning |
|---|---|
| `version` | DeltaScope build version |
| `rule_id` | Requested rule ID |
| `status.enabled` | Effective enabled state |
| `status.level` | Effective rule level |
| `status.state` | `on` or `off` |
| `default` | Built-in default policy values for the rule |
| `current` | Effective values after config loading |
| `config_effect.has_config` | Whether global `--config` was supplied |
| `config_effect.has_override` | Whether the requested rule had explicit config keys or effective differences |
| `config_effect.changed_fields` | Changed top-level fields, such as `enabled`, `level`, or `params.limit` |
| `config_effect.messages` | Human-readable explanation lines |
| `rule_details_command` | `deltascope rules explain <rule_id>` |

JSON output must not include `severity`.

## Error Behavior

The command returns a user error and non-zero exit when:

- `<rule-id>` is missing.
- More than one positional arg is supplied.
- `<rule-id>` is not a shipped rule.
- `--format` is not `text` or `json`.
- `--config` points to a missing, unreadable, or invalid YAML file.
- The config contains an unknown rule, invalid level, invalid param, or unknown param.

Unknown rule errors should name the requested rule:

```text
rule "not.real.rule" not found
```

Config validation should reuse existing config lint semantics where possible, so `config status` does not silently ignore invalid configs.

## Rationale

`config status` is clearer than `config explain-rule` because it describes the result users are actually asking for: the rule's current status under the active config.

The feature should start with one rule at a time. A full `config effective` command that prints all 371 rules is useful later, but it is more output and a larger contract. Single-rule status gives immediate value and keeps the first release small.

The command should live under `config`, not `rules`, because it answers a configuration question. `rules explain` remains the semantic explanation surface.

The command should use the existing global `--config` flag to match `audit`; however, docs may also remind users that `config lint --file` remains the validation-only command.

## Public Contract

After v0.310.0, users can rely on:

- `deltascope config status <rule-id>` existing as a CLI command.
- Text output stating `ON` or `OFF`.
- Text output stating the effective `level` when the rule is on.
- Text output explaining whether the user's config changed `enabled`, `level`, or params.
- Text output showing default and current values.
- Text output linking to `deltascope rules explain <rule-id>`.
- JSON output using the wrapper documented above.
- Unknown rule IDs returning non-zero with a clear message.
- Invalid configs returning non-zero instead of producing partial status.
- The command not running an audit and not parsing SQL.

## Privacy / No-Leak Contract

`config status` must not:

- Accept SQL input.
- Parse SQL.
- Run the audit service.
- Connect to a database.
- Include user SQL payloads.
- Include parser `near ...` text.
- Include database object names from migrations.
- Include live metadata values.

The command reads only:

- built-in default policy
- rule catalog metadata
- the selected YAML config file, when `--config` is supplied

The command may echo rule IDs and config values from the user's config file. It should not print the entire config file.

## Deferred / Out Of Scope

### Task 2: Rule Config Status Core

Add a focused status derivation layer that compares default policy, effective policy, raw config presence, and rule catalog metadata.

Proposed files:

- `internal/application/configstatus/status.go`
- `internal/application/configstatus/status_test.go`
- `internal/application/configstatus/README.md`

Proposed API:

```go
type Request struct {
    RuleID     string
    ConfigPath string
}

type Result struct {
    RuleID             string
    Status             RuleStatus
    Default            RulePolicySnapshot
    Current            RulePolicySnapshot
    ConfigEffect       ConfigEffect
    RuleDetailsCommand string
}

type RuleStatus struct {
    Enabled bool
    Level   rule.Level
    State   string // on or off
}

type RulePolicySnapshot struct {
    Enabled bool
    Level   rule.Level
    Params  map[string]any
}

type ConfigEffect struct {
    HasConfig     bool
    HasOverride   bool
    ChangedFields []string
    Messages      []string
}

func Inspect(ctx context.Context, req Request) (Result, error)
```

Core behavior:

- Validate `RuleID` is non-empty.
- Verify the rule exists in `catalog.Lookup`.
- Load built-in defaults from `policy.Default`.
- Load effective policy from `viperconfig.LoadPolicy` when `ConfigPath` is set, and use
  its output **verbatim** as the "current" snapshot. See *Config Semantics: Rule-Level
  Replacement* above: mentioning a rule replaces its whole policy and zeroes omitted fields.
- Parse raw YAML (a private `rawConfigFile` in this package; the application layer must
  not import the CLI package) to detect which fields the user explicitly wrote, so omitted
  fields can be reported with an explicit warning rather than silently.
- Reuse config lint semantics for invalid config (unknown rule, invalid level, unknown
  param, param type mismatch) instead of silently accepting malformed files.
- Compare default and effective `enabled`, `level`, and params.
- Generate deterministic messages in field order (enabled, level, then params keys
  alphabetically):
  - no config supplied
  - no override found
  - `Your config mentions this rule, so it replaces the default rule policy.` (framing, first)
  - `` `enabled` is omitted, so the effective value is false. `` (dangerous omission)
  - `` `enabled` is set to false; your config disables this rule. `` (explicit)
  - `` `level` changes from blocker to warning. ``
  - `` `params.limit` changes from 64 to 48. ``
  - `` `params.required` is removed. ``
- Return deterministic `ChangedFields` ordering: `enabled`, `level`, then `params.<key>`
  alphabetically.
- `HasOverride` is true when the rule is mentioned in the config file (its policy is
  replaced), and false when the file exists but never mentions the rule.
- Clone param maps before returning; never mutate default or effective policy maps.
- JSON-marshaling `Result` must never include `severity`.

Focused tests (implemented in `internal/application/configstatus/status_test.go`):

- default-only rule reports ON and no config
- config path with no matching rule reports no override
- partial `level` override reports the rule OFF, with omitted-`enabled` warning, level
  change, and removed param (documents the replacement danger)
- full-spec explicit disable reports OFF with only `enabled` changed
- partial `params` override reports OFF with omitted `enabled`/`level` warnings and the
  param change
- multiple full-spec overrides are deterministic across repeated calls
- mentioned rule whose values match default still reports `has_override=true`
- unknown rule returns an error naming the rule
- invalid config (unknown rule, invalid level, invalid param type, unknown param) errors
- result JSON has no `severity`
- params maps are cloned (mutating returned maps does not leak into later calls)

## Consequences

`config status` makes effective rule configuration a user-facing CLI contract. Future config-schema changes must preserve clear reporting of default versus current values.

The command makes `level` even more visible as the public priority field. Future work must not introduce a parallel `severity` field without a separate migration decision.

If users need bulk inspection later, implement a separate `config effective` command instead of expanding single-rule text output into a full policy dump.
