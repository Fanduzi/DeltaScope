## Context

v0.230.0 exposed two release-system failure modes:

1. **Downstream failure after assets exist.** The first release attempt created GitHub Release assets, then `publish-homebrew-cask` failed because the tap token could not push to `Fanduzi/homebrew-deltascope`.
2. **Full rerun breaks on existing assets.** A later full workflow rerun failed in `release-linux` because GoReleaser tried to upload already-existing release assets and GitHub returned `422 already_exists`.

The release eventually succeeded by deleting the old release and tag, retagging `v0.230.0`, and rerunning from scratch. That path required explicit operator acceptance of tag/release replacement and should not be the default recovery procedure.

## Decision

1. **Full release remains tag-driven.** The existing `.github/workflows/release.yml` continues to be the single authoritative path triggered by tag push. No structural changes to the release pipeline.
2. **Add a manual downstream recovery workflow.** A new `.github/workflows/release-recover.yml` will provide a safe `workflow_dispatch` path for recovering Homebrew and npm publishing after a partial failure.
3. **Add an early existing-release guard.** Before GoReleaser publishes assets, `release.yml` will check whether the GitHub Release already exists and fail immediately with an actionable message directing the operator to the recovery workflow.

## Recovery Contract

The recovery workflow observes these boundaries:

- **Read-only on release assets.** It downloads existing GitHub Release assets as source of truth. It never uploads, replaces, or deletes release assets.
- **No binary rebuilds.** GoReleaser is not invoked. No compilation step.
- **No tag/release/asset deletion.** The workflow never removes tags, releases, or assets.
- **Homebrew idempotent.** If the cask in `Fanduzi/homebrew-deltascope` is already up to date (no diff), the job succeeds with a clear message.
- **npm idempotent.** If `@fanduzi/deltascope-mcp@$VERSION` is already published and matches the requested version, the job succeeds without overwriting. If absent, it publishes with `--access public --provenance`.

## Secrets

| Secret | Purpose | Failure mode |
|--------|---------|-------------|
| `HOMEBREW_TAP_TOKEN` | Write access to `Fanduzi/homebrew-deltascope` | Push fails with authentication error |
| `NPM_TOKEN` | npm publish | Publish fails with authentication error |

The workflow cannot read secret values directly. It infers permission state from the success or failure of clone/push/publish operations.

For `HOMEBREW_TAP_TOKEN`, the expected fine-grained token shape:
- Resource owner includes `Fanduzi`
- Repository access includes `Fanduzi/homebrew-deltascope`
- Repository permission: `Contents: Read and write`

## Non-Goals

- No parser changes.
- No SQL audit rule changes.
- No SDK, CLI, HTTP, or MCP product behavior changes.
- No release version surface changes.
- No automatic tag, release, or asset deletion.
- No npm overwrite of existing packages.
- No GoReleaser replacement.
- No secret rotation or direct secret value validation.
