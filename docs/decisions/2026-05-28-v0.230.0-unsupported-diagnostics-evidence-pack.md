# Decision: Unsupported Diagnostics Evidence Pack

Date: 2026-05-28
Status: Accepted
Related milestone/version: v0.230.0
Related commits: 0bdf52b (v0.220.0 base)
Related tests: `internal/application/audit/unsupported_diagnostics_evidence_test.go`, `internal/application/audit/unsupported_diagnostics_evidence_postgresql_tag_test.go`

## Context

v0.220.0 standardized the parser-error diagnostic message:

> statement was not audited because the selected dialect parser could not parse it; no audit findings were inferred

This fixed raw parser payload leakage and made parser-error SQL clearly unaudited. The remaining UX gap is that the diagnostic is sparse: it says what happened, but not enough about what the user should do next or how to distinguish parser errors from structured unsupported boundaries.

Current census (unchanged since v0.220.0):

| Dialect | Total | Finding Covered | Normalized Silent | Unsupported Boundary | Parser Error | Unclassified |
|---|---:|---:|---:|---:|---:|---:|
| MySQL | 61 | 46 | 0 | 0 | 15 | 0 |
| TiDB | 54 | 45 | 0 | 0 | 9 | 0 |
| PostgreSQL | 285 | 274 | 6 | 0 | 5 | 0 |

## Decision

Add a stable structured diagnostic evidence layer for parser-error and structured unsupported outcomes. Public surfaces will expose a `Diagnostic` struct with classification, reason, action hint, audited flag, and dialect — without inferring object names from unparsed SQL.

## Rationale

- Users need actionable next steps, not just a description of the failure mode.
- Distinguishing `parser_error` from `unsupported_statement` helps users understand whether the issue is a parser limitation or a deliberate unsupported boundary.
- Structured evidence enables programmatic handling (CI gates, dashboards) without parsing prose.
- Generic action hints are safe: they avoid guessing specific object names from failed parse text.

## Public Contract

### Diagnostic Evidence Fields

| Field | Type | Meaning |
|---|---|---|
| `classification` | string | Stable category: `parser_error` or `unsupported_statement` |
| `reason` | string | Safe human-readable explanation |
| `action_hint` | string | Generic next step for the user |
| `audited` | bool | `false` for parser-error and unsupported statement-level outcomes |
| `dialect` | string | Selected dialect when available |

### Parser-Error Diagnostic

- `classification` = `parser_error`
- `reason` = v0.220.0 standard diagnostic (unchanged)
- `action_hint` = `verify the selected dialect and syntax, split multi-statement input if needed, or upgrade DeltaScope when parser support becomes available`
- `audited` = `false`
- `dialect` = selected dialect

### Structured Unsupported Diagnostic

- `classification` = `unsupported_statement`
- `reason` = safe explanation (reuses existing `UnsupportedDetail.Reason` when available)
- `action_hint` = `treat this statement as not covered by DeltaScope policy checks; review it manually or track support in a future DeltaScope release`
- `audited` = `false`
- `dialect` = selected dialect

### No-Leak Contract

Diagnostics must not contain:

- routine body, function body, trigger body, event body
- event schedule expressions
- TTL option expressions
- locality region strings
- tablespace file paths
- resource group option values
- PostgreSQL option payloads
- raw parser `near ...` fragments
- raw SQL text

The action hint must stay generic. It must not suggest a specific object name inferred from failed parse text.

## Deferred / Out Of Scope

- No parser support added.
- No fallback parser added.
- No parser dependency upgrade.
- No new SQL audit rules added.
- No parser_error count reduction.
- No conversion of parser errors into structured unsupported details by guessing.
- No full DDL support or dialect parity claim.
- No change to policy evaluation for supported statements.

## Consequences

- Future diagnostic additions must preserve the no-leak contract.
- Public surface tests (Task 3) will lock in the evidence contract across all transports.
- If a future milestone adds fallback parsing, parser_error diagnostics should be reclassified rather than removed.
- Census and feasibility counts must remain unchanged through this milestone.
