## Context

v0.210.0 classified 29 tracked DDL `parser_error` forms across three dialects:

| Dialect | Parser Error Cases |
|---|---:|
| MySQL | 15 |
| TiDB | 9 |
| PostgreSQL | 5 |
| **Total** | **29** |

Feasibility buckets:

| Bucket | MySQL | TiDB | PostgreSQL | Total |
|---|---:|---:|---:|---:|
| `parser_upgrade_candidate` | 5 | 0 | 5 | 10 |
| `bounded_fallback_candidate` | 1 | 3 | 0 | 4 |
| `product_unsupported_or_inapplicable` | 0 | 6 | 0 | 6 |
| `unsafe_fallback_defer` | 9 | 0 | 0 | 9 |

When the selected dialect parser cannot parse a tracked DDL statement, DeltaScope currently returns a raw parse error. Public surfaces (SDK, CLI, HTTP, MCP) do not consistently communicate that the SQL was not audited and no findings were inferred.

## Decision

Parser-error DDL is an unsupported parser surface. DeltaScope must return a clear diagnostic stating that no audit was performed and no findings were inferred from unparsed SQL. This milestone does not attempt to solve parser grammar limitations.

## Rationale

- Fallback parsing risks incorrect auditing. Extracting facts from raw parser-error SQL and producing findings from guessed structure could mislead users into trusting incomplete analysis.
- Parser dependency upgrades require separate investigation (tracked as `parser_upgrade_candidate` in 10 cases).
- Bounded fallback candidates (4 cases) still need careful scope analysis before any implementation.
- 6 cases are product-unsupported or inapplicable and should not produce findings even with a working parser.
- The safest immediate action is to make the existing failure explicit and consistent, not to change parser behavior.

## Public Contract

For any tracked parser-error DDL case, public surfaces must communicate:

| Field | Requirement |
|---|---|
| `error` | Non-nil; includes stable semantics indicating parser cannot parse the statement and no audit was performed |
| `findings` | Empty; no findings inferred from unparsed SQL |
| `unsupported` | Empty unless the parser produced a structured unsupported statement; no fabrication from failed parse text |
| `message` | States the current dialect parser cannot parse the statement and no audit findings were inferred |
| `raw_sql` | Never echoed into structured diagnostics or synthesized findings |

### No-Leak Contract

Parser-error diagnostics must not expose:

- Routine body, function body, trigger body, event body
- Event schedule expressions
- TTL option expressions
- Locality region strings
- Tablespace file paths
- Resource group option values
- PostgreSQL option payloads (drop_slot, NOT VALID, constraint names)

## Deferred / Out Of Scope

- No fallback parser.
- No parser dependency upgrade.
- No new SQL audit rules.
- No `parser_error` count reduction.
- No full DDL support or dialect parity claim.
- No conversion of parser errors into `UnsupportedDetail` by guessing from raw SQL.

### Task 4: Docs, Gates, and Milestone Readiness

#### Baseline Regression Fix

Pre-existing failure audit revealed a regression introduced in Task 2. The `errParserUnsupported` replacement in `service.go` masked the typed `PostgreSQLCapabilityBoundaryError` for PostgreSQL parse failures on non-PG builds. Three packages failed on the current branch that passed on `main@e24710e`:

- `pkg/deltascope`: `TestAuditReturnsCapabilityBoundaryErrorForExplicitPostgreSQLOnUnsupportedBuild`
- `internal/interfaces/http`: `TestHandlerAuditRejectsExplicitPostgreSQLOfflineRequestsOnUnsupportedBuild`
- `internal/interfaces/mcp`: `TestAuditSQLToolRejectsExplicitPostgreSQLOfflineRequestsOnUnsupportedBuild`

Fix: added `errors.As(err, &pgCap)` guard in `service.go` before returning `errParserUnsupported`, preserving the typed capability-boundary error for PostgreSQL. All three packages now pass.
