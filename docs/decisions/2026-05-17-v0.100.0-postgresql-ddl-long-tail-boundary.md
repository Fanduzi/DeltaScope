## Context

v0.100.0 continued pre-1.0 PostgreSQL DDL coverage work. A long-tail census identified 57 candidate PostgreSQL DDL statement forms. The goal was selected PostgreSQL object lifecycle coverage — promote safe bounded forms to rules, defer forms that would require retaining unsafe payloads. This is not full PostgreSQL DDL grammar support.

## Decision

Promote safe, bounded lifecycle forms to findings/rules. Keep unsafe payload-heavy boundary CREATE forms unsupported.

Final result:
- 36 new PostgreSQL-only DDL rules
- 55/57 long-tail cases finding-covered
- 2 intentionally unsupported boundary cases: `CREATE TRANSFORM`, `CREATE ACCESS METHOD`

## Rationale

**Promote** when object identity can be represented with bounded structural facts (name, type, schema, owner, OID, language). Defer when normalization would require retaining function/body/handler payloads or discarding the identity needed for lifecycle audit.

Examples of promote-vs-defer reasoning:

- `DROP TRANSFORM` — promoted. Uses bounded `type@language` identity.
- `DROP ACCESS METHOD` — promoted. Uses name-only identity.
- `ALTER LARGE OBJECT ... OWNER TO` — promoted. Uses OID + owner transition.
- `CREATE TRANSFORM` — deferred. `FROM SQL WITH FUNCTION` / `TO SQL WITH FUNCTION` embeds handler function names as identity. Representing this would require emitting function names as normalized facts or finding metadata, violating the no-payload contract.
- `CREATE ACCESS METHOD` — deferred. `HANDLER handler_function` embeds the handler function name as identity. Same no-payload concern.

## Public Contract

- SDK, CLI, HTTP, and MCP share the same audit semantics for rule IDs, severities, summary counts, and verdict behavior. Surface envelopes differ (library struct, CLI exit code + stdout, HTTP JSON, MCP tool response).
- This is selected long-tail PostgreSQL DDL coverage, not full PostgreSQL DDL support.
- No DCL/permission expansion.
- No live database execution or migration outcome validation.
- No handler, function, body, query, definition, or options payloads are emitted as normalized facts or finding metadata.

## Deferred / Out Of Scope

- `CREATE TRANSFORM` — deferred, identity requires handler function payload
- `CREATE ACCESS METHOD` — deferred, identity requires handler function payload
- Full PostgreSQL DDL grammar coverage
- DCL/permission expansion
- Online object-state validation

## Verification Evidence

- Long-tail census: 57 total, 55 finding_covered, 0 normalized_silent, 2 unsupported_boundary, 0 parser_error
- SQL corpus: 314 policy rule IDs, 505/505 supported targets, 100% coverage, 213 expected YAML files
- Public surface tests covered SDK, CLI, HTTP, MCP
- Payload/no-leak tests assert forbidden handler/function/body/query/definition/options values are not emitted

## Consequences

- Future agents must treat `CREATE TRANSFORM` and `CREATE ACCESS METHOD` as intentionally deferred, not forgotten.
- New boundary promotions must follow the same bounded-identity/no-payload rule: if object identity requires retaining a handler or function name, the form stays deferred until a safe opaque identity contract is defined.
- If a future implementation wants to support these forms, it must first define a safe opaque identity contract that does not emit raw handler/function names.
