## Context

DeltaScope already ships the right primitives for understanding how a YAML
config affects one rule:

- `deltascope config lint --file <path>` detects rule-level replacement hazards.
- `deltascope config status <rule-id> --config <path>` shows the effective
  ON/OFF state of one rule under a config file.
- `deltascope rules explain <rule-id>` explains shipped rule metadata.

The weak point is the human-readable handoff between these commands, not the
primitives themselves.

A user who writes a rule-level partial override has written valid config:

```yaml
rules:
  dml.where.require:
    level: warning
```

But rule-level config is a whole-policy replacement, not a merge with defaults.
Omitted fields are zero-valued, so this example also omits `enabled` and
`params`, and the rule can become OFF. `config lint` already warns about this,
but the current wording is dense, restates the mechanism without a direct next
inspection step, and does not hand the user the exact command that confirms the
effective result. `rules explain` shows metadata and examples but does not show
the default policy as a copyable baseline for a safe full override.

## Decision

Improve human-readable CLI copy and guidance across the three surfaces. Do not
change policy loading, rule behavior, audit output, parser behavior, or any
machine-readable contract.

`config lint` warning copy becomes direct and task-oriented. Each replacement
hazard states plainly:

- the rule policy is replaced, not merged with defaults,
- an omitted `enabled` becomes `false` (the rule is OFF),
- an omitted `level` becomes empty,
- omitted `params` remove the defaults,

followed by an `Inspect effective rule status:` line pointing at
`deltascope config status <rule-id> --config <path>`. The label is
`Inspect effective rule status:` rather than `Next:`, because it describes the
concrete action instead of implying a generic wizard flow. Warning ordering
stays deterministic.

`config status` remains the authoritative single-rule effective-status view.
Its text output may be lightly polished to align wording with `config lint`,
but it stays a single-rule ON/OFF check, not a full policy dump or an audit
explanation.

`rules explain` text output gains:

- a `Default policy:` block built from the actual default policy,
- a `Safe override example:` block that keeps default `enabled` and `params`
  while changing `level`,
- an `Inspect effective rule status:` command pointing at `config status`.

## Rationale

The replacement hazard is real and silent: a syntactically valid config can
disable a rule without any error. The lowest-risk fix is to make the existing
inspection loop self-explanatory rather than to change loading or merge
semantics. Better copy lets a user catch the mistake, see the effective result,
and copy a correct full override, all without new behavior.

`Inspect effective rule status:` is preferred over `Next:` because it names the
action and the artifact (the effective rule status) that resolves the warning.
`Next:` reads as a step in an unspecified multi-step wizard and undersells the
command.

Keeping JSON and exit-code semantics stable means this milestone is guidance
polish with a narrow blast radius: only the three human-readable text paths
move.

## Public Contract

Only human-readable CLI text changes. No new machine-readable schema is
introduced.

- `config lint` remains text-only.
- `config lint --strict` produces the same stdout as the default mode for
  warning-only results; it only changes the exit code to `2`.
- `config status --format json` is unchanged.
- `rules explain --format json` is unchanged.
- No output introduces a `severity` field; DeltaScope's public priority term
  remains `level`.
- No raw SQL, token, secret, or full config file content is added to output.

## Deferred / Out Of Scope

- No `LoadPolicy` behavior change.
- No partial-merge semantics for rule policy.
- No default policy changes.
- No audit behavior changes.
- No parser, rule, finding JSON, SDK, HTTP, MCP, SARIF, GitHub Actions, or
  GitLab Code Quality renderer changes.
- No new output format.
- No config auto-fix command.
- No full effective-policy dump.
- No promise that `config lint` detects every semantic interaction between
  rules.
- No CLI Chinese / i18n output. Chinese guidance is maintained in docs only.

## Architecture

Existing package ownership stays intact; this milestone moves text only.

- `internal/application/configlint` owns warning detection and warning message
  facts.
- `internal/application/configstatus` owns effective-status derivation for one
  rule.
- `internal/interfaces/cli/config.go` owns `config lint` text rendering and
  `--strict` behavior.
- `internal/interfaces/cli/config_status.go` owns `config status` CLI
  text/JSON rendering.
- `internal/interfaces/cli/rules.go` owns `rules explain` CLI rendering.
- `internal/domain/policy` remains the source of default rule policy; the
  `rules explain` safe-override example reads `policy.Default()`, not duplicated
  catalog values.
- `internal/domain/rule/catalog` remains the source of rule metadata.

No new shared "policy explanation" package is introduced for the first
implementation. Small package-local render helpers are acceptable; a shared
package is deferred until duplication is shown.

## Consequences

Future CLI text changes in these three surfaces must keep the handoff wording
consistent: `Inspect effective rule status:` pointing at `config status`, and
the rule-policy-replaces-not-merges framing in `config lint`. Docs reference the
same phrase, so the wording is a consistency point across CLI and docs.

If rule-level merge semantics are ever introduced, this decision must be
superseded by a new record, because the replacement-hazard warnings and the
safe-override framing would no longer be the full truth.

Because `config status --format json` and `rules explain --format json` are
frozen, any future machine-readable addition to either command requires a
separate decision record.

Task 2 rewrote the `config lint` replacement-hazard copy and made the CLI
render it as a multi-line block. No semantics, policy loading, exit-code

Files changed:

- `internal/application/configlint/warn.go` — new message strings only.

Warning wording contract (each warning carries both halves of the framing):

- omitted `enabled`: `<rule> is OFF because "enabled" is omitted.` + framing.
- omitted `level`: `<rule> has no effective level because "level" is omitted.` + framing.
- omitted whole `params`: `<rule> removes default params because "params" is omitted.` + framing.
- omitted `params.<key>`: `<rule> removes default "params.<key>" because that key is omitted.` + framing.
- framing: `This config replaces the whole rule policy; it does not merge with defaults.`

CLI rendering contract:

- header `Config OK with warnings` and bullet `Warnings:` unchanged.
- each warning renders as `- <line 1>` then `  ` continuation lines, followed by
  `  Inspect effective rule status:` and
  `    deltascope config status <rule-id> --config <file path>`.
- the handoff label is `Inspect effective rule status:`; `Next:` is not used.
- `config lint --strict` stdout is byte-identical to the default warning output;
  only the exit code becomes `exitUser` (2). Validation errors still take
  precedence and suppress the warning block. No `severity` field is introduced.

## Task 3 Evidence

Task 3 extended the `rules explain` human-readable text with three blocks and
left JSON, exit codes, and every other surface untouched.

Files changed:

- `internal/interfaces/cli/rules.go` — `renderRulesExplainText` gains a
  `Default policy:` block, a `Safe override example:` block, and an
  `Inspect effective rule status:` handoff. The prior `Config Example:` block
  was removed: it was generated from `policy.Default()` and was byte-identical
  to the new `Default policy:` block (same YAML, only the label differed), so
  keeping both would have printed the default policy twice. `Default Params:`
  is retained as the compact params-only view. New package-local helpers
  `resolveDefaultRulePolicy`, `renderRulePolicyYAML`, and `formatYAMLScalar`
  keep the renderer self-contained; `formatYAMLScalar` is a deliberate local
  mirror of the catalog helper (shared package deferred per this decision).
- `internal/interfaces/cli/cli_test.go` — `TestRulesExplainPrintsDetailSections`
  now asserts the new section labels instead of the removed `Config Example`.
- `internal/interfaces/cli/rules_catalog_test.go` —
  `TestRulesExplain_KnownRuleText` asserts the three new labels; new
  `TestRulesExplain_DefaultPolicyAndSafeOverride` pins the default-policy
  contents (enabled/level/params) and the full safe-override shape (enabled +
  params + `level: warning`, not a level-only snippet) for `dml.where.require`;
  new `TestRulesExplainJSON_NoTextOnlyLabels` pins JSON freedom from the
  text-only labels.

Text-only output contract (only `rules explain` text; JSON is frozen):

- `Default policy:` renders `rules.<id>.{enabled, level, params}` from
  `policy.Default()` (authoritative), with params sorted by key and empty
  params as `params: {}`. No `severity`.
- `Safe override example:` is a complete rule policy override: it keeps the
  default `enabled` and `params`, and sets `level` to `warning` when the
  default is not already `warning` (otherwise keeps `warning`). This is the
  full shape that avoids the partial-override footgun.
- `Inspect effective rule status:` is the fixed handoff
  `deltascope config status <rule-id> --config deltascope.yaml`. `Next:` is
  not used.
- `rules explain --format json` is unchanged; the `config_example` JSON field
  still carries the catalog-generated snippet.

Default-policy source is `policy.Default()` via
`policy.Default().Rules[entry.RuleID]`; the catalog and `policy.Default()` are
both derived from the shipped rule set so the lookup always succeeds, with a
defensive fallback to the entry's `Default*` fields for unreachable drift.
The renderer reads `policy.Default()` and never mutates it (params maps are
only iterated for output), preserving the no-leak invariant also guarded by
`internal/application/configstatus` tests.
