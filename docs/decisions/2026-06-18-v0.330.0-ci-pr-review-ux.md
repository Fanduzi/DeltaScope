## Context

DeltaScope already has the ingredients for good PR review, but they live in separate places:

- `deltascope audit --format github-actions` emits inline GitHub Actions workflow-command annotations.
- Markdown audit output (v0.300.0) includes a `## Action Summary` that groups findings by rule and points at the remediation command.
- `deltascope config lint --file <config> --strict` (v0.320.0) can fail CI on rule-level replacement hazards before SQL is audited.
- `deltascope rules explain <rule-id>` (v0.290.0) is the follow-up command a reviewer needs for any finding.

In practice these surfaces are fragmented. A reviewer sees a failing job or a set of annotations, then still has to open raw logs and piece together what to fix first, which rule dominates, and which `rules explain` to run. There is no single, short, PR-visible artifact that summarizes an audit the way the markdown `Action Summary` already does for local runs.

The shipped `docs/examples/github-actions.yml` is also stale. It documents an old composite-action style that posts a PR comment and requests `pull-requests: write`; it does not show the current v0.320.0 pattern with a `config lint --strict` gate, inline annotations, and a job summary. The example therefore no longer reflects how the product is meant to be used in CI.

## Decision

v0.330.0 ships a thin CI/PR review layer — presentation and docs, not a bot or service. It adds:

1. A new audit output format, `github-summary`, designed to be appended to GitHub's `$GITHUB_STEP_SUMMARY`.
2. GitHub Actions annotation wording improvements so each annotation is self-contained.
3. A refreshed GitHub Actions workflow example that combines a `config lint --strict` gate, inline annotations via `--format github-actions`, and a job summary via `--format github-summary`.
4. Reference documentation explaining when to use each output format (`github-actions`, `github-summary`, `sarif`, `gitlab-codequality`, `json`).

It does not add PR comment posting, a GitHub App, GitHub API/network calls, token handling, workflow dispatch, or a new remote service.

## Rationale

The product already produces all the data a reviewer needs; the gap is surfacing it in the place a reviewer looks (the PR checks UI and the job summary) without forcing them to read logs. Reusing the derived `Action Summary` (already a documented, privacy-bounded surface since v0.300.0) for the job summary keeps this a rendering change rather than a new model.

A job summary is the right vehicle because it is the single most visible artifact on a failed GitHub Actions check, it is append-only and free of authentication, and it maps exactly onto the short markdown summary the local report already produces. Annotations are improved rather than replaced because they remain the correct inline mechanism; they just need to carry enough context (level, rule id, explain command) to be actionable without a log dive.

The milestone deliberately stays markdown/presentation-only. Machine-readable surfaces (`json`, `sarif`, `gitlab-codequality`) and SDK/HTTP/MCP response shapes are stability-critical contracts; they already expose structured findings that CI tooling can aggregate. A new summary belongs in the human surface, not a new machine schema, until there is clear demand.

`level` (`blocker`/`warning`/`notice`) remains the only public priority concept. No `severity` field is introduced, to avoid duplicating the priority taxonomy.

## Public Contract

### `--format github-summary`

`deltascope audit --format github-summary` emits GitHub-flavored Markdown intended for `$GITHUB_STEP_SUMMARY`.

- It is a human-readable surface, **not** a stable machine-readable schema. Parsing it in automation is unsupported; machine consumers should use `--format json`, `--format sarif`, or `--format gitlab-codequality`.
- It must render:
  - a fixed title `## DeltaScope SQL Review`
  - the verdict, rendered as the uppercased canonical `report.Verdict` value (`PASS` / `REVIEW` / `REJECT`). The summary does not invent a binary `PASS`/`FAIL` term; it stays consistent with DeltaScope's three-valued verdict model (`pass`/`review`/`reject`) and the markdown renderer's use of the canonical verdict.
  - finding counts as a right-aligned table (`Statements`, `Blockers`, `Warnings`, `Notices`)
  - the derived `Action Summary` section when findings exist
  - `No findings.` for clean results
  - a trailing `Unsupported statements: N` line when the result carries unsupported statements, so unsupported diagnostics are not silently hidden in a job summary (count only; no feature label or SQL)
  - an optional short audit-context block when CLI context is available (mode/dialect/schema and their provenance, already printed elsewhere)
- It must not include raw SQL.
- It must not introduce a `severity` field; public priority remains `level`.

Illustrative shape (findings present):

```markdown
## DeltaScope SQL Review

Verdict: REJECT

| Metric | Count |
| --- | ---: |
| Statements | 3 |
| Blockers | 1 |
| Warnings | 2 |
| Notices | 0 |

## Action Summary

- [blocker] `dml.where.require`: 1 finding
  Summary: DELETE must use a WHERE clause.
  Suggestion: Add a WHERE clause or document why the full-table operation is intentional.
  Explain: deltascope rules explain dml.where.require
  Statements: 2
```

Clean result:

```markdown
## DeltaScope SQL Review

Verdict: PASS

No findings.
```

The `Action Summary` derives from existing findings and the shipped rule catalog via `report.BuildActionSummary(result, catalog.All(), report.ActionSummaryOptions{Limit: 10})`, so its ordering (`blocker` → `warning` → `notice`, then count descending, then rule id ascending), 10-group default cap, and `Showing N of M rule groups.` truncation behavior are inherited from v0.300.0 and unchanged.

### `--format github-actions` annotations

This milestone changes annotation **wording only**. The stable workflow-command behavior is preserved:

- Level-to-command mapping is unchanged: `blocker` → `::error`, `warning` → `::warning`, `notice` → `::notice`.
- File/line/column behavior is unchanged.
- Workflow-command escaping for `%`, newline, and carriage return is unchanged.

What changes:

- Finding annotation **title** becomes `[<level>] <rule_id>` (was rule id only).
- Finding annotation **message** keeps the existing message and optional suggestion, and appends `Explain: deltascope rules explain <rule_id>`.
- Unsupported-statement notices are unchanged and do **not** gain `rules explain` links, because unsupported statements have no rule id.

The change is additive within the workflow-command format; existing annotation consumers continue to parse location and level as before.

## Privacy / No-Leak Contract

`github-summary` must not include:

- raw SQL or normalized SQL
- parser `near ...` fragments
- database secrets or connection strings
- live metadata payloads

It may include:

- rule ids and levels
- finding counts
- catalog-backed summary/suggestion text and the `rules explain <rule_id>` command
- 1-based statement indexes
- the global scope marker
- audit-context fields that are already printed in the markdown report

GitHub Actions annotations keep the existing escaping for `%`, newline, and carriage return.

## Architecture

- Add a new renderer package: `internal/infrastructure/output/githubsummary`. Its `Render(report.Result)` produces the markdown job summary. It reuses `report.BuildActionSummary`, the shipped rule catalog via `catalog.All()`, and `report.ActionSummaryOptions{Limit: 10}`. It does not write to `$GITHUB_STEP_SUMMARY` (callers redirect output), does not call GitHub APIs, and does not change audit evaluation.
- CLI integration: add `github-summary` to the root `--format` validation, help text, and error message, and add a `renderResult` branch in `internal/interfaces/cli/audit.go`.
- GitHub Actions annotation wording changes stay inside `internal/infrastructure/output/githubactions` (`Render` / `formatAnnotation`).
- No changes to the application audit flow or domain rule evaluation. The milestone is confined to output renderers, CLI format wiring, and documentation.

## Task 2 Evidence: GitHub Summary Renderer Core

Task 2 added the `internal/infrastructure/output/githubsummary` renderer package (`render.go`, `render_test.go`, `README.md`) and registered it in `internal/infrastructure/output/README.md`. No CLI wiring, no GitHub Actions annotation changes, and no audit/rule/parser/policy/finding-JSON/API-shape changes were made. The renderer is not yet reachable from the CLI; that is Task 3.

**Contract clarification surfaced by implementation:** DeltaScope's verdict model is three-valued (`pass` / `review` / `reject` in `internal/domain/report/result.go`), and no human surface invents a `PASS`/`FAIL` binary today (the markdown renderer renders the canonical verdict string). The `github-summary` renderer therefore renders the verdict as the **uppercased canonical value** — `PASS`, `REVIEW`, or `REJECT` — rather than inventing a `FAIL` term that would collapse `reject` and `review`. This keeps the job summary consistent with the report model and the markdown renderer. The illustrative shapes above were corrected from the earlier `FAIL` wording to `REJECT` accordingly. A blocker-only audit renders `Verdict: REJECT`; a warnings-only audit renders `Verdict: REVIEW`.

**Unsupported-statements count:** the renderer appends `Unsupported statements: N` when the result carries unsupported statements, surfacing only the count (no feature label, no SQL) so unsupported diagnostics are not silently hidden in a job summary. This is reflected in the package README and in `TestRenderUnsupportedOnly`.

Renderer behavior is covered by focused tests: clean result, finding action summary, catalog-backed summary/suggestion, global scope marker (no statement index), raw-SQL omission, 10-group truncation, determinism, no `severity` wording, and unsupported-only count. It reuses `report.BuildActionSummary(result, catalog.All(), report.ActionSummaryOptions{Limit: 10})` for grouping/ordering/cap, and the shared `output.GetBuilder`/`PutBuilder` builder pool.

Wording changes, as specified in the public contract:

- Finding annotation **title** is now `[<level>] <rule_id>` (was rule id only), e.g. `title=[blocker] dml.where.require`.

No `severity` field is introduced and no raw SQL is added beyond what an existing finding message already carries.

## Consequences

A new human-readable audit format becomes public. Future changes to `github-summary` output are a presentation choice, not a machine-contract change, but the fixed title, verdict, counts, derived `Action Summary`, and the no-raw-SQL / no-`severity` guarantees become user-relied properties and should be preserved.

The GitHub Actions annotation text becomes part of what reviewers see inline. The `[level] rule_id` title and `Explain:` line should be treated as stable, additive wording; the underlying workflow-command location and level semantics are unchanged.

The shipped rule catalog remains part of the audit UX (summary/suggestion text appears in both the markdown report and the job summary). New rules should keep catalog summary and suggestion text useful enough to surface in CI summaries.
