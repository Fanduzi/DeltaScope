## Context

DeltaScope has three user-facing surfaces around rules and config:

- `deltascope rules explain <rule_id>` explains what a shipped rule means.
- `deltascope config status <rule-id>` reports the effective ON/OFF and `level` of one rule under the active config (shipped in v0.310.0).
- `deltascope config lint --file <path>` validates that a YAML config file is syntactically and semantically valid.

`config status` already explains the footgun for a single rule: under audit-faithful rule-level replacement (documented in v0.310.0), mentioning a rule in YAML replaces the whole `RulePolicy`. Omitted `enabled` becomes false, omitted `level` becomes empty, and omitted params are absent. A user who writes

```yaml
rules:
  dml.where.require:
    level: warning
```

intending only to soften the level actually turns the rule **off**, because `enabled` is omitted and replaced with false.

`config lint` currently cannot see this. Today `lintConfigFile` validates shape and values (unknown rule, invalid level, unknown param, param type mismatch) and, on success, prints only:

```text
Config OK
```

The YAML above is valid YAML and valid current config, so `config lint` calls it `Config OK`. That is the gap v0.320.0 closes: `config lint` should catch the rule-level replacement footgun without changing audit behavior, without changing `LoadPolicy`, and without claiming partial configs merge.

The second motivation is housekeeping. The lint-warning work is small on its own, and recent public docs have accumulated formulaic, AI-flavored phrasing. v0.320.0 bundles a focused public-docs cleanup into the same milestone rather than shipping a thin release and a separate cleanup.

## Decision

v0.320.0 adds **non-fatal warnings** to `deltascope config lint --file <path>` for rule-level replacement hazards, and adds a `--strict` flag that promotes warnings to a non-zero exit. In the same milestone it humanizes public docs per the `humanizer-zh` criteria, without changing technical meaning or stable terms.

v0.320.0 does **not** change `LoadPolicy`, policy defaults, audit behavior, rule evaluation, parser behavior, finding JSON, SDK/HTTP/MCP output, or the SARIF / GitHub Actions / GitLab CodeQuality renderers. It does **not** add a `severity` field. Warnings are advisory; they do not merge partial configs onto defaults and do not alter what audit does with the file.

## Config Lint Warning Contract

Default `config lint` behavior (no `--strict`):

| File state | Output | Exit |
|---|---|---|
| No errors, no warnings | `Config OK` | 0 |
| No errors, has warnings | `Config OK with warnings`, then the warning list | 0 |
| Has errors | The error message | 2 |

Errors take precedence over warnings: if the file is invalid, lint prints the error and exits 2 without enumerating warnings.

`--strict`:

| File state | Output | Exit |
|---|---|---|
| No errors, no warnings | `Config OK` | 0 |
| No errors, has warnings | same `Config OK with warnings` + warning list | 2 |
| Has errors | the error message | 2 |

`--strict` only changes the exit code for the warnings-only case. It does not change wording and does not change how errors are handled.

The existing valid/invalid config definitions do not change. The only behavioral change is warning visibility and the `--strict` exit code. `config lint --file` keeps requiring `--file`; `config init`, `config show-default`, and `config status` are unchanged.

Example for the canonical footgun (default mode):

```text
$ deltascope config lint --file ./deltascope.yaml
Config OK with warnings
  warning: rule "dml.where.require" is mentioned without "enabled"; the rule policy is replaced, not merged, so omitted "enabled" becomes false and the rule is OFF.
```

Same file with `--strict` exits 2 but prints the same text. A clean file still prints `Config OK` and exits 0 under both modes. An unknown rule still prints the existing error and exits 2.

## Warning Detection Scope

A warning is produced when a config mentions a **known** rule but omits or partially supplies fields in a way that changes effective behavior under rule-level replacement. v0.320.0 covers four minimum cases:

1. **Omitted `enabled`, default `true`.** The rule policy is replaced, omitted `enabled` becomes false, and the rule is OFF.
2. **Omitted `level`, default non-empty.** The rule policy is replaced, omitted `level` becomes empty, replacing the default level.
3. **Omitted `params`, default has params.** The rule policy is replaced, omitted `params` become empty, removing the default params.
4. **Partial `params`, default has params.** The rule policy is replaced, so omitted default params are removed, not merged.

Detection reuses the same raw-config shape `config lint` and `config status` already parse (`rawRuleConfig` with `Enabled *bool`, `Level string`, `Params map[string]any`). `Enabled` is a pointer precisely so omission is distinguishable from an explicit `false`; this is what lets case 1 report omission rather than a deliberate disable. The comparison baseline is `policy.Default()`, which `lintConfigFile` already loads.

**Task 2 implementation note.** The warning core ships in a new `internal/application/configlint` package and keeps a local minimal raw-config parser (`Enabled *bool`, `Level *string`, `Params map[string]any`) identical to `configstatus`, including the `Level` pointer so an omitted `level` is distinguishable from an explicit empty string. It derives warnings directly from the parsed raw config and `policy.Default()`; it does not call `viperconfig.LoadPolicy`, because the effective consequences follow from replacement semantics rather than the merged policy. It intentionally does not refactor the shipped `configstatus`/CLI parsers in this task; consolidating the now-three raw-config parsers (CLI `lintConfigFile`, `configstatus`, `configlint`) into a shared helper is deferred cleanup.

### Deterministic Ordering

Warnings must be deterministic so docs, tests, and diffs are stable:

- Order warnings by `rule_id` ascending.
- Within one rule, order by field: `enabled`, then `level`, then each `params.<key>` alphabetically.

### Warning Wording

Wording must be concrete and must not overclaim. Each warning:

- States that the rule policy is **replaced, not partially merged**.
- States the effective consequence for that field (omitted `enabled` becomes false and the rule is OFF; omitted `level` becomes empty; omitted params are removed).
- Prefers `level`, never `severity`.
- Does not promise remediation, a full effective-policy dump, or a migration guarantee.

Reference wording:

```text
warning: rule "dml.where.require" is mentioned without "enabled"; the rule policy is replaced, not merged, so omitted "enabled" becomes false and the rule is OFF.
warning: rule "dml.where.require" is mentioned without "level"; the rule policy is replaced, not merged, so omitted "level" becomes empty, replacing the default "blocker".
warning: rule "ddl.table.audit_columns.require" is mentioned without "params"; the rule policy is replaced, not merged, so omitted "params" become empty, removing the default params.
warning: rule "dml.where.require" supplies a partial "params" map; the rule policy is replaced, not merged, so omitted default params ("required") are removed.
```

### Errors Stay Errors

Unknown rules, invalid levels, unknown params, param type mismatches, malformed YAML, and a missing/unreadable file remain **errors** (exit 2), not warnings. v0.320.0 adds no new error categories and removes none.

## CLI / JSON Boundary

`config lint` has no JSON surface today. Inspecting `internal/interfaces/cli/config.go`, the lint command prints only the literal string `Config OK` on success and returns a user error on failure; there is no `--format` flag and no JSON rendering for lint. v0.320.0 therefore needs **text output only** for `config lint`. It does not invent a lint JSON contract.

If later implementation discovers an existing lint JSON surface elsewhere in the codebase, the implementation task will document and preserve it rather than widen scope. `config status --format json` is a separate, already-shipped contract and remains unchanged.

## Rationale

`config status` already explains one rule's effective state, but only after the user thinks to ask. `config lint` is the command users run to check a whole file, so the replacement hazard belongs there, at the moment the file is being validated. Surfacing it as a **warning** rather than an error keeps valid configs valid: a user may intentionally disable a rule by omitting `enabled`, and the existing explicit-disable path (`enabled: false` with full fields) must keep printing `Config OK`. `--strict` gives CI and pre-commit hooks an opt-in non-zero exit without breaking interactive use.

Text-only output matches the existing `config lint` contract: there is no JSON lint surface to preserve or extend, so the smallest correct change is additional text and one flag. Adding a lint JSON contract would be a separate decision with its own stabilization work and is deferred.

Bundling the docs cleanup avoids shipping a near-empty release and lets the v0.320.0 release notes carry both the lint warning and the cleanup as one coherent change. Keeping historical release notes, old DRs, and `internal/**/README.md` out of scope bounds the diff and avoids rewriting material that documents past, frozen behavior.

## Public Contract

After v0.320.0, users can rely on:

- `config lint` printing `Config OK` for a file with no errors and no warnings, exit 0.
- `config lint` printing `Config OK with warnings` plus a warning list for a file with replacement hazards, exit 0 by default.
- `config lint --strict` exiting 2 for a warnings-only file (same text), exit 0 for a clean file, exit 2 for errors.
- Warnings being deterministic: ordered by `rule_id` ascending, then `enabled`, `level`, `params.<key>` alphabetically.
- Warnings naming the replaced, not merged, policy and the effective field consequence.
- Existing lint errors (unknown rule, invalid level, unknown param, param type mismatch, malformed YAML, missing file) still exiting 2.
- No change to `config init`, `config show-default`, or `config status` (including `config status --format json`).
- No change to `LoadPolicy`, default policy values, audit behavior, rule evaluation, parser behavior, finding JSON, SDK/HTTP/MCP output, or the SARIF / GitHub Actions / GitLab CodeQuality renderers.
- No `severity` field introduced; `level` remains the public priority field.
- No lint JSON contract introduced in this milestone.

## Privacy / No-Leak Contract

`config lint` continues to read only:

- the selected YAML config file
- built-in default policy
- rule catalog metadata (rule IDs, default levels, default params)

It does not accept SQL, parse SQL, run the audit service, connect to a database, or emit user SQL payloads, parser `near ...` text, database object names, or live metadata. The new warnings echo only rule IDs and field names derived from the user's own config file and the defaults. `--strict` changes only the exit code; it does not change what is read or printed.

## Deferred / Out Of Scope

v0.320.0 will not:

- Change `LoadPolicy` or introduce merge semantics for partial rule configs. Partial configs still replace the whole `RulePolicy`; warnings only describe that fact.
- Change audit behavior, rule evaluation, default policy values, or finding JSON shape.
- Add a lint JSON contract. Text output only.
- Add SDK, HTTP, or MCP lint-warning surfaces.
- Add a `severity` field or rename `level`.
- Add parser support or new audit rules.
- Add a bulk `config effective` command.
- Humanize historical release notes older than v0.290.0, old `docs/decisions/*.md`, `internal/**/README.md` (absent a code change), or `docs/examples/*` prose.
- Commit `docs/plans/` or `docs/plans_zh/`.
- Push, tag, release, dispatch workflows, or publish npm/Homebrew. Release happens only on explicit user instruction via the `go-release` skill.

## Consequences

`config lint` becomes a second surface (besides `config status`) that documents rule-level replacement. Both must keep agreeing with `LoadPolicy` and audit; future policy-loading changes must update both the status and the lint-warning derivations together.

`--strict` makes `config lint` usable as a CI gate for replacement hazards. Teams that adopt it in CI will see builds fail on previously-`Config OK` files, so the v0.320.0 release notes must call out the opt-in nature of `--strict` and that default-mode exit codes are unchanged.

The docs cleanup sets a tone expectation for future public docs: technical and direct over promotional or formulaic. Future doc work in the in-scope paths should match that tone without a separate decision.
