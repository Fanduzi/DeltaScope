## Context

v0.100.0 and v0.110.0 established long-tail boundary coverage: 57/57 PostgreSQL DDL forms produce lifecycle findings. Rules fire, identity is bounded, and no SQL expression payloads leak. However, findings currently carry only rule ID, level, and message. They do not expose the structured metadata that consumers need to make operational decisions — for example, whether a `CREATE INDEX` is `CONCURRENT`, how many columns an index covers, whether an `ADD COLUMN` has a default expression, or whether a `SET DATA TYPE` is a safe in-place rewrite.

This milestone enriches existing findings with **bounded semantic metadata**: structured key-value pairs derived from the AST that describe what the statement does, without exposing the raw SQL expressions that triggered the finding.

This is a **metadata depth release**, not new DDL grammar coverage. No new DDL forms become supported. No new rules are added. Existing rule IDs and levels do not change.

## Decision

Enrich four existing PostgreSQL DDL rules with additive, bounded metadata fields. Each rule's extractor reads specific AST fields and emits structured metadata into the finding. The metadata is bounded: it exposes semantic properties (booleans, counts, categorical enums) and never exposes raw SQL expression text.

### Enriched rules

1. **`ddl.pg.create_index.concurrently.require`** — `CREATE INDEX` metadata
2. **`ddl.pg.alter.add_column.non_null_default.rewrite.warn`** — `ADD COLUMN ... NOT NULL DEFAULT` metadata
3. **`ddl.pg.alter.add_column.non_null_no_default.warn`** — `ADD COLUMN ... NOT NULL` metadata
4. **`ddl.pg.alter.set_data_type.rewrite.warn`** — `ALTER COLUMN ... SET DATA TYPE` metadata

### Allowed bounded metadata output

These structured fields may be emitted as finding metadata:

| Field | Type | Rules | Description |
|-------|------|-------|-------------|
| `concurrently` | bool | create_index.concurrently | Whether `CONCURRENTLY` was specified |
| `index_kind` | string enum | create_index.concurrently | Index kind: `btree`, `hash`, `gist`, `gin`, `spgist`, `brin`, or empty for default |
| `column_count` | int | create_index.concurrently | Number of index columns |
| `included_column_count` | int | create_index.concurrently | Number of `INCLUDE` columns |
| `has_predicate` | bool | create_index.concurrently | Whether a partial-index `WHERE` predicate exists |
| `has_expression_keys` | bool | create_index.concurrently | Whether any index key is an expression |
| `expression_count` | int | create_index.concurrently | Number of expression index keys |
| `has_default` | bool | add_column non_null rules | Whether the column has a `DEFAULT` clause |
| `default_kind` | string enum | add_column non_null rules | Default kind: `literal`, `null`, `function`, `expression`, or empty |
| `not_null` | bool | add_column non_null rules | Whether `NOT NULL` is specified |
| `has_using` | bool | set_data_type.rewrite | Whether a `USING` expression is specified |

### Forbidden payload (must not be emitted)

The following are explicitly excluded from all output surfaces (metadata, messages, corpus YAML, CLI text, HTTP JSON, MCP, SDK):

- Predicate SQL text (`WHERE` clause expression)
- Expression index SQL text (index key expressions)
- Default expression SQL text
- Default function names
- `USING` expression SQL text
- Body, query, definition, or options payload
- Arbitrary handler or function names

## Rationale

v0.100.0's decision record established the principle that DeltaScope must not leak SQL expression bodies. This principle remains: metadata fields are bounded semantic properties, not raw SQL.

The metadata contract is strictly additive. Existing consumers reading `rule_id`, `level`, and `message` remain fully compatible. New metadata fields are optional key-value pairs that consumers may ignore.

Cross-surface consistency is enforced: SDK, CLI, HTTP, and MCP must all emit the same metadata shape for the same rule on the same input. This prevents surface-specific drift that would break automation.

## Public Contract

1. **Additive only.** Metadata changes do not alter rule IDs, rule levels, verdict semantics, or existing output fields.
2. **No SQL expression bodies.** No raw SQL expression text is emitted in any output surface.
3. **Structured and bounded.** Metadata values are booleans, integers, or categorical string enums — never free-form SQL.
4. **Cross-surface consistency.** SDK, CLI, HTTP, and MCP produce identical metadata for identical input.
5. **Compatible.** Consumers that ignore metadata continue to work without changes.

## Scope

### In scope

- `ddl.pg.create_index.concurrently.require` metadata enrichment
- `ddl.pg.alter.add_column.non_null_default.rewrite.warn` metadata enrichment
- `ddl.pg.alter.add_column.non_null_no_default.warn` metadata enrichment
- `ddl.pg.alter.set_data_type.rewrite.warn` metadata enrichment
- No-leak tests proving forbidden payloads are absent
- SQL corpus expected YAML updates reflecting new metadata
- Public surface tests (SDK, CLI, HTTP, MCP) verifying metadata consistency

### Out of scope

- Full PostgreSQL DDL support
- DCL/permission expansion
- Live schema validation
- Validating old/new type compatibility
- Validating index operator classes
- Storing predicate, default, expression, or USING SQL text
- Changing rule IDs or levels
- v1.0/stable API claims

## Verification Evidence

- No-leak tests will verify forbidden payloads are absent across all output surfaces.
- SQL corpus expected YAML will be updated and gate-checked.
- Public surface tests will confirm metadata consistency across SDK, CLI, HTTP, and MCP.
- Decision record gate will pass.
- GitNexus detect_changes will confirm no production symbol changes in this task.

## Consequences

- Future metadata additions must follow the same additive, bounded, no-SQL-text contract.
- If an AST field cannot be safely categorized as bounded metadata, it must be excluded rather than approximated.
- Cross-surface consistency tests become a permanent gate for any metadata change.
