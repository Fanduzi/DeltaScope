## Context

After v0.120.0 shipped PostgreSQL semantic metadata and long-tail DDL enhancements, the existing ALTER TABLE coverage census (`postgresql_alter_table_coverage_census_postgresql_tag_test.go`) covers 42 baseline cases: 41 finding-covered, 1 normalized-silent.

PostgreSQL `ALTER TABLE` supports over 40 distinct action types. DeltaScope covers selected migration-safety patterns, not the full grammar. Without a durable characterization of the residual surface, future contributors or agents may incorrectly assume full ALTER TABLE support, or may waste effort on low-priority syntax families.

Task 1 created a residual census (66 cases across 7 families) to serve as the planning source for the next implementation pack. Tasks 3A–3C implemented the first pack: storage/layout rules (`SET TABLESPACE`, `SET ACCESS METHOD`) and their public surface coverage.

## Decision

1. The Task 1 residual census is the authoritative planning source for the next batch of PostgreSQL ALTER TABLE implementation work.
2. DeltaScope does not claim full PostgreSQL ALTER TABLE grammar coverage. Public docs and release notes must not state "full PostgreSQL ALTER TABLE support."
3. Unsupported and parser-error forms are intentional boundaries until explicitly promoted through a future decision.
4. Future ALTER TABLE findings continue to follow bounded metadata / no-payload principles: no expression bodies, no operator payloads, no partition bound literals.
5. This decision record has been expanded from "residual census prioritization" to include the storage/layout implementation results (Tasks 3A–3C).

### Design Rationale

**Why separate actions instead of extending `enable_trigger` with a `trigger_mode` option:**

The existing `enable_trigger` action already fires `ddl.pg.alter.enable_trigger.notice` via `pgAlterActionAdvisoryRule`, which matches on action string alone and does not forward `alter.Options` into finding metadata. Mapping REPLICA/ALWAYS triggers to the same `enable_trigger` action would cause double findings (existing rule + new mode-specific rule) without a clear way to suppress the generic message.

Using unique actions (`enable_replica_trigger`, `enable_always_trigger`, `enable_rule`, `disable_rule`, `enable_replica_rule`, `enable_always_rule`) ensures each SQL variant gets exactly one finding with a mode-specific message. This is consistent with how `set_logged` / `set_unlogged` use separate actions rather than a shared `set_logged_state` with an option.

**Why notice for trigger mode and enable rule; warning for disable rule:**

- Enabling a trigger in REPLICA/ALWAYS mode changes replication behavior but does not disable anything — notice is appropriate.
- Enabling a rule re-activates query routing — notice is appropriate (parallel to `enable_trigger.notice`).
- Disabling a rule removes query routing logic — warning is appropriate (parallel to `disable_trigger.warn`).

**Why RLS cases are unchanged:**

All four RLS variants (`ENABLE/DISABLE/FORCE/NO FORCE ROW LEVEL SECURITY`) are already finding-covered by dedicated rules. No action needed.

## Task 5: Reloptions Pack Design

Date: 2026-05-19
Status: Accepted (design-only, no production code in this task)

### Candidate Analysis

The `table_properties` family currently has 12 census cases: 2 finding-covered (SET TABLESPACE, SET ACCESS METHOD from Task 3), 10 unsupported_boundary. Two of those 10 are table-level reloptions:

- `ALTER TABLE users SET (fillfactor = 70)` — SET reloptions
- `ALTER TABLE users RESET (fillfactor)` — RESET reloptions

These are the only `SET (...)` / `RESET (...)` forms in the census that target table-level storage parameters. Column-level variants (`ALTER TABLE ... ALTER COLUMN ... SET (n_distinct = -1)`) use different pg_query enum values (`AT_SetOptions` / `AT_ResetOptions`) and belong to the `column_attributes` family. They are explicitly out of scope for Task 5.

### Promotion Decisions

Both candidates are promoted to finding-covered.

| # | SQL Family | Decision | Rule ID Draft | Level | New Action |
|---|-----------|----------|---------------|-------|------------|
| 1 | `ALTER TABLE ... SET (...)` | promote | `ddl.pg.alter.set_reloptions.warn` | warning | `set_reloptions` |
| 2 | `ALTER TABLE ... RESET (...)` | promote | `ddl.pg.alter.reset_reloptions.notice` | notice | `reset_reloptions` |

### Design Rationale

**Why warning for SET and notice for RESET:**

SET reloptions changes storage parameters that can affect table rewrite behavior, autovacuum scheduling, and physical storage layout. Some parameters (like `fillfactor`) require a table rewrite, but DeltaScope cannot determine which parameters trigger rewrites without live catalog access. The conservative level is warning.

RESET reloptions reverts parameters to their defaults, which is generally less risky. This is informational — notice level.

**Why bounded counts instead of per-parameter rules:**

PostgreSQL supports dozens of storage parameters across TOAST, autovacuum, and storage families. Creating per-parameter rules (e.g., `set_fillfactor`, `set_autovacuum_enabled`) would explode the rule surface and leak configuration details. A single `set_reloptions` rule with `option_count` provides audit visibility without leaking sensitive parameter names or values.

### Stable Object Identity

| Category | Identity Keys |
|----------|--------------|
| Reloptions change | table name + action (set/reset) |

### Bounded Metadata Keys

SET reloptions:

| Key | Source | Example |
|-----|--------|---------|
| `operation` | fixed | `alter_table` |
| `action` | alter action | `set_reloptions` |
| `table` | DDL table name | `users` |
| `option_count` | count of SET parameters | `2` |
| `has_reloptions` | always | `true` |

RESET reloptions:

| Key | Source | Example |
|-----|--------|---------|
| `operation` | fixed | `alter_table` |
| `action` | alter action | `reset_reloptions` |
| `table` | DDL table name | `users` |
| `reset_count` | count of RESET parameters | `1` |
| `has_reloptions` | always | `true` |

### Forbidden Payload Keys / Values

The following must NEVER appear in finding metadata:

| Forbidden Key | Why |
|---------------|-----|
| `option_names` | Leaks parameter names |
| `option_values` | Leaks parameter values |
| `reloptions` | Leaks raw reloption list |
| `fillfactor` | Leaks specific parameter name |
| `autovacuum_enabled` | Leaks specific parameter name |
| Any parameter name as key | Leaks configuration detail |
| Any parameter value as value | Leaks configuration value |
| `raw_sql` | Leaks full statement |
| `reloption_expr` | Leaks expression payload |

The rules emit only the option count, a has-reloptions flag, and the table name. No parameter names, no parameter values, no raw expressions.

### No-Leak / No-Overclaim

The reloptions rules do NOT:
- Emit any storage parameter name or value.
- Claim to determine whether the SET triggers a table rewrite.
- Claim to validate parameter names against PostgreSQL's supported set.
- Claim to estimate rewrite duration or lock contention.
- Claim live catalog validation of current reloption state.
- Cover column-level `ALTER COLUMN ... SET (...)` (different pg_query enum, different family).
- Cover index-level `ALTER INDEX ... SET (...)` (separate statement type).
- Claim full PostgreSQL ALTER TABLE support.

### Parser Feasibility

Both actions use existing pg_query v6.2.2 enum values:

| pg_query Enum | Go Constant | Value | New Action |
|---------------|-------------|-------|------------|
| `AT_SetRelOptions` | `AlterTableType_AT_SetRelOptions` | 36 | `set_reloptions` |
| `AT_ResetRelOptions` | `AlterTableType_AT_ResetRelOptions` | 37 | `reset_reloptions` |

The cmd payload provides `cmd.GetDef()` as a `List` of `DefElem` nodes. Each `DefElem` has:
- `defname`: the option name (e.g., "fillfactor")
- `arg`: the option value (e.g., Integer 70)

For no-leak compliance, the parser must:
- Count the number of DefElem items → `option_count` (for SET) or `reset_count` (for RESET)
- NOT extract or forward individual option names or values into alter.Options
- Emit action `set_reloptions` or `reset_reloptions`

The implementation is additive: new switch cases in `extractor_ddl_alter.go`, no modification to existing cases.
