## Context

After v0.120.0 shipped PostgreSQL semantic metadata and long-tail DDL enhancements, the existing ALTER TABLE coverage census (`postgresql_alter_table_coverage_census_postgresql_tag_test.go`) covers 42 baseline cases: 41 finding-covered, 1 normalized-silent.

PostgreSQL `ALTER TABLE` supports over 40 distinct action types. DeltaScope covers selected migration-safety patterns, not the full grammar. Without a durable characterization of the residual surface, future contributors or agents may incorrectly assume full ALTER TABLE support, or may waste effort on low-priority syntax families.

Task 1 created a residual census (66 cases across 7 families) to serve as the planning source for the next implementation pack. Tasks 3A–3C implemented the first pack: storage/layout rules (`SET TABLESPACE`, `SET ACCESS METHOD`) and their public surface coverage.

## Decision

1. The Task 1 residual census is the authoritative planning source for the next batch of PostgreSQL ALTER TABLE implementation work.
2. DeltaScope does not claim full PostgreSQL ALTER TABLE grammar coverage. Public docs and release notes must not state "full PostgreSQL ALTER TABLE support."
3. Unsupported and parser-error forms are intentional boundaries until explicitly promoted through a future decision.
4. Future ALTER TABLE findings continue to follow bounded metadata / no-payload principles: no expression bodies, no operator payloads, no partition bound literals.
5. This decision record has been expanded from "residual census prioritization" to include the storage/layout implementation results (Tasks 3A–3C).

## No-Leak / No-Overclaim

The storage/layout rules do not output:
- `fillfactor`, `reloptions`, `cluster`, `tablespace_sql`, `access_method_sql`
- They do not claim to validate whether the target tablespace or access method exists.
- They do not claim to estimate rewrite duration or perform live validation.

## Deferred / Out of Scope

- reloptions `SET (...)` / `RESET (...)`
- `CLUSTER ON` / `SET WITHOUT CLUSTER`
- `SET WITHOUT OIDS`
- `INHERIT` / `NO INHERIT`
- `OF TYPE` / `NOT OF`
- `ALTER TABLE ALL IN TABLESPACE`
- PG17 parser-error syntax (NOT NULL NOT VALID, ALTER CONSTRAINT NOT ENFORCED/INHERIT/NO INHERIT)
- CHECK/EXCLUDE expressions: do not emit expression bodies.
- Generated expressions: do not emit expression bodies.
- Partition bounds: do not emit bound expressions.
- Live catalog validation of tablespace/access method existence: not performed.
- Function/operator volatility or immutability: not inferred.
- Full PostgreSQL ALTER TABLE grammar support: not claimed.
- DCL/permission expansion: out of scope.

This milestone is not "full PostgreSQL ALTER TABLE support."

### Design Rationale

**Why separate actions instead of extending `enable_trigger` with a `trigger_mode` option:**

The existing `enable_trigger` action already fires `ddl.pg.alter.enable_trigger.notice` via `pgAlterActionAdvisoryRule`, which matches on action string alone and does not forward `alter.Options` into finding metadata. Mapping REPLICA/ALWAYS triggers to the same `enable_trigger` action would cause double findings (existing rule + new mode-specific rule) without a clear way to suppress the generic message.

Using unique actions (`enable_replica_trigger`, `enable_always_trigger`, `enable_rule`, `disable_rule`, `enable_replica_rule`, `enable_always_rule`) ensures each SQL variant gets exactly one finding with a mode-specific message. This is consistent with how `set_logged` / `set_unlogged` use separate actions rather than a shared `set_logged_state` with an option.

**Why notice for trigger mode and enable rule; warning for disable rule:**

- Enabling a trigger in REPLICA/ALWAYS mode changes replication behavior but does not disable anything — notice is appropriate.
- Enabling a rule re-activates query routing — notice is appropriate (parallel to `enable_trigger.notice`).
- Disabling a rule removes query routing logic — warning is appropriate (parallel to `disable_trigger.warn`).

**Why RLS cases are unchanged:**

All four RLS variants (`ENABLE/DISABLE/FORCE/NO FORCE ROW LEVEL SECURITY`) are already finding-covered by dedicated rules. No action needed.

### Stable Object Identity

| Category | Identity Keys |
|----------|--------------|
| Trigger mode change | table name + trigger name + trigger_mode |
| Rule mode change | table name + rule name + rule_mode |

### Bounded Metadata Keys

Trigger mode variants:

| Key | Source | Example |
|-----|--------|---------|
| `operation` | fixed | `alter_table` |
| `action` | alter action | `enable_replica_trigger` / `enable_always_trigger` |
| `table` | DDL table name | `users` |
| `trigger` | alter.Name | `trg_users_audit` |
| `trigger_mode` | alter option | `replica` / `always` |

Rule variants:

| Key | Source | Example |
|-----|--------|---------|
| `operation` | fixed | `alter_table` |
| `action` | alter action | `enable_rule` / `disable_rule` / `enable_replica_rule` / `enable_always_rule` |
| `table` | DDL table name | `users` |
| `rule` | alter.Name | `users_rewrite_rule` |
| `rule_mode` | alter option | `replica` / `always` (absent for `enable_rule` / `disable_rule`) |

### Forbidden Payload Keys / Values

The following must NEVER appear in finding metadata:

| Forbidden Key | Why |
|---------------|-----|
| `trigger_function` | Leaks implementation detail |
| `trigger_body` | Leaks procedural logic |
| `trigger_when` | Leaks timing expression |
| `trigger_events` | Leaks event specification |
| `trigger_columns` | Leaks column list |
| `rule_query` | Leaks rewrite rule body |
| `rule_body` | Leaks rule command text |
| `rule_commands` | Leaks rule DO / INSTEAD payload |
| `rule_where` | Leaks rule qualification |
| Any raw SQL | Leaks full statement |

The rules emit only the trigger/rule object name (an identifier already present in the SQL statement), the mode, and the table name. No function names, no bodies, no expressions, no predicates.

### No-Leak / No-Overclaim

The trigger/rule mode rules do NOT:
- Emit trigger function names or trigger body content.
- Emit rule query body, rule commands, or rule qualification expressions.
- Claim live validation of trigger or rule existence in the database catalog.
- Claim runtime behavior validation (whether the trigger actually fires, whether the rule actually routes).
- Claim full PostgreSQL `ALTER TABLE` support.
- Claim `ALTER TRIGGER` or `ALTER RULE` standalone statement support (those are separate statement types).

### Parser Feasibility

All 6 new actions use existing pg_query v6.2.2 enum values:

| pg_query Enum | Value | New Action |
|---------------|-------|------------|
| `AT_EnableReplicaTrig` | 41 | `enable_replica_trigger` |
| `AT_EnableAlwaysTrig` | 40 | `enable_always_trigger` |
| `AT_EnableRule` | 47 | `enable_rule` |
| `AT_DisableRule` | 50 | `disable_rule` |
| `AT_EnableReplicaRule` | 49 | `enable_replica_rule` |
| `AT_EnableAlwaysRule` | 48 | `enable_always_rule` |

All enum values carry the trigger/rule name via `cmd.GetName()`. No expression or body parsing is needed. The implementation is additive: new switch cases in `extractor_ddl_alter.go`, no modification to existing cases.

PostgreSQL grammar note: `ENABLE REPLICA TRIGGER` and `ENABLE ALWAYS TRIGGER` accept only a specific trigger name (not `ALL` or `USER`). Similarly, `ENABLE/DISABLE RULE` and their REPLICA/ALWAYS variants always take a specific rule name. No scope handling is needed.

### Public Surface Expectations

SDK, CLI, HTTP, and MCP should all assert:
- `enable_replica_trigger` rule fires with metadata including `trigger`, `trigger_mode=replica`, `table`.
- `enable_always_trigger` rule fires with metadata including `trigger`, `trigger_mode=always`, `table`.
- `enable_rule` rule fires with metadata including `rule`, `table`.
- `disable_rule` rule fires with metadata including `rule`, `table`.
- `enable_replica_rule` rule fires with metadata including `rule`, `rule_mode=replica`, `table`.
- `enable_always_rule` rule fires with metadata including `rule`, `rule_mode=always`, `table`.
- No finding contains trigger function names, trigger body, rule query, or any forbidden payload key.

### Deferred / Non-Goals

- Standalone `ALTER TRIGGER ... ENABLE/DISABLE` — separate statement type, not ALTER TABLE.
- Standalone `CREATE RULE` / `DROP RULE` body content — already covered by existing lifecycle rules but rule body emission is forbidden.
- `ALTER TABLE ... ENABLE TRIGGER name` with `trigger_scope` metadata forwarding — pre-existing gap; the existing rule does not emit `trigger_scope` in finding metadata. Fixing this is out of scope for Task 4.
- Full PostgreSQL trigger system introspection (firing order, condition evaluation, dependency chains).
- Full PostgreSQL rule system introspection (query rewriting analysis, rule cascade detection).
- Live catalog validation of trigger or rule existence.
- Live validation of trigger firing behavior.
- Full PostgreSQL ALTER TABLE grammar support.

## Recommended Next Pack

1. **Priority 1: Task 4 implementation** — Trigger/rule mode rules. 6 parser cases + 6 rules + public surface tests. Bounded, low-risk, all parser infrastructure exists.
2. **Priority 2: parser-error boundary documentation / parser support investigation** — PG17 syntax blocks downstream normalization and rule evaluation. Four forms cannot be classified until the parser handles them.
3. **Priority 3: remaining table_properties family** — 10/12 still unsupported. Includes `SET (...)` / `RESET (...)` reloptions, `CLUSTER ON` / `SET WITHOUT CLUSTER`, `SET WITHOUT OIDS`, `INHERIT` / `NO INHERIT`, `OF TYPE` / `NOT OF`, `ALTER TABLE ALL IN TABLESPACE`.
4. **Priority 4: column_attributes** — Bounded metadata candidates (STATISTICS, n_distinct, STORAGE, COMPRESSION), but lower migration-safety priority and some generated-expression payload risk.
5. **Priority 5: constraint residuals** — EXCLUDE USING gist and ALTER CONSTRAINT DEFERRABLE have high value, but parser gaps and expression/operator payload risks require careful handling.
