# v0.260.0 Unsupported Diagnostics Guidance Codes

Date: 2026-06-04
Status: Accepted
Related milestone/version: v0.260.0
Related tests:
  `internal/application/audit/unsupported_diagnostics_evidence_test.go`
  `internal/application/audit/unsupported_diagnostics_evidence_postgresql_tag_test.go`
  `pkg/deltascope/audit_unsupported_diagnostics_evidence_test.go`

## Context

When DeltaScope encounters SQL it cannot parse, the diagnostic output includes `classification`, `reason`, `action_hint`, `audited`, and `dialect`. A user who sees `classification=parser_error` knows the statement was not audited, but cannot tell which unsupported boundary it falls into or where to find detailed evidence about why.

v0.250.0 classified all 29 remaining parser_error cases into feasibility buckets (parser_upgrade_candidate, bounded_fallback_candidate, unsafe_fallback_defer, product_unsupported_or_inapplicable). That classification lives in test fixtures and developer documentation, not in runtime output.

Users need a direct, stable link from the diagnostic to the evidence documentation so they can answer: "Is this something I should review manually? Will a future DeltaScope upgrade likely support it?"

## Decision

Add two optional fields to `spec.Diagnostic`:

- `guidance_code` — a stable machine-readable string identifying the unsupported boundary category.
- `evidence_ref` — a GitHub documentation URL pointing to the relevant evidence section.

These fields appear only in diagnostics where `classification` is `parser_error` or `unsupported_statement`. All existing fields remain unchanged and backward-compatible.

## Guidance Codes

| Code | Meaning | When it appears |
|---|---|---|
| `parser_upgrade_candidate` | Would become parseable after an upstream parser/library upgrade | `parser_error` cases classified in v0.250.0 as parser_upgrade_candidate |
| `bounded_fallback_candidate` | Could potentially be handled by a bounded pre-parser fallback | `parser_error` cases classified as bounded_fallback_candidate (research only, not implemented) |
| `unsafe_fallback_defer` | Fallback would risk payload leak or false confidence | `parser_error` cases involving unbounded bodies, predicates, or sensitive payloads |
| `product_unsupported_or_inapplicable` | Feature not supported by the target dialect/product | Dialect-specific feature gaps (e.g., TiDB triggers) |
| `unsupported_statement` | Statement recognized but outside audit scope | Statements parsed successfully but not covered by any rule |

v0.260.0 Task 1 RED tests cover `parser_upgrade_candidate` only. Remaining codes will be covered in subsequent tasks.

## Evidence Reference URL

All `evidence_ref` values must point to:

```
https://github.com/Fanduzi/DeltaScope/blob/main/docs/reference/cli.md#parser-upgrade-candidate-evidence-v02500
```

This anchor corresponds to the "Parser Upgrade Candidate Evidence (v0.250.0)" section in `docs/reference/cli.md` which documents the feasibility bucket facts, candidate lists, and non-candidate boundaries.

## User Benefit

1. A user sees `guidance_code=parser_upgrade_candidate` and knows the statement is a candidate for future parser support, not a permanent limitation.
2. A user clicks `evidence_ref` and reads the full classification table, including non-candidate boundaries.
3. Machine consumers (CI gates, dashboards) can group and count diagnostics by `guidance_code` without parsing free-text `reason` or `action_hint`.

## Public Contract

1. `guidance_code` and `evidence_ref` are optional fields. They appear only in `parser_error` and `unsupported_statement` diagnostics. Consumers must handle their absence.
2. Existing fields (`classification`, `reason`, `action_hint`, `audited`, `dialect`) are unchanged and backward-compatible.
3. `guidance_code` values are stable strings from a controlled vocabulary. New codes may be added; existing codes will not be renamed or removed.
4. `evidence_ref` is always a `https://github.com/Fanduzi/DeltaScope/` URL. It never contains local paths, inline documentation, or generic description strings.
5. Neither field contains raw SQL, parser near-text, object names, function bodies, default expressions, or any user payload.

## Privacy / No-Leak Constraints

1. `guidance_code` is a fixed string from the vocabulary above. It never encodes SQL content.
2. `evidence_ref` is a fixed documentation URL. It never embeds statement-specific content.
3. The combined diagnostic output must not allow reconstructing the original SQL, object names, or parser internals.

## Non-Goals

- No parser support added.
- No fallback parser.
- No SQL audit rules added.
- No parser_error count reduction.
- No audit verdict or finding semantic changes.
- No claim of full DDL support or dialect parity.
- No change to parser, extractor, rule, or policy behavior.

## Relationship to v0.250.0

v0.250.0 is the evidence pack — it classified all 29 parser_error cases into feasibility buckets and documented them in developer-facing reference docs. v0.260.0 connects that classification to runtime diagnostic output so users see it directly.
