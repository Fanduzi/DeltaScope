## Context

v0.270.0 added a generated DDL coverage catalog with 400 verified entries:

| Dialect | Total | finding_covered | normalized_silent | unsupported_boundary | parser_error | unclassified |
|---|---:|---:|---:|---:|---:|---:|
| MySQL | 61 | 46 | 0 | 0 | 15 | 0 |
| TiDB | 54 | 45 | 0 | 0 | 9 | 0 |
| PostgreSQL | 285 | 274 | 6 | 0 | 5 | 0 |

The catalog is available as JSON and as English/Chinese reference documentation, but users still need to manually inspect a large JSON file or read long documentation to answer common questions:

- Is this DDL form verified by DeltaScope?
- Is the form finding-covered, normalized-silent, unsupported, or blocked by the parser?
- Which parser-error forms have `guidance_code=parser_upgrade_candidate`?
- How do MySQL, TiDB, and PostgreSQL coverage differ for a family of statements?

The v0.270.0 catalog intentionally does not claim vendor grammar completeness. v0.280.0 must preserve that boundary while making the verified catalog easier to query.

## Decision

v0.280.0 will add a first-class CLI query interface for the generated DDL coverage catalog.

Proposed command:

```bash
deltascope ddl-coverage [flags]
```

The CLI command will read the checked-in catalog data and return filtered catalog entries. It is a coverage lookup tool, not an audit execution path.

Initial filters:

| Flag | Meaning |
|---|---|
| `--dialect mysql|tidb|postgresql` | Limit results to one dialect |
| `--classification finding_covered|normalized_silent|unsupported_boundary|parser_error|unclassified` | Limit results by catalog classification |
| `--guidance-code parser_upgrade_candidate` | Limit results by guidance metadata |
| `--family <text>` | Case-insensitive substring match on catalog family |
| `--form <text>` | Case-insensitive substring match on catalog form |
| `--search <text>` | Case-insensitive substring match across family, form, notes, guidance code, and rule IDs |
| `--format text|json` | Select human-readable or machine-readable output |
| `--limit <n>` | Limit result count; `0` means no explicit limit |

Default output should be concise text with stable columns:

```text
DIALECT     CLASSIFICATION      FAMILY          FORM                         GUIDANCE
mysql       parser_error        view_lifecycle  ALTER VIEW                   parser_upgrade_candidate
postgresql  finding_covered     table_alter     ALTER TABLE VALIDATE ...     -
```

JSON output should preserve the catalog entry shape and include a summary object:

```json
{
  "version": "v0.280.0",
  "summary": {
    "total": 2,
    "returned": 2,
    "filters": {
      "dialect": "mysql",
      "classification": "parser_error"
    }
  },
  "entries": []
}
```

## Rationale

A CLI query is the smallest useful public surface because DeltaScope already has a CLI and release gates for CLI behavior. It gives users a direct local answer without requiring SDK integration or running an audit against representative SQL.

This choice avoids expanding the runtime audit output contract. SDK, HTTP, and MCP parity are valuable, but they are intentionally deferred until the CLI query semantics are proven stable.

The command must consume generated catalog data rather than hand-maintained lists. The v0.270.0 drift gate remains the source of truth for catalog correctness; v0.280.0 adds query behavior on top.

## Public Contract

After v0.280.0, users can rely on:

- `deltascope ddl-coverage` existing as a CLI catalog lookup command.
- Text output being stable enough for human use, not guaranteed as a parsing contract.
- JSON output being the machine-readable contract for automation.
- Filter values using the v0.270.0 catalog vocabulary:
  - `finding_covered`
  - `normalized_silent`
  - `unsupported_boundary`
  - `parser_error`
  - `unclassified`
- Query results reflecting verified DeltaScope catalog entries, not vendor grammar completeness.
- Unknown filter enum values failing with a clear validation error.
- Empty result sets returning success with `entries: []`, not a runtime audit failure.

## Privacy / No-Leak Contract

The query command must not introduce new user payload exposure.

The command reads catalog entries only. It must not parse arbitrary SQL, execute SQL, or call the audit service. Free-text filter values may appear in local CLI input, but they must not be embedded into generated catalog entries or persisted.

Output must not include:

- Parser `near ...` text
- Raw parser errors
- Routine/function bodies
- Default expressions
- User SQL payloads
- Object names beyond generic fixture labels already present in catalog forms or notes

## Deferred / Out Of Scope

v0.280.0 will not:

- Add parser support
- Add fallback parser behavior
- Add SQL audit rules
- Change audit verdicts or finding semantics
- Change SDK, HTTP, or MCP audit response shapes
- Claim full DDL support
- Claim dialect parity
- Claim MySQL/TiDB/PostgreSQL vendor grammar completeness
- Treat `testdata/sql-corpus` as an official SQL grammar suite
- Add an interactive TUI or web UI
- Accept raw SQL and infer its catalog entry through parsing
- Publish a remote searchable service

## Implementation Plan

### Task 1: Design Contract

- Create this decision record.
- Define the CLI command, filters, JSON shape, privacy constraints, non-goals, and verification plan.
- No production code changes.

### Task 2: Catalog Query Core

- Add a small catalog query package or internal helper that loads the embedded/generated catalog and applies filters.
- Keep filtering deterministic and case-insensitive for text fields.
- Validate enum filters before executing queries.
- Add unit tests for:
  - dialect filtering
  - classification filtering
  - guidance-code filtering
  - search/family/form filtering
  - combined filters
  - empty result behavior
  - invalid enum errors

### Task 3: CLI Surface

- Add `deltascope ddl-coverage` command wiring.

  - empty result sets

## Consequences

Future catalog fields become more visible to users because the CLI can surface them directly. Any new catalog field should therefore be evaluated for:

- JSON output stability
- text output usefulness
- privacy/no-leak risk
- release consistency validation
- EN/ZH documentation parity

If future work adds SDK, HTTP, or MCP catalog query surfaces, it should either reuse the same query core or document why a different contract is required.
