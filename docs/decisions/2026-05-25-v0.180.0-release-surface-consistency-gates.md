# Decision: v0.180.0 Release Surface Consistency Gates

Date: 2026-05-25
Status: Proposed
Related milestone/version: v0.180.0
Related tests:
- `scripts/test_verify_release_consistency.py` (planned)
Related docs:

## Context

Release surfaces have repeatedly required manual synchronization across landing page, release notes EN/ZH, changelog, roadmap, rules reference, and capability matrix. This manual process has caused recurring errors:

- **Landing recent-release cards drifting to stale versions** such as `v0.110.0 / v0.100.0 / v0.90.0` instead of the correct previous three releases.
- **Release notes, changelog, roadmap, and landing page using inconsistent residual census numbers** — for example, `finding_covered=64` instead of the correct `66/60/2/0/4/0` during v0.170.0 preparation.
- **EN/ZH release surfaces drifting on the same key numbers**, where one language was corrected and the other was not.
- **Release copy accidentally overclaiming** full PostgreSQL `ALTER TABLE` support or PostgreSQL 18 parser support.

These are release-engineering defects, not product defects. They erode user trust and require expensive last-minute fixes during release preparation.

The existing `make release-version-surface-gates` (powered by `scripts/verify_release_version_surfaces.sh`) validates version string presence and file existence, but does not validate release-domain semantic facts.

## Decision

Add a release surface consistency gate that enforces high-value invariants across all release surfaces:

1. **Keep the existing shell gate** (`scripts/verify_release_version_surfaces.sh`) unchanged.
2. **Add a Python consistency checker** (`scripts/verify_release_consistency.py`) that validates semantic release facts.
3. **Wire both into `make release-version-surface-gates`** so the new checker runs alongside the existing shell checks.
4. **Cover the checker with unit tests** (`scripts/test_verify_release_consistency.py`) that prove negative cases catch known regressions.

Why Python: the repository already uses Python for scripts/tests; string and regex checks across many Markdown/HTML files are easier to keep readable in Python than shell; the script can produce structured, actionable failure messages.

## Gate Categories

### 1. Release Sequence

- `docs/releases/README.md` first version equals `VERSION`.
- Landing current release equals `VERSION`.
- Landing recent cards equal releases 2-4 from `docs/releases/README.md`.
- Landing recent card count is exactly 3.

For v0.170.0: current `v0.170.0`, recent `v0.160.0`, `v0.150.0`, `v0.140.0`.

### 2. Residual Census Arithmetic

For releases with PostgreSQL ALTER TABLE residual census claims:

- All release surfaces must agree on the configured census tuple.
- Arithmetic must pass: `finding_covered + normalized_silent + unsupported_boundary + parser_error + unclassified == total`.
- EN/ZH release notes, changelog, roadmap, and landing page must contain the correct values.
- Known wrong claims are rejected: `finding_covered=64`, `64 of 66`, `60→64`, `60 to 64`, `unsupported_boundary 0→0` for v0.170.0.

For v0.170.0: `66/60/2/0/4/0`.

### 3. SQL Corpus Metrics

For releases with SQL corpus claims:

- EN/ZH release notes must contain the configured corpus facts.
- Accept compact forms: `535/535`, `100.0`, `243 YAML`.

For v0.170.0: `535/535`, `100.0%`, `243 YAML`.

### 4. PostgreSQL ALTER TABLE Rule Count

For releases that mention PostgreSQL ALTER TABLE rule count:

- Rules reference EN/ZH must contain the configured count.
- Capability matrix EN/ZH must contain the configured count.
- Release notes EN/ZH must contain the configured count.

For v0.170.0: 32 rules.

### 5. Required Rule IDs

For release facts with `required_rule_ids`, all listed rule IDs must appear in:

- EN/ZH release notes.
- EN/ZH rules reference.
- EN/ZH capability matrix.

For v0.170.0: `ddl.pg.alter.set_expression.notice`, `ddl.pg.alter.add_identity.notice`, `ddl.pg.alter.add_exclusion_constraint.notice`, `ddl.pg.alter.move_all_tablespace.notice`.

### 6. No-Overclaim

Reject positive overclaims in release surfaces:

- `full PostgreSQL ALTER TABLE support`
- `complete PostgreSQL ALTER TABLE support`
- `PostgreSQL 18 parser support`
- `runtime validation`
- `live validation`
- `rewrite duration estimate`

Allow lines containing negative/non-goal markers: `Not`, `No`, `non-goal`, `deferred`, `不`, `不会`, `未`, `非目标`, `不支持`.

### 7. No-Leak Wording

Forbidden payload terms (`raw_sql`, `first_name`, `last_name`, `||`, `sequence_options`, `exclusions`, `operator_class`, `predicate`, `where_clause`, `room_id`, `during`, `&&`) may appear only in lines with no-leak/non-goal markers (`No-leak`, `not emitted`, `不泄漏`, `非目标`, `不会输出`).

### 8. EN/ZH Numeric Parity

EN and ZH release notes must both contain the same version, rule count, residual census values, and corpus values. EN/ZH rules references and capability matrices must both contain the same rule count and required rule IDs.

## Config Model

The checker uses an explicit in-script release facts map keyed by version:

```python
RELEASE_FACTS = {
    "v0.170.0": {
        "pg_alter_table_rule_count": 32,
        "residual_census": {
            "total": 66, "finding_covered": 60, "normalized_silent": 2,
            "unsupported_boundary": 0, "parser_error": 4, "unclassified": 0,
        },
        "sql_corpus": {
            "supported_rule_dialect_targets": 535,
            "covered_rule_dialect_targets": 535,
            "coverage_percent": "100.0",
            "expected_yaml_files_total": 243,
        },
        "required_rule_ids": [
            "ddl.pg.alter.set_expression.notice",
            "ddl.pg.alter.add_identity.notice",
            "ddl.pg.alter.add_exclusion_constraint.notice",
            "ddl.pg.alter.move_all_tablespace.notice",
        ],
    },
}
```

For a new release, the facts entry must be added or updated if release notes mention milestone-specific census/rule data.

## Non-Goals

- No new SQL parser coverage, rules, or public API features.
- No modification to release notes content strategy — the gate only validates, it does not generate.
- No external dependencies; Python standard library only.
- No changes to production Go logic.

## Acceptance Criteria

- `VERSION=v0.170.0 make release-version-surface-gates` passes (runs both shell and Python gates).
- `VERSION=v0.170.0 make release-contract-gates` passes.
- Unit tests prove stale landing recent cards are rejected.
- Unit tests prove `finding_covered=64` is rejected.
- Unit tests prove positive overclaim (`Full PostgreSQL ALTER TABLE support`) is rejected while negative wording (`Not full PostgreSQL ALTER TABLE support`) is allowed.
- No production Go logic changes.
- No external dependencies added.

## Failure Output Contract

Failures are actionable:

```text
[release-consistency][FAIL] docs/releases/release-notes-v0.170.0.md contains stale census claim "64 of 66"; expected finding_covered=60 and normalized_silent=2
```

Success prints a short summary:

```text
release-consistency: VERSION=v0.170.0
release-consistency: recent releases v0.160.0, v0.150.0, v0.140.0
release-consistency: residual census 66/60/2/0/4/0
release-consistency: sql corpus 535/535, 100.0%, 243 YAML
release-consistency: pg alter table rule count 32
release-consistency: PASS
```

## Why Decision Record Is Required

This milestone changes the release workflow contract by adding release-blocking semantic gates and defining durable release-surface invariants. It is a public release contract change, not just internal tooling.

## Consequences

- Release preparation gains automated consistency checks that catch the exact classes of errors seen in recent milestones.
- Adding a new release requires updating `RELEASE_FACTS` if release notes mention milestone-specific census/rule data.
- The gate does not replace human review; it automates the most error-prone numerical and wording invariants.
- Future refinement may externalize facts to a committed YAML/JSON file, but a Python dict suffices for v0.180.0.
