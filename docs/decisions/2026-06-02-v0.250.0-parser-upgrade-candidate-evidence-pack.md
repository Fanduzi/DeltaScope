## Context

v0.230.0 shipped the unsupported diagnostics evidence pack. v0.242.0 completed release recovery CI hardening. The codebase now has stable census baselines, a feasibility classification system for all 29 remaining `parser_error` cases, and corpus coverage at 100%.

This milestone freezes the parser-upgrade candidate evidence contract: which `parser_error` forms would benefit from parser/library upgrades, and which non-candidate boundaries must not be crossed.

## Decision

Identify and document all parser-upgrade candidates across MySQL, TiDB, and PostgreSQL. Record current census facts, feasibility bucket counts, and explicit non-candidate boundaries. No parser behavior changes, no new rules, no fallback extraction, no output shape changes.

## Non-Candidate Boundaries

The following buckets are explicitly non-candidate for this milestone and carry explicit constraints:

- **`bounded_fallback_candidate`** (4 cases): Research items only. A bounded pre-parser fallback could safely extract object identity without payload leak, but this milestone does not implement any fallback. Any future fallback design must prove no payload exposure and no false-confidence risk.

- **`product_unsupported_or_inapplicable`** (6 cases): Product or dialect boundaries. TiDB does not support triggers, user-defined SQL functions, or events. These forms should not be pursued to reduce parser_error counts. Parsing unsupported features creates false confidence.

- **`unsafe_fallback_defer`** (9 cases): Fallback would require parsing unbounded bodies, predicates, option payloads, or sensitive strings. These carry payload leak, false confidence, or misinference risk. MySQL trigger, event, tablespace, and resource group forms must not be inferred from raw failed parse text. Routine option semantics (SQL SECURITY, COMMENT) require understanding option values, not just token presence.

## Public Contract

1. `parser_error` SQL is not audited. No findings are generated for unparseable SQL.
2. No audit findings are inferred from failed parses.
3. Raw SQL text and parser `near ...` error fragments are not copied into user-facing guidance.
4. `parser_upgrade_candidate` classification means these forms would be candidates for support after a parser/library upgrade — they are not currently supported.
5. Current CLI, HTTP, MCP, and SDK output shapes are unchanged.

## Non-Goals

- No fallback parser.
