## Context

DeltaScope currently depends on:

```text
github.com/pingcap/tidb/pkg/parser v0.0.0-20260319162650-7d7a2372f4ec
```

The target TiDB parser version:

```text
github.com/pingcap/tidb/pkg/parser v0.0.0-20260622124716-26db2d85d6cd
```

adds DML `RETURNING` support to the parser AST and grammar. The target parser
introduces `Returning []*SelectField` on `InsertStmt`, `UpdateStmt`, and
`DeleteStmt`, and attaches a `ReturningClause` to these grammar paths:

- `INSERT ... RETURNING`
- single-table `DELETE FROM ... RETURNING`
- single-table `UPDATE ... RETURNING`
- multi-table `UPDATE ... RETURNING`

The target parser does not attach the clause to `REPLACE ... RETURNING`,
multi-table `DELETE aliaslist FROM ... RETURNING`, or `DELETE ... USING ...
RETURNING`.

DeltaScope uses the TiDB parser for both MySQL and TiDB dialects. That means
the parser upgrade changes dialect behavior in both paths:

- TiDB dialect should accept `RETURNING`; TiDB supports this DML syntax.
- MySQL dialect should not silently treat `RETURNING` as valid MySQL syntax;
  MySQL Server does not support it.

The existing mismatch hint is `dialect.postgresql.syntax.detected.notice`.
Before the parser upgrade, `RETURNING` reached that hint through the parse-error
path. After the parser upgrade, `RETURNING` parses successfully and reaches the
success path. The notice does not disappear, but its meaning becomes wrong:
`RETURNING` is no longer a PostgreSQL-only clue because it is valid TiDB syntax.

The current raw-token heuristic also cannot distinguish a real `RETURNING`
clause from an identifier or alias named `returning`. The parser grammar
intentionally still allows `RETURNING` as an alias outside the clause position.
A structural parser fact is therefore required.

## Decision

Upgrade the TiDB parser to
`v0.0.0-20260622124716-26db2d85d6cd` and model DML `RETURNING` as a minimal
parser-neutral fact:

```go
HasReturning bool `json:"has_returning,omitempty"`
```

on `spec.DML`.

Do not project returned column names, expressions, aliases, or raw parser
subtrees. The audit behavior only needs clause presence, and a boolean avoids
unnecessary payload exposure and public-schema commitment.

Split `RETURNING` out of the existing PostgreSQL syntax mismatch heuristic:

- Remove `RETURNING` from `possiblePostgreSQLMismatchPatterns`.
- Preserve the PostgreSQL mismatch notice for genuinely PostgreSQL-specific
  tokens that remain parse errors or successful syntax clues, such as
  `ON CONFLICT`, `::`, `ALTER COLUMN TYPE USING`, and
  `GENERATED AS IDENTITY`.
- Add a new non-configurable global finding for MySQL Server dialect only:
  `dialect.mysql.returning.unsupported.notice`.

The new finding fires when:

```text
statement dialect == mysql && statement.DML.HasReturning == true
```

It does not fire for TiDB dialect. It does not fire for PostgreSQL dialect.
It does not fire from raw regex scanning.

The message must be MySQL-Server-scoped, for example:

```text
MySQL Server does not support DML RETURNING; if this SQL targets TiDB, re-run with --dialect tidb.
```

The exact wording can be refined during implementation, but it must not claim
MariaDB support. DeltaScope does not currently expose a MariaDB dialect.

## Rationale

This is a parser-upgrade correctness boundary, not a formatting polish task.
The target parser fixes a TiDB parser limitation by accepting TiDB-supported
`RETURNING` syntax. Without a DeltaScope-side dialect boundary:

- TiDB audits get a false PostgreSQL mismatch notice for valid TiDB SQL.
- MySQL audits can parse invalid MySQL Server syntax and return a successful
  audit result with an inaccurate PostgreSQL-oriented notice.
- The existing raw-token heuristic can false-match aliases or identifiers named
  `returning`.

A boolean `HasReturning` fact solves the needed distinction with the smallest
stable contract:

- it is parser-derived, not inferred from raw SQL text;
- it avoids returning column names, expressions, and parser fragments;
- it follows the existing `HasWhere`, `HasLimit`, `HasOrderBy`, `HasSubquery`,
  and `HasOnDuplicate` pattern in `spec.DML`;
- it lets the application layer produce a dialect-boundary global finding once,
  so SDK, CLI, HTTP, and MCP remain aligned through the shared `report.Result`.

A configurable DML policy rule is not the first choice. This behavior is a
dialect contract, not a team policy preference: MySQL Server does not support
DML `RETURNING`, while TiDB does. The existing PostgreSQL mismatch hint is also
non-configurable, and this new MySQL `RETURNING` finding should follow that
pattern.

## Public Contract

After the milestone:

- TiDB dialect accepts parser-supported `INSERT`, `UPDATE`, and single-table
  `DELETE` `RETURNING` forms without emitting
  `dialect.postgresql.syntax.detected.notice`.
- MySQL dialect emits `dialect.mysql.returning.unsupported.notice` for parsed
  DML statements whose AST contains a `RETURNING` clause.
- `RETURNING` is no longer treated as a PostgreSQL-only syntax token on the
  MySQL/TiDB parser path.
- `ON CONFLICT`, `::`, `ALTER COLUMN TYPE USING`, and
  `GENERATED AS IDENTITY` keep the existing PostgreSQL mismatch behavior.
- `spec.DML` gains an additive JSON field `has_returning` when true.
- The new global finding uses `level`, not `severity`.
- The finding carries only bounded metadata such as selected dialect,
  suggested dialect, and token name. It does not carry raw SQL, returned column
  names, expressions, parser error fragments, connection strings, credentials,
  or routine bodies.
- SDK, CLI, HTTP, and MCP expose the behavior consistently because they consume
  the same audit result.

The parser's unsupported `RETURNING` forms remain unsupported by this milestone.
Examples include `REPLACE ... RETURNING` and the target parser's unsupported
multi-table `DELETE ... RETURNING` variants.

## Deferred / Out Of Scope

- No MariaDB dialect.
- No claim that MySQL dialect supports MariaDB `RETURNING`.
- No `ReturningColumns`, `ReturningExpressions`, or parser subtree projection.
- No sensitive-column or `RETURNING *` governance rule.
- No configurable policy rule for allowing or forbidding `RETURNING`.
- No parser fallback.
- No inference from raw parse-error SQL.
- No broad parser-error census reduction goal.
- No raw SQL or parser-fragment leak in findings or diagnostics.
- No SDK, HTTP, or MCP bespoke implementation; surface parity comes from shared
  audit output.
- No `severity` field.

## Architecture

The intended ownership is:

- `go.mod` / `go.sum` own the TiDB parser version bump.
- `internal/domain/spec/dml.go` owns the parser-neutral `HasReturning` field.
- `internal/infrastructure/parser/tidb/extractor.go` owns AST projection from
  `len(stmt.Returning) > 0` to `spec.DML.HasReturning`.
- `internal/application/audit/mismatch.go` owns dialect-mismatch finding
  construction and token heuristics.
- `internal/application/audit/service.go` owns adding global mismatch findings
  to shared audit results.
- Public surfaces should remain thin: CLI, SDK, HTTP, and MCP should verify the
  shared result rather than duplicate dialect logic.

If implementation discovers that the new parser changes additional grammar
behavior beyond `RETURNING`, pause and update this decision before widening
scope.

## Consequences

Future parser upgrades must distinguish syntax accepted by TiDB from syntax
specific to PostgreSQL or unsupported by MySQL Server. Raw token scans are
acceptable only when the parser cannot provide a structural fact; when the AST
can distinguish a clause from an identifier, the extractor should project the
bounded fact.

Because `spec.DML.HasReturning` is an additive public JSON field, future work
must preserve its meaning: it means the parsed DML statement has a real
`RETURNING` clause, not merely a token or alias named `returning`.

If DeltaScope later adds a MariaDB dialect or sensitive-returning-column
governance, that work needs a separate decision record. It would widen dialect
support or project additional SQL payload facts beyond this milestone's
bool-only boundary.
