## Context

v0.100.0 intentionally deferred `CREATE TRANSFORM` and `CREATE ACCESS METHOD` because their handler/function names appeared to be identity-carrying payload. At the time, the AST shape was not characterized in detail — the deferral was a conservative safety decision.

The v0.100.0 decision record stated: if a future implementation wants to support these forms, it must first define a safe opaque identity contract that does not emit raw handler/function names.

Task 1 (AST census) was created to verify whether such a contract is technically possible by inspecting the `pg_query_go` AST node fields for both statements.

## Decision

**Support both.** `CREATE TRANSFORM` and `CREATE ACCESS METHOD` can be safely promoted from unsupported boundary to findings using bounded identity without leaking handler/function payloads.

- `CREATE TRANSFORM` uses bounded identity `type@language` (e.g., `jsonb@plpython3u`), matching the existing `DROP TRANSFORM` identity.
- `CREATE ACCESS METHOD` uses bounded identity `amname` (e.g., `heap2`), matching the existing `DROP ACCESS METHOD` identity.
- Implementation handler/function names must not be emitted in normalized facts, finding metadata, public output, release docs examples, or corpus expected YAML.

## Rationale

Task 1 showed both AST node types have identity fields in distinct, stable positions separate from handler/function payload fields.

**CREATE TRANSFORM** (`CreateTransformStmt`):

| Field | Value | Role |
|-------|-------|------|
| `type_name.names` | `[jsonb]` | Object identity |
| `lang` | `"plpython3u"` | Object identity |
| `fromsql.objname` | `[jsonb_to_plpython]` | Payload (excluded) |
| `tosql.objname` | `[plpython_to_jsonb]` | Payload (excluded) |

**CREATE ACCESS METHOD** (`CreateAmStmt`):

| Field | Value | Role |
|-------|-------|------|
| `amname` | `"heap2"` | Object identity |
| `amtype` | `"t"` | Identity (bounded enum) |
| `handler_name` | `[heap_tableam_handler]` | Payload (excluded) |

Because identity and payload are in separate AST fields, the extractor can read only identity fields and discard payload fields entirely. This satisfies the v0.100.0 bounded-identity/no-payload contract.

## Public Contract

### CREATE TRANSFORM normalized form

- Operation: `create_transform`
- Object type: `transform`
- Object name: `<type>@<language>`
- No function names in options, metadata, or messages beyond the type@language identity.

### CREATE ACCESS METHOD normalized form

- Operation: `create_access_method`
- Object type: `access_method`
- Object name: access method name
- Optional bounded `access_method_type` only if implementation proves it stable and useful.
- No handler name in options, metadata, or messages.

### General

- SDK, CLI, HTTP, and MCP share the same audit semantics for these new rules.
- This is still not full PostgreSQL DDL support, not DCL expansion, and not live validation.

## Deferred / Out Of Scope

- Function/handler semantic validation
- Function existence, language existence, access method handler validation
- Function signatures, bodies, definitions, queries, options
- Full PostgreSQL DDL grammar coverage
- DCL/permission expansion
- Live database validation or migration execution

## Verification Evidence

- Task 1 focused AST census tests passed, confirming identity/payload field separation.
- Full PostgreSQL parser test suite passed with no regressions.
- GitNexus reported LOW risk, 3 test-only symbols changed, 0 affected processes.
- Decision record gate should pass after this file is added.
- If Task 3A proceeds, extractor tests, rule tests, corpus fixtures, and public surface tests will provide additional evidence.

## Consequences

- Task 3A may implement support for both CREATE forms using the bounded identity contract defined here.
- If implementation discovers normalization cannot preserve the no-payload contract, revert to explicit unsupported and update this decision record.
- Future PostgreSQL boundary promotions must first prove identity/payload separation via AST characterization before promotion.
