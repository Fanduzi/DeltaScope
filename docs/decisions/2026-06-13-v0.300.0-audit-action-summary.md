## Context

DeltaScope already tells users whether an audit passed or failed and emits detailed findings with:

- `level`: `blocker`, `warning`, or `notice`
- `rule_id`
- message
- suggestion
- structured explanation when rule catalog metadata exists

v0.280.0 made DDL coverage discoverable through `deltascope ddl-coverage`.
v0.290.0 made shipped rules discoverable through:

```bash
deltascope rules list
deltascope rules explain <rule_id>
```

The remaining usability gap is in the primary audit workflow. A real user who runs `deltascope audit` can receive many findings, but the current human report still forces them to read the report statement-by-statement before answering:

- What must be fixed first?
- Which rule is causing most of the failures?
- Are there repeated violations I can fix as one migration cleanup?
- Which `rules explain` command should I run to understand the rule?

This milestone should improve that workflow. It should not return to polishing unsupported DDL surfaces. Parser gaps remain parser gaps; the product value here is making supported audit findings easier to act on.

## Decision

v0.300.0 will add an **action summary** to human-oriented audit output.

The summary is derived from existing audit findings and rule catalog metadata. It groups findings by rule, orders them by practical remediation priority, and gives a direct command users can run to inspect each rule:

```text
## Action Summary

Fix first:

1. [blocker] `dml.where.require` — 2 findings
   Summary: Require DML where require
   Suggestion: add a WHERE clause that narrows the affected rows
   Explain: deltascope rules explain dml.where.require
   Statements: 1, 3

2. [warning] `ddl.index.name.require` — 1 finding
   Summary: Require DDL index name require
   Suggestion: give the index an explicit, policy-compliant name
   Explain: deltascope rules explain ddl.index.name.require
   Statements: 2
```

When an audit has no findings, the renderer should not emit an action summary section.

### Initial Surface

The first public surface is the default CLI markdown output:

```bash
deltascope audit --file ./migration.sql
deltascope audit --format markdown --file ./migration.sql
```

The action summary should also be available to the markdown renderer used by agent and documentation workflows because it is a deterministic rendering of `report.Result`.

### Non-Surfaces

v0.300.0 will not add the action summary to these surfaces:

- audit JSON output
- Go public API types in `pkg/deltascope`
- HTTP audit response JSON
- MCP audit response JSON
- GitHub Actions annotations
- SARIF
- GitLab Code Quality

Those surfaces are machine contracts. They already expose structured findings that consumers can aggregate themselves. Adding a new machine-readable summary should be a separate public-contract decision if there is clear demand.

## Action Summary Contract

### Data Source

The summary is built from:

- `report.Result.Statements[*].Findings`
- `report.Result.GlobalFindings`
- `internal/domain/rule/catalog` entries, when a finding's `rule_id` exists in the shipped catalog

It must not re-run the audit service, parse SQL, evaluate rules, or inspect raw SQL.

### Grouping

Each action item groups findings by `rule_id`.

For each group, derive:

| Field | Source |
|---|---|
| `rule_id` | finding `RuleID` |
| `level` | highest-priority level observed for the group |
| `count` | number of findings with that rule ID |
| `summary` | rule catalog summary when available; otherwise first finding message |
| `suggestion` | rule catalog suggestion when available; otherwise first finding suggestion |
| `statement_indexes` | 1-based indexes of statements containing that rule; omitted for global-only findings |
| `has_global_findings` | true if any grouped finding came from `GlobalFindings` |
| `explain_command` | `deltascope rules explain <rule_id>` |

### Ordering

Action items are sorted deterministically:

1. level priority: `blocker`, then `warning`, then `notice`
2. finding count descending
3. `rule_id` ascending

This makes the report answer "what should I fix first?" without inventing a new severity model.

### Limit

Markdown output should render at most 10 action items by default.

If more groups exist, include a final line:

```text
Showing 10 of 17 rule groups.
```

No CLI flag is planned for v0.300.0. A flag such as `--action-summary-limit` can be added later if users need it. The default cap keeps terminal reports readable without adding configuration surface too early.

### Privacy / No-Leak Contract

The action summary must not include:

- raw SQL
- normalized SQL
- parser `near ...` text
- database object names derived only from user SQL
- metadata values from a live database
- default expressions or function bodies
- raw finding metadata maps

The summary may include:

- rule IDs
- rule levels
- counts
- static rule catalog summaries
- static rule catalog suggestions
- 1-based statement indexes
- the `deltascope rules explain <rule_id>` command

If a rule is not present in the catalog, fallback text must be limited to the existing finding message and suggestion already emitted by the audit result. Do not add new payload extraction for the summary.

## Rationale

This milestone improves the main user workflow. It uses the discovery foundation shipped in v0.290.0 and brings it back into real audit reports.

The action summary should be derived, not persisted in `report.Result`, for the first release. That keeps SDK/HTTP/MCP JSON unchanged and avoids committing to a new machine-readable schema before there is evidence consumers need it.

The summary should use `level`, not `severity`. DeltaScope's existing public model is `blocker`, `warning`, and `notice`. Adding `severity` now would create a duplicate concept and imply a larger risk taxonomy than the product has.

The initial implementation should be markdown-only because markdown is the default human surface. CI formats and API formats need stability more than convenience. They can be considered after the derived model proves useful.

## Public Contract

After v0.300.0, users can rely on:

- Default markdown audit output including an `Action Summary` section when findings exist.
- The section grouping findings by `rule_id`.
- The section sorting groups by `blocker`, `warning`, `notice`, then count descending, then rule ID ascending.
- Each item including a `deltascope rules explain <rule_id>` command.
- Clean audits omitting the action summary section.
- Audit JSON output remaining unchanged.
- Finding JSON shape remaining unchanged.
- `level` remaining the public priority field; no `severity` field is introduced.

Text layout is a human-readable contract, not a strict parsing target. Automation should continue to use `--format json` and aggregate findings itself.

## Deferred / Out Of Scope

v0.300.0 will not:

- Add parser support.
- Add new SQL audit rules.
- Change existing rule behavior.
- Change default rule levels.
- Add or rename finding fields.
- Add a `severity` field.
- Change SDK, HTTP, or MCP audit response shapes.
- Add a new `report` subcommand.
- Add an interactive TUI or web UI.
- Rank by inferred business impact beyond existing `level`.
- Use regex over raw SQL to infer unsupported behavior.
- Claim complete migration remediation.

### Task 2: Action Summary Core

Add a small derived summary package or file under `internal/domain/report`.

Proposed files:

- `internal/domain/report/action_summary.go`
- `internal/domain/report/action_summary_test.go`
- update `internal/domain/report/README.md`

Proposed API:

```go
type ActionSummaryOptions struct {
    Limit int
}

type ActionSummary struct {
    Items      []ActionItem
    TotalItems int
}

type ActionItem struct {
    RuleID            string
    Level             rule.Level
    Count             int
    Summary           string
    Suggestion        string
    StatementIndexes  []int
    HasGlobalFindings bool
    ExplainCommand    string
}

func BuildActionSummary(result Result, entries []catalog.Entry, options ActionSummaryOptions) ActionSummary
```

Core requirements:

- Group statement findings and global findings by rule ID.
- Use 1-based statement indexes.
- Deduplicate statement indexes within a rule group.
- Use catalog summary/suggestion when available.
- Fall back to finding message/suggestion when catalog metadata is unavailable.
- Sort by level priority, count descending, rule ID ascending.
- `Limit <= 0` means no limit for the core function.
- Return an empty `Items` slice, not nil, when there are no findings.
- Do not mutate `report.Result` or catalog entries.

Focused tests:

- empty result returns empty non-nil items
- blocker groups sort before warning and notice
- count descending breaks ties within the same level
- rule ID ascending breaks remaining ties
- catalog summary/suggestion preferred
- finding fallback works for unknown rule ID
- statement indexes are 1-based and deduplicated
- global findings set `HasGlobalFindings`
- limit truncates but preserves `TotalItems`
- output contains no `severity` field when JSON-marshaled in tests

Before editing symbols, run GitNexus impact on any existing symbol that will be modified. New symbols do not need pre-edit impact, but changes to `Result`, `Summary`, or existing report functions would require impact analysis.

## Consequences

The default markdown report becomes more opinionated. Future markdown changes must preserve the action summary's purpose: help humans decide what to fix first without turning markdown into a second machine contract.

If users later need automation around action summaries, that should be designed as an explicit JSON/API contract instead of scraping markdown.

The rule catalog becomes part of the audit report UX even though it remains read-only metadata. Future rule additions should keep catalog summary and suggestion text useful enough to appear in top-level audit summaries.
