# v0.270.0 DDL Coverage Catalog

Date: 2026-06-05
Status: Accepted
Related milestone/version: v0.270.0

## Context

DeltaScope's DDL coverage facts are scattered across multiple locations:

- MySQL/TiDB DDL census test cases in `internal/application/audit/cross_dialect_ddl_coverage_census_test.go`
- PostgreSQL DDL census cases in `internal/application/audit/postgresql_ddl_coverage_census_postgresql_tag_test.go`
- PostgreSQL ALTER TABLE residual cases in `internal/application/audit/postgresql_alter_table_residual_census_postgresql_tag_test.go`
- SQL corpus fixtures in `testdata/sql-corpus/`
- Release notes in `docs/releases/`
- Prior decision records in `docs/decisions/`
- Parser-error feasibility reports from v0.210.0 and v0.250.0

The `testdata/sql-corpus` achieves 100% coverage against supported rule x dialect targets, but it is a test corpus, not an official DDL grammar suite. DDL form coverage facts primarily come from census tests, not corpus fixtures.

Users, integrators, and maintainers cannot answer "does DeltaScope audit this DDL form?" from a single location.

## User Problem

A user who wants to know whether a specific DDL form (e.g., MySQL `ALTER VIEW`, PostgreSQL `ALTER TABLE ... VALIDATE CONSTRAINT`) is audited, silent, unsupported, or a parser error must read test code, release notes, and decision records. There is no consolidated reference.

## Decision

v0.270.0 will create a DDL coverage catalog consisting of:

1. A machine-readable JSON artifact at `docs/reference/ddl-coverage-catalog.json`
2. English user documentation at `docs/reference/ddl-coverage.md`
3. Chinese user documentation at `docs/reference/ddl-coverage.zh-CN.md`
4. A drift gate `make ddl-coverage-catalog-test` preventing catalog/census divergence

The catalog will be generated from shared census data, not hand-maintained.

## Public Contract

### Catalog JSON

Path: `docs/reference/ddl-coverage-catalog.json`

Top-level structure:

```json
{
  "version": "v0.270.0",
  "generated_from": [
    "internal/application/audit/cross_dialect_ddl_coverage_census_test.go",
    "internal/application/audit/postgresql_ddl_coverage_census_postgresql_tag_test.go",
    "internal/application/audit/postgresql_alter_table_residual_census_postgresql_tag_test.go"
  ],
  "summary": { "mysql": {}, "tidb": {}, "postgresql": {} },
  "entries": []
}
```

Prefer omitting timestamps to keep diffs deterministic.

### Catalog Entry Fields

Each entry in `entries` must include:

| Field | Required | Description |
|---|---|---|
| `dialect` | Yes | One of `mysql`, `tidb`, `postgresql` |
| `family` | Yes | Logical grouping (e.g., `table_lifecycle`, `view_lifecycle`) |
| `form` | Yes | Stable form label (e.g., `ALTER VIEW`), not raw user SQL |
| `classification` | Yes | One of the classification vocabulary values below |
| `guidance_code` | No | v0.260.0 guidance code (e.g., `parser_upgrade_candidate`) |
| `evidence_ref` | No | Public documentation URL for the evidence |
| `finding_rule_ids` | Yes | Array of rule IDs that fire for this form; may be empty |
| `notes` | Yes | Brief human-readable note |

### User Documentation Paths

- `docs/reference/ddl-coverage.md` (English)
- `docs/reference/ddl-coverage.zh-CN.md` (Chinese)

## Classification Vocabulary

| Classification | Meaning |
|---|---|
| `finding_covered` | The form parses/extracts and can produce one or more audit findings under current rules |
| `normalized_silent` | The form parses/extracts, but current default policy produces no finding; a known silent path, not an untracked gap |
| `unsupported_boundary` | DeltaScope recognizes a product boundary and returns unsupported diagnostics instead of pretending to audit |
| `parser_error` | The selected dialect parser cannot parse the form, so DeltaScope does not audit it |
| `unclassified` | Reserved for catalog generation failures; release gate should require zero |

## Source of Truth Strategy

Preferred approach:

1. Extract existing census case definitions into reusable package-level catalog data structures
2. Keep tests and generator using the same source
3. Generate docs/reference JSON and markdown from that shared source

This avoids a new drift problem where docs claim one thing and census tests assert another.

Acceptable fallback:

- Keep existing tests unchanged
- Add a small generator that imports application test data or reads a structured fixture
- Add a drift gate proving generated docs match the current census output

Avoid:

- Hand-writing `docs/reference/ddl-coverage-catalog.json` with no generator
- Copying 400+ entries into docs and manually maintaining them
- Scraping `go test -v` log output as the primary source

## No-Overclaim / User Wording

The catalog must describe itself as "verified representative DeltaScope coverage" and must not claim to cover "all MySQL/TiDB/PostgreSQL DDL." User-facing docs must explain:

- This tells you what DeltaScope has verified, not what the database vendor grammar allows
- The catalog is generated from DeltaScope's own census test data
- Absence from the catalog means DeltaScope has not verified the form, not that the form is unsupported in the database

## Privacy / No-Leak Constraints

The catalog must not include:

- Raw sensitive payloads or user payload values
- Parser `near ...` text
- Function bodies, routine bodies, or default expressions
- Object names beyond generic fixture labels already present in census names
- Any content that allows reconstructing original SQL
