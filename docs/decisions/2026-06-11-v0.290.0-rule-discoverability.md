## Context

DeltaScope already emits rule findings with a configured `level`:

- `blocker`
- `warning`
- `notice`

The public finding field is `level`, not `severity`. Rule configuration also uses `level` in `configs/deltascope.example.yaml`.

However, users who want to understand available rules must currently inspect reference docs, YAML config, release notes, or source code. Common user questions are not directly answerable from the CLI:

- Which rules exist for this dialect?
- Which rules are `blocker`, `warning`, or `notice` by default?
- What does this `rule_id` mean?
- Why did a finding fire?
- What risk does the rule represent?
- What action should I take?
- Which config key controls the rule?

v0.280.0 made DDL coverage discoverable through `deltascope ddl-coverage`. v0.290.0 will apply the same product direction to rules: make existing rule behavior easier to discover and explain without changing audit semantics.

## Decision

v0.290.0 will add a read-only rule discovery surface.

Proposed CLI commands:

```bash
deltascope rules list [flags]
deltascope rules explain <rule_id> [flags]
```

The commands expose existing rule metadata and default policy information. They do not evaluate SQL, parse SQL, run audits, or change findings.

### `rules list`

Lists rules with filters.

Initial flags:

| Flag | Meaning |
|---|---|
| `--dialect mysql|tidb|postgresql|common` | Filter by rule dialect scope |
| `--level blocker|warning|notice` | Filter by configured/default level |
| `--kind ddl|dml` | Filter by SQL statement kind |
| `--category <text>` | Case-insensitive category/family filter |
| `--search <text>` | Case-insensitive search across rule id, summary, risk, suggestion, config key, and tags |
| `--format text|json` | Select human-readable or machine-readable output |
| `--limit <n>` | Limit result count; `0` means no explicit limit |

Default text output should be concise:

```text
RULE ID                                      LEVEL    DIALECT      KIND  CATEGORY
ddl.pg.alter.drop_column.forbid             warning  postgresql  ddl   alter_table
ddl.table.primary_key.require               blocker  common      ddl   table
```

JSON output should include a stable wrapper:

```json
{
  "version": "v0.290.0",
  "summary": {
    "total": 2,
    "returned": 2,
    "filters": {
      "dialect": "postgresql",
      "level": "warning"
    }
  },
  "rules": []
}
```

### `rules explain`

Explains one rule by exact `rule_id`.

Default text output should include:

- Rule ID
- Level
- Dialect scope
- Kind
- Category
- Summary
- Why
- Risk
- Suggestion / action
- Config key
- Whether the rule is enabled by default

JSON output should return one rule object.

Missing rule IDs should return a clear non-zero error.

## Rule Metadata Contract

Rule discovery needs a normalized rule catalog entry.

Proposed fields:

| Field | Required | Description |
|---|---|---|
| `rule_id` | Yes | Stable rule identifier used in findings and config |
| `config_key` | Yes | Config key controlling the rule; normally same as rule ID |
| `level` | Yes | One of `blocker`, `warning`, `notice` |
| `enabled` | Yes | Default enabled state from policy/config |
| `kind` | Yes | `ddl` or `dml` |
| `dialects` | Yes | Dialect scopes: `mysql`, `tidb`, `postgresql`, or `common` |
| `category` | Yes | Stable grouping such as `alter_table`, `index`, `table`, `dml_safety` |
| `summary` | Yes | One-line human-readable description |
| `why` | No | Why the rule exists |
| `risk` | No | What can go wrong |
| `suggestion` | No | Recommended action |
| `tags` | Yes | Searchable tags; may be empty |
| `source` | Yes | Where the metadata came from, e.g. `policy`, `rule`, `docs` |

The catalog should prefer metadata already present in rule explanations and default policy. If a rule lacks rich explanation text, v0.290.0 may ship a minimal entry with `summary` and defer full copy enrichment.

## Rationale

This is more useful to real users than further polishing unsupported DDL behavior. Users need to understand findings they already receive and how to configure rules.

The feature should not rename `level` to `severity`. `level` is already part of the finding JSON and config contract. Introducing a parallel `severity` term would create confusion and migration risk. Documentation may explain that `level` is DeltaScope's severity-like field.

The commands should read rule metadata, not run the audit pipeline. This keeps the feature safe, deterministic, and independent from SQL parser support.

## Public Contract

After v0.290.0, users can rely on:

- `deltascope rules list` existing as a CLI rule catalog lookup command.
- `deltascope rules explain <rule_id>` existing as a CLI rule explanation command.
- JSON output being the automation contract.
- Text output being stable enough for humans, not a strict parsing contract.
- `level` values remaining `blocker`, `warning`, and `notice`.
- Unknown enum filters returning clear validation errors.
- Unknown rule IDs returning non-zero with a clear error.
- Empty `rules list` results returning success with `rules: []`.

## Privacy / No-Leak Contract

Rule discovery commands must not:

- Accept or parse raw SQL
- Execute SQL
- Run the audit service
- Include user SQL payloads
- Include parser `near ...` text
- Include object names from user input
- Include function bodies, default expressions, or migration payloads

The commands output rule metadata only.

## Deferred / Out Of Scope

v0.290.0 will not:

- Add new audit rules
- Change existing rule evaluation semantics
- Change finding JSON shape
- Rename `level` to `severity`
- Add a new `severity` field
- Change default rule levels
- Change config file shape
- Add SDK, HTTP, or MCP rule discovery surfaces
- Add interactive TUI or web UI
- Claim rule completeness against every possible database risk
- Change parser support or unsupported DDL handling

SDK/HTTP/MCP parity may be considered later if CLI usage proves the contract useful.

## Consequences

Rule metadata becomes a user-facing contract. Future rule additions should include enough metadata to make `rules list` and `rules explain` useful.

The existing `level` vocabulary becomes more visible. Any future level changes must be treated as a public contract change.

If richer explanations are added over time, they should improve the rule catalog without changing audit behavior.
