# 可解释审计结果任务提示词

> 用于 `Explainable Audit Results` 里程碑的逐任务实施与评审。
> 每个提示词都假设工作发生在 `/Users/fan/GolangProjects/DeltaScope` 中。

## 全局规则

- 保持现有离线优先审计引擎不变。
- 保持 verdict 语义、finding 数量与 `--fail-on` 行为不变。
- 将解释增强视为一项共享的求值后能力，而不是 CLI 专属格式化技巧。
- 让规则执行与解释元数据保持为两个通过 `rule_id` 关联的独立关注点。
- 对每个非平凡模型、增强、传输或 UX 变更使用 TDD。
- 将 `three-level-doc` 视为硬门槛。
- 每个任务都返回变更文件、运行测试、状态与 commit hash。

## 里程碑重点

- 附着在审计 finding 上的稳定解释结构
- 作为解释事实来源的规则目录
- 求值后的 finding 增强
- CLI 中面向人的解释输出
- HTTP 与 `pkg/deltascope` 中的结构化解释输出
- 诚实的元数据感知说明
- 教用户如何阅读增强 finding 的文档

## 任务意图

### 任务 1：规划工件

- 保存该里程碑的设计、实施计划与任务提示词。
- 保持命名与范围对齐 `Explainable Audit Results`。

### 任务 2：共享解释模型

- 为共享结果类型增加稳定解释结构。
- 不要改变 verdict 语义，也不要让解释数据变成正确性的强制条件。

### 任务 3：规则目录扩展

- 扩展已发布规则目录，使其不仅能列规则，还能解释 finding。
- 优先保持元数据简洁、稳定，而不是写成长篇描述。

### 任务 4：解释增强

- 在求值之后，利用目录元数据与当前审计上下文增强 finding。
- 如果解释元数据缺失，必须优雅降级。

### 任务 5：公共包暴露

- 通过 `pkg/deltascope` 暴露解释数据，让下游调用方可直接使用。
- 保持公共 API 一致且有文档记录。

### 任务 6：CLI 输出

- 在不破坏紧凑默认输出的前提下，增加面向解释的详细 CLI 视图。
- 确保 JSON 输出清晰暴露结构化解释数据。

### 任务 7：HTTP 输出

- 从 `POST /v1/audit` 返回结构化解释字段。
- 除新增解释字段外，保持现有响应契约稳定。

### 任务 8：元数据透明性

- 让解释输出诚实说明元数据是增强了结果还是限制了结果。
- 不要暗示引擎并没有实际掌握的置信度。

### 任务 9：文档

- 更新 reference 与 recipe 文档，教用户如何阅读增强 finding。
- 保持 CLI、HTTP 与库示例对齐。

### 任务 10：收口

- 重新运行完整验证。
- 确认解释增强不会改变现有 verdict 结果。
- 更新 handoff、autonomous progress 与 decisions。
- 让该里程碑处于可发布状态。
