# DeltaScope 审计能力补完设计

## 目标

将 DeltaScope 推进到“审计能力完整”的里程碑：保持当前离线优先流程，引入可选的元数据增强，并通过正式的能力矩阵作为验收事实来源，补齐剩余重要的审计缺口。

## 成功标准

- DeltaScope 默认仍可完全离线运行。
- 当提供连接信息时，DeltaScope 可以使用实例事实与对象元数据增强审计判断。
- 剩余重要的 DDL 与 DML 审计缺口必须满足以下之一：
  - 已实现，
  - 已被更强的等价能力替代，
  - 或明确延期并记录原因。
- 仓库中包含一份能力矩阵，将每项重要审计能力标记为已覆盖、已替代、已延期或有意不纳入范围。
- 公共文档升级到与产品成熟度相匹配的水平：
  - `README.md`
  - `README_ZH.md`
  - `CHANGELOG.md`
  - `SECURITY.md`

## 为什么要有这个里程碑

项目已经具备稳定的库 API、CLI、HTTP 服务、更完整的 `CREATE TABLE` 覆盖，以及不断增强的 `ALTER TABLE` 语义模型。当前剩余的差距不在基础设施，而在于审计完整性。这个里程碑的目标，是把项目从“很多方面都很强”提升到“能够依据明确定义的能力矩阵被证明是完整的”。

## 推荐方向

使用一套审计引擎并附加可选的元数据提供者，而不是分别构建离线与在线两条代码路径。

### 核心原则

在线增强只增加事实，不引入第二套工作流。

这意味着：

- 没有元数据访问时，引擎只基于 SQL 与策略求值
- 有元数据访问时，同一引擎会基于 SQL、策略、实例事实和表快照求值

## 元数据模型

### 实例事实

这些是会影响兼容性与风险判断的服务端级事实：

- `version`
- `character_set_database`
- `innodb_large_prefix`
- `innodb_default_row_format`
- `innodb_adaptive_hash_index`

### 对象事实

这些是用于存在性与兼容性规则的表级事实：

- 目标表是否存在
- 当前表快照
- 当前列定义
- 当前索引定义
- 当前主键定义

## 提议的结构

- `internal/domain/spec`
  - 扩展元数据感知审计事实与快照类型
- `internal/domain/rule`
  - 继续让规则消费规范化事实，而不是原始数据库客户端
- `internal/application/audit`
  - 编排纯离线与可选元数据增强执行
- `internal/infrastructure/...`
  - 为 MySQL 和 TiDB 增加元数据提供者实现

## 能力矩阵

能力矩阵是里程碑工件，不是一个“可有可无”的附录。

它应当：

- 在一份稳定文档中列出每项重要审计能力
- 将每一行标记为：
  - 已覆盖
  - 已替代/增强
  - 已延期
  - 有意不纳入范围
- 指向实现该能力的规则 ID 或模块

这份矩阵将成为该里程碑的验收清单。

## 范围

### 范围内

- 能力矩阵
- 可选元数据提供者抽象
- 实例事实加载
- 目标表快照加载
- 对象存在性检查
- 更深入的 alter 兼容性检查
- 剩余重要 DDL/DML 审计缺口
- 文档与发布面升级

### 范围外

- MCP server
- 认证与 bearer-token 中间件
- explain-plan 驱动的风险分析
- 全库巡检/抓取
- UI 工作

## 预期结果

完成这个里程碑后，DeltaScope 应该能够对“它可以审计什么”给出一套统一、清晰的答案，并且这个答案应由代码、测试和能力矩阵共同支撑，而不是靠直觉。
