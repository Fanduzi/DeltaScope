# 可解释审计结果设计

## 目标

让 DeltaScope 在 CLI、HTTP 和 `pkg/deltascope` 三个界面上的审计结果都具备自解释能力，使用户与 AI agent 能立即理解某条规则为何触发、代表什么风险，以及最直接的修复路径是什么。

## 背景

DeltaScope 已经具备强大的规则引擎、稳定的 verdict 语义、规则目录基础，以及覆盖 CLI、HTTP 与库使用场景的产品界面。当前剩余差距不在基础审计覆盖，而在结果可用性。

现在的 finding 已足够用于阻断或告警，但调用方仍需额外回答很多追问，例如：

- 为什么这条规则会被当前 SQL 触发？
- DeltaScope 指向的实际风险是什么？
- 让 SQL 变得可接受的最短路径是什么？
- 哪个配置项控制了这个行为？
- 这条规则是否依赖元数据感知上下文？

这个缺口同时影响人类与机器：

- 开发者仍需要从输出跳到文档或源码
- CI 日志的可执行性还不够强
- AI agent 能拿到 verdict 与 message，但缺少足够结构化的指引，无法给出精确下一步建议

## 非目标

本里程碑不包括：

- 新增大量 DDL 或 DML 规则
- 改变 verdict 语义或 `--fail-on` 行为
- 增加 UI 工作
- 增加 LLM 生成解释
- 增加 explain-plan 驱动的 SQL 分析
- 引入团队级策略继承或 preset

## 考虑过的方案

### 方案 A：仅 CLI 的解释层

只改进面向人的 CLI 输出，不改变 HTTP 与库的结果结构。

优点：

- 实现范围最小
- CLI 可见体验提升最快

缺点：

- 在传输层代码中复制了解释逻辑
- HTTP 与库调用方仍需自行处理
- 对 AI agent 的消费场景支撑较弱

### 方案 B：审计结果路径中的共享解释层

在规则求值之后，为 finding 附加结构化解释元数据，并让 CLI、HTTP 与库消费方共享同一份增强结果。

优点：

- 解释来源唯一
- 各传输界面保持对齐
- 为后续文档与 agent 工具打下良好基础
- 避免在各类 formatter 中重复实现解释逻辑

缺点：

- 需要谨慎设计结果结构
- 相比只做 CLI 输出，里程碑略大一些

### 方案 C：规则发现工作台

不止增强 finding，还围绕规则搜索、浏览与配置构建更广泛的规则发现工作台。

优点：

- 长期运维体验最好
- 提升上手与自助探索能力

缺点：

- 对单个里程碑来说范围过大
- 容易把“结果可用性”里程碑变成一个宽泛的治理/发现项目

## 推荐

选择方案 B。

DeltaScope 已经具备面向解释的规则目录雏形。下一步最具杠杆的动作，是将其提升为稳定、共享的解释层，用来增强真实审计 finding，而不是只生成一次性的 CLI 文案。这样既能聚焦于让结果更可执行，也不会把精力分散到无关的治理或发现工作上。

## 设计

### 1. 产品定义

这个里程碑要把 DeltaScope 从一个只能说“这条 SQL 有风险”的工具，提升为一个还能说明下列信息的工具：

- 为什么它会这样判断
- 它指向的是哪类具体风险
- 如何快速推进到可接受状态
- 哪条规则与哪个配置界面控制了该行为
- 元数据可用性是否影响了结果

该里程碑应命名为 `Explainable Audit Results`，而不是 `Rule Explainability`，因为产品界面是增强后的审计结果，而不只是静态规则元数据。

### 2. 共享解释模型

为每条 finding 增加一个稳定的解释结构。

推荐形状：

- `summary`
- `why`
- `risk`
- `suggestion`
- `rule`
  - `id`
  - `default_level`
  - `metadata_aware`
- `config`
  - 相关参数
  - level / enablement 是否可配置
- `links`
  - 指向规则/配置文档的稳定引用
- `metadata_note`
  - 说明解释是否因元数据感知上下文而受限或增强

该结构应简洁、确定，并且完全本地化。它不能依赖外部服务或模型推理。

### 3. 解释的事实来源

将已交付的规则目录作为解释元数据的唯一事实来源。

规则目录应从简单的发现元数据，扩展为能够解释已发布规则的元数据，包含：

- 稳定摘要
- 风险框架
- 修复提示
- 配置指引
- 元数据感知说明
- 仅在确实能提升修复清晰度时，加入可选的触发/合法示例

规则执行应与规则描述保持分离，它们之间的关联仍然是 `rule_id`。

### 4. 审计流程集成

保持当前审计流程不变：

`parse -> extract -> enrich -> evaluate`

在求值之后增加一个共享的解释增强阶段：

`parse -> extract -> enrich -> evaluate -> explain`

重要约束：

- 解释增强绝不能改变 verdict
- 解释增强绝不能屏蔽 finding
- 若解释元数据缺失，必须优雅退化为最小解释，而不是让审计失败

### 5. 结果界面

#### CLI

CLI 应为 finding 增加一个可读性强的详细解释模式，同时保留适合 shell 与 CI 的紧凑默认输出。

推荐方向：

- 保持当前紧凑默认输出稳定
- 增加一个详细模式或 explain 导向 flag，用于更丰富的输出
- 让 JSON 模式暴露完整结构化解释数据

#### HTTP

`POST /v1/audit` 应以稳定的结构化形式返回增强后的 finding 数据。现有 verdict 与 summary 语义应保持不变。

#### `pkg/deltascope`

稳定结果对象应暴露解释结构，使下游调用方（包括 AI agent）无需抓取 CLI 文本即可消费。

### 6. 元数据感知透明性

对于元数据感知规则与增强后的运行结果，解释必须诚实说明哪些信息可用、哪些信息不可用。

例如：

- 如果元数据让规则更精确，应明确说明
- 如果元数据不可用且解释质量受限，也应明确说明
- 不要暗示引擎实际上并没有掌握的确定性

这对维护离线优先行为的可信度至关重要。

### 7. 文档策略

这个里程碑还应增加一套稳定的、面向用户的解释，告诉用户如何阅读 DeltaScope 的结果。

推荐的文档产出：

- 更新 reference 文档，描述解释字段
- 增加一段简短的 recipe 或 reference 内容，展示如何理解增强后的 finding
- 在 CLI、HTTP 与库示例之间保持文档对齐

## 验收标准

当满足以下条件时，该里程碑完成：

1. DeltaScope 为 finding 附带稳定的解释结构。
2. 已发布规则的核心规则集在规则目录中具备解释元数据。
3. CLI 能展示解释细节，同时不破坏当前紧凑默认模式。
4. HTTP 审计响应暴露结构化解释数据。
5. `pkg/deltascope` 为下游调用方暴露同样的解释数据。
6. 解释元数据缺失时能优雅退化，且绝不改变 verdict 行为。
7. 元数据感知规则能明确表达元数据可用性是否影响了解释精度。
8. 产品文档解释了如何理解增强后的审计 finding。
