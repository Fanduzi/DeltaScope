# v0.36.0 PostgreSQL Generated/Identity Rule Coverage Pack Design

## Goal

Increase the practical audit value of PostgreSQL generated/identity support by making existing PostgreSQL DDL rule coverage apply coherently to the generated/identity forms that became supported in `v0.34.0` and `v0.35.0`.

This milestone is about **rule coverage**, not deeper parser support and not a full generated/identity semantics engine.

## Context

The PostgreSQL generated/identity line has already passed three support phases:

- `v0.33.0` preserved generated/identity facts and unsupported metadata
- `v0.34.0` supported generated/identity definition forms
- `v0.35.0` supported generated/identity state-transition forms

That means DeltaScope can now parse and normalize:

- generated stored definitions in `CREATE TABLE`
- identity definitions in `CREATE TABLE`
- generated/identity add-column forms in `ALTER TABLE`
- generated/identity state transitions such as:
  - `DROP EXPRESSION`
  - `SET GENERATED ALWAYS`
  - `SET GENERATED BY DEFAULT`
  - `DROP IDENTITY`

The remaining gap is not extractor coverage. The gap is whether those supported statements produce useful PostgreSQL audit findings beyond "statement is supported".

## Problem Statement

Supported PostgreSQL generated/identity statements now flow through the normal audit path, but there is still a strong chance that:

- some existing PostgreSQL DDL rules do not fire on these shapes
- the supported statements produce too little audit signal
- users cannot easily tell whether generated/identity-related DDL is low-risk or high-risk

This is now the wrong product posture. Parser support without meaningful rule coverage turns into "normalized but under-audited".

## Design Goal

Position `v0.36.0` as a **PostgreSQL rule coverage milestone**.

This release should be described as:

- "DeltaScope extends PostgreSQL DDL rule coverage to generated/identity forms already supported by the extractor"

not as:

- "DeltaScope now fully understands generated expressions"
- "DeltaScope now models full identity/sequence semantics"
- "DeltaScope now simulates complete generated/identity lifecycle behavior"

## Candidate Scope

### Statements In Scope

The candidate statement families are the already-supported PostgreSQL generated/identity forms:

- `CREATE TABLE ... GENERATED ALWAYS AS (...) STORED`
- `CREATE TABLE ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`
- `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED`
- `ALTER TABLE ... ADD COLUMN ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`
- `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ALWAYS`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED BY DEFAULT`
- `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

### Rule Goal

The immediate target is **existing PostgreSQL DDL rule coverage**, especially rules that already reason about:

- table rewrites
- lock severity / DDL disruption
- broad ALTER TABLE risk
- PostgreSQL-specific DDL boundaries and review surfaces

Task 1 must identify which existing rules currently do or do not apply to the in-scope statements.

### Optional Narrow Additions

If the gap analysis shows a clear high-value hole, `v0.36.0` may also add one or two narrow PostgreSQL rule improvements for generated/identity statements.

Examples of acceptable narrow additions:

- a generated/identity state-transition risk rule if one specific high-signal pattern is currently silent
- an identity-option change risk rule if it can be stated without full sequence semantics

Examples of unacceptable additions:

- expression evaluation
- dependency graphing of generated expressions
- full identity/sequence policy modeling

## Decision Gate

`v0.36.0` should begin with a rule-coverage decision gate.

Task 1 must answer:

### Proceed

Proceed only if:

- existing supported generated/identity statements can be traced through the current PostgreSQL rule pipeline
- the missing coverage can be fixed by changing rule applicability or adding one or two narrow rules
- no new schema-state simulation is required
- the rule changes can be expressed in current facts/contract

### Stop

Stop if:

- the apparent rule gap is actually a parser/fact gap again
- rule coverage would require full generated-expression semantics
- rule coverage would require complete sequence-state semantics
- the only path forward is a large policy system instead of a narrow coverage milestone

If Task 1 returns **Stop**, `v0.36.0` should downgrade to a smaller conclusion milestone:

- rule-coverage readiness report only
- or one tightly bounded PostgreSQL DDL rule fix unrelated to generated/identity

## Non-Goals

This milestone does not include:

- generated expression evaluation
- generated expression rendering
- full PostgreSQL identity/sequence semantics
- cross-statement schema-state reconstruction
- MySQL/TiDB generated/identity work
- transport redesign
- broad rule framework refactors

## Architecture Constraints

### Use Existing Facts First

Any rule coverage work must prefer facts already present in the current shared contract:

- `generated_when`
- `is_identity`
- `identity_options`
- explicit `spec.Alter.Action` values:
  - `drop_expression`
  - `set_generated`
  - `drop_identity`

If those facts are not sufficient, Task 1 should say so explicitly instead of inventing more support by default.

### Prefer Existing Rule Extension Over New Rule Explosion

The best outcome is that a few existing PostgreSQL DDL rules become applicable to generated/identity statements with minimal code.

The second-best outcome is one or two very narrow new PostgreSQL rule additions.

The wrong outcome is a large new rule family for generated/identity semantics.

## User-Facing Outcome

If this milestone ships, users should observe:

- generated/identity PostgreSQL DDL now produces more meaningful findings
- supported statements are not only parseable, but also better audited
- CLI / HTTP / MCP / pkg outputs contain clearer PostgreSQL risk signals for these forms

Users should not observe:

- claims of full generated/identity semantic understanding
- claims of expression evaluation
- claims of complete lifecycle reasoning

## Risks

### Overfitting Rules To Syntax

There is a risk of adding rules that trigger only because a statement contains generated/identity syntax, without reflecting a real operational risk.

Task 1 must separate syntax novelty from audit value.

### Rule Surface Drift

If a rule is changed to cover generated/identity statements, all service/corpus/public surfaces must stay aligned. This is manageable, but only if the scope remains narrow.

### Hidden Dependence On Missing Semantics

A rule that sounds simple may actually require missing semantic context. Task 1 must stop that before implementation starts.

## Success Criteria

Task 1 is the primary gate:

- a written rule-coverage report exists
- it identifies which existing rules hit or miss the supported generated/identity forms
- it returns **Proceed** or **Stop**

If the answer is **Proceed**, later tasks must prove:

- the approved rule coverage change produces real findings for the approved forms
- no unsupported generated/identity semantics are implied
- corpus, service, public surfaces, and docs all reflect the exact coverage increase
