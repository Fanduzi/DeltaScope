# v0.34.0 PostgreSQL Generated/Identity Narrow Support Pack Design

## Goal

Promote a narrow, explicitly bounded subset of PostgreSQL generated-column and identity-column statements from extractor-level unsupported outcomes to supported normalized DDL facts.

This milestone should turn prior fact-preservation work into real product capability without claiming full PostgreSQL generated/identity support.

## Context

The PostgreSQL generated/identity line has progressed in four steps:

- `v0.26.0` — `CREATE TABLE` generated/identity forms became explicit unsupported boundaries.
- `v0.30.0` / `v0.31.0` — `ALTER TABLE` generated/identity boundary family was tightened with explicit unsupported feature names.
- `v0.32.0` — readiness evidence established that parser access is stable enough for narrow support work.
- `v0.33.0` — shared contract facts and unsupported metadata surfacing were added:
  - `generated_when`
  - `is_identity`
  - `identity_options`
  - `UnsupportedDetail.Metadata`

The next step should stop treating every generated/identity column definition as unsupported. DeltaScope now has enough parser access and contract shape to let a bounded subset flow through the normal DDL path.

## Problem Statement

DeltaScope can now preserve facts about PostgreSQL generated/identity columns, but the statements that define those columns are still rejected as unsupported:

- `CREATE TABLE ... GENERATED ALWAYS AS (...) STORED`
- `CREATE TABLE ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`
- `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED`
- `ALTER TABLE ... ADD COLUMN ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`

That means users can see good metadata for statements that the engine still refuses to audit as supported DDL.

This is now the wrong tradeoff. The facts are stable enough, and the value of continuing to reject these exact forms is lower than the value of letting them participate in standard DDL review.

## Design Goal

Ship a narrow support release.

The release should be positioned as:

- "DeltaScope now supports narrow PostgreSQL generated/identity column definition forms in `CREATE TABLE` and `ALTER TABLE ... ADD COLUMN`"

not:

- "DeltaScope now fully supports generated columns"
- "DeltaScope now fully supports identity columns"
- "DeltaScope now evaluates generated expressions"
- "DeltaScope now models full PostgreSQL sequence semantics"
- "DeltaScope now supports generated/identity state transitions"

## Supported Scope

### Statements That Become Supported

#### `CREATE TABLE`

The following forms should become supported:

- generated stored column definitions:

```sql
CREATE TABLE users (
  first_name text,
  last_name text,
  full_name text GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED
);
```

- identity column definitions:

```sql
CREATE TABLE users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
```

```sql
CREATE TABLE users (
  id bigint GENERATED BY DEFAULT AS IDENTITY (
    START WITH 10
    INCREMENT BY 5
    CACHE 20
  ) PRIMARY KEY
);
```

#### `ALTER TABLE ... ADD COLUMN`

The following forms should become supported:

- generated stored add-column
- identity add-column, including `ALWAYS` and `BY DEFAULT`
- identity add-column with the limited structured `identity_options` shape already locked in `v0.33.0`

These statements should no longer populate `unsupported`.

### Facts That Must Remain Preserved

Supported statements must preserve the `v0.33.0` facts on `spec.Column`:

- `generated_when`
- `is_identity`
- `identity_options`

`GeneratedExpression` remains out of scope and must not appear in the shared contract.

## Unsupported Scope That Must Remain Unchanged

This milestone must not change the existing explicit unsupported behavior for state-transition forms:

- `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ...`
- `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

These should keep their current explicit unsupported feature names:

- `generated_column`
- `generated_as_identity`

## Non-Goals

This milestone does not include:

- generated expression semantic evaluation
- generated expression text rendering
- complete PostgreSQL sequence semantics
- new rule IDs
- generated/identity-specific audit rules
- PostgreSQL state-transition support for generated/identity columns
- MySQL/TiDB behavior changes
- public transport redesign
- release tagging/publishing inside implementation tasks

## Architecture

### Extractor Behavior

The PostgreSQL extractor should stop rejecting narrow generated/identity column definitions in:

- `CREATE TABLE` column extraction path
- `ALTER TABLE ... ADD COLUMN` extraction path

The extractor should continue to:

- fill `spec.Column` with `generated_when`, `is_identity`, and `identity_options`
- return normal `spec.Statement` / `spec.Alter` payloads
- avoid populating `UnsupportedDetail` for these narrow supported forms

### Unsupported Metadata

For the newly supported forms, unsupported metadata should disappear because the statement is no longer unsupported.

For state-transition forms that remain unsupported, the `v0.33.0` metadata behavior should stay as-is.

## User-Facing Outcome

After `v0.34.0`, users should observe:

- generated/identity `CREATE TABLE` statements audit like other supported PostgreSQL DDL
- generated/identity `ALTER TABLE ... ADD COLUMN` statements audit like other supported PostgreSQL alter actions
- no `ErrUnsupportedStatement` / `unsupported` array for those narrow supported cases
- structured generated/identity facts remain visible in shared/public result payloads

Users should not observe:

- new blocker/warning/notice rules specifically for generated/identity semantics
- generated expression evaluation
- support for `DROP EXPRESSION`, `SET GENERATED`, or `DROP IDENTITY`

## Rule Behavior

This milestone should not introduce new rules.

Supported generated/identity statements simply become eligible for the existing PostgreSQL DDL pipeline:

- statement extraction succeeds
- statement facts reach the normal audit application flow
- existing generic DDL rules can run where relevant

If current rules ignore generated/identity-specific facts, that is acceptable for `v0.34.0`. This release is about support admission, not semantic policy depth.

## Compatibility

This change is behavior-widening, not shape-widening:

- no new contract fields should be added beyond `v0.33.0`
- no existing fields should be removed
- supported statements will stop appearing in `unsupported`

That last point is the main compatibility change. It is intentional and should be treated as the core product behavior change of `v0.34.0`.

## Risks

### Overclaiming

Docs must say "narrow support" or "supported definition forms", not "full support".

### Hidden dependency risk

The current unsupported branches may be the only place preserving some generated/identity facts. Task 1 must confirm that once those branches are removed for narrow supported forms, the facts still survive in normal statement extraction.

### Rule gap risk

Supported generated/identity statements may produce no new findings. That is acceptable for this milestone, but docs must not imply semantic enforcement beyond support admission.

### State-transition confusion

Users may assume `DROP EXPRESSION` / `SET GENERATED` / `DROP IDENTITY` also became supported. Docs and tests must explicitly prevent this.

## Success Criteria

- `CREATE TABLE` generated stored columns become supported.
- `CREATE TABLE` identity columns become supported.
- `ALTER TABLE ... ADD COLUMN` generated stored columns become supported.
- `ALTER TABLE ... ADD COLUMN` identity columns become supported.
- `generated_when`, `is_identity`, and `identity_options` remain preserved on supported statements.
- The above statements no longer populate `unsupported`.
- State-transition generated/identity forms remain explicit unsupported outcomes.
- Corpus, service, CLI, HTTP, MCP, and `pkg/deltascope` tests all lock the new supported behavior.
- Release docs describe support widening accurately and narrowly.
