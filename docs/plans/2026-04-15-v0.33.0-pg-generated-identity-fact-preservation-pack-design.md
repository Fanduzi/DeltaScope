# v0.33.0 PostgreSQL Generated/Identity Fact Preservation + Unsupported Metadata Surfacing Pack Design

## Goal

Preserve PostgreSQL generated-column and identity-column facts in DeltaScope's shared statement contract, and expose those facts through unsupported-result metadata when generated/identity statements still return unsupported outcomes.

This milestone is the first controlled step from boundary-only PostgreSQL work toward real semantic support. It should add user-visible facts, not claim generated-column or identity-column support.

## Context

Recent PostgreSQL releases tightened generated/identity unsupported boundaries:

- `v0.26.0`: `CREATE TABLE` generated columns and identity columns became explicit unsupported outcomes.
- `v0.30.0`: `ALTER TABLE ... ADD COLUMN` generated/identity forms became explicit unsupported outcomes.
- `v0.31.0`: adjacent generated/identity `ALTER TABLE` forms (`DROP EXPRESSION`, `SET GENERATED`, `DROP IDENTITY`) became explicit unsupported outcomes.
- `v0.32.0`: the support-readiness gate confirmed stable AST facts and recommended fact preservation before full support.

The important `v0.32.0` conclusion is:

- parser access is not the blocker
- shared contract shape is the blocker
- generated/identity facts should enter DeltaScope as facts first
- full support, rule behavior, and stateful `ALTER TABLE` semantics should remain deferred

## Problem Statement

DeltaScope currently recognizes generated/identity PostgreSQL statements well enough to reject them with stable unsupported feature names, but unsupported results do not carry structured generated/identity facts.

That leaves users with a precise feature tag, but not enough context:

- a generated column is reported as `generated_column`, but the generated mode and expression are not surfaced
- an identity column is reported as `generated_as_identity`, but `ALWAYS` vs `BY DEFAULT` and sequence options are not surfaced
- CLI/HTTP/MCP/pkg consumers cannot build richer reporting around unsupported generated/identity boundaries without reparsing SQL themselves

The next useful milestone is therefore not "support generated columns". It is "preserve generated/identity facts consistently, even when the statement is still unsupported".

## Design Goal

Ship a fact-preservation and metadata-surfacing release.

The release should be positioned as:

- "DeltaScope now preserves generated/identity facts and surfaces them in unsupported metadata"

not:

- "DeltaScope now supports generated columns"
- "DeltaScope now supports identity columns"
- "DeltaScope now evaluates generated expressions"
- "DeltaScope now models PostgreSQL sequence behavior"
- "DeltaScope now supports generated/identity `ALTER TABLE` state transitions"

## Non-Goals

This milestone does not include:

- removing `generated_column` unsupported outcomes
- removing `generated_as_identity` unsupported outcomes
- generated expression semantic evaluation
- full identity sequence semantics
- rule behavior changes
- new rule IDs
- new CLI flags
- stateful schema-diff behavior for `ALTER TABLE`
- MySQL/TiDB behavior changes
- release tagging/publishing inside implementation tasks

## Contract Shape

### Column Facts

Add additive `omitempty` fields to `spec.Column`.

Recommended candidate shape:

```go
type Column struct {
    // existing fields...
    GeneratedWhen       string                 `json:"generated_when,omitempty"`
    GeneratedExpression string                 `json:"generated_expression,omitempty"`
    IsIdentity          bool                   `json:"is_identity,omitempty"`
    IdentityOptions     map[string]interface{} `json:"identity_options,omitempty"`
}
```

The implementation tasks should validate the final type before editing production code. The expected semantics are:

- `GeneratedWhen`: PostgreSQL `pg_query` encoding, where `"a"` means `ALWAYS` and `"d"` means `BY DEFAULT`
- `GeneratedExpression`: stable SQL expression string if a safe deparse/rendering path is available
- `IsIdentity`: true only for `CONSTR_IDENTITY`
- `IdentityOptions`: normalized identity sequence options when present

If Task 1 proves expression rendering or option normalization is not stable enough, the implementation should narrow the first production change to:

```go
GeneratedWhen string `json:"generated_when,omitempty"`
IsIdentity    bool   `json:"is_identity,omitempty"`
```

and defer the unstable fields. The milestone should not force weak contracts into public JSON.

### Unsupported Metadata

Add additive metadata to unsupported details so unsupported generated/identity outcomes can carry the same facts as the extracted column.

Recommended candidate shape:

```go
type UnsupportedDetail struct {
    Index    int            `json:"index,omitempty"`
    Feature  string         `json:"feature"`
    SQL      string         `json:"sql,omitempty"`
    Reason   string         `json:"reason"`
    Metadata map[string]any `json:"metadata,omitempty"`
}
```

Recommended metadata keys:

| Key | Type | Applies to | Meaning |
|-----|------|------------|---------|
| `table` | string | generated + identity | owning table name when available |
| `table_schema` | string | generated + identity | owning table schema when explicitly present |
| `column` | string | generated + identity | affected column name |
| `generated_when` | string | generated + identity | `"a"` or `"d"` from `pg_query` |
| `generated_expression` | string | generated column | expression string if safely available |
| `is_identity` | bool | identity | true for identity columns |
| `identity_options` | object | identity | normalized option map if safely available |

Metadata must be omitted when empty. Existing consumers that ignore unknown JSON fields remain compatible.

## Supported Statement Scope

### In Scope

Fact preservation should initially cover:

- `CREATE TABLE ... column GENERATED ALWAYS AS (...) STORED`
- `CREATE TABLE ... column GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY (...)`
- `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED`
- `ALTER TABLE ... ADD COLUMN ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY (...)`

Unsupported metadata should be surfaced for the same generated/identity boundaries because these statements remain unsupported.

### Out of Scope

Do not attempt fact preservation for state-transition statements in this milestone:

- `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ...`
- `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

Those statements do not include a full target column definition. They should keep explicit unsupported feature names from `v0.31.0`, but they should not block the `CREATE TABLE` / `ADD COLUMN` fact-preservation milestone.

## Expression Strategy

Generated expression rendering is the highest contract-risk item.

Task 1 must decide between:

1. Use an existing stable `pg_query` deparse/rendering path.
2. Implement a narrow expression renderer for simple expressions already in tests.
3. Defer `GeneratedExpression` from production and only preserve mode/identity facts.

Recommendation: prefer deferral over a brittle renderer. If the expression cannot be rendered with a stable contract, do not add `GeneratedExpression` in `v0.33.0`.

## Identity Option Strategy

Identity options should be normalized only after characterizing enough option shapes.

Minimum options to characterize before production:

- `START WITH`
- `INCREMENT BY`
- `MINVALUE`
- `MAXVALUE`
- `CACHE`
- `CYCLE`
- `NO CYCLE`

Recommended normalization:

- lowercase keys without PostgreSQL syntax noise (`start`, `increment`, `minvalue`, `maxvalue`, `cache`, `cycle`)
- integer values for numeric options
- boolean value for `cycle`
- omit unsupported/unknown option forms rather than guessing

If mixed option value types are not stable, defer `IdentityOptions` from production and ship only `GeneratedWhen` + `IsIdentity`.

## Data Flow

1. PostgreSQL parser produces `ColumnDef` constraints.
2. Extractor reads `CONSTR_GENERATED` and `CONSTR_IDENTITY`.
3. Extractor fills additive fields on `spec.Column`.
4. If the statement remains unsupported, extractor also attaches a metadata map to `spec.UnsupportedDetail`.
5. Application audit aggregation copies unsupported details without dropping metadata.
6. CLI, HTTP, MCP, and `pkg/deltascope` surfaces serialize the unsupported metadata unchanged.

The implementation should avoid reparsing SQL at transport layers. All facts should originate in the PostgreSQL extractor.

## Compatibility

This is additive and backward-compatible if:

- all new fields use `omitempty`
- unsupported metadata is omitted when empty
- existing unsupported feature names remain unchanged
- existing unsupported errors remain errors on surfaces that currently propagate them as errors
- no existing rule IDs or verdict behavior changes

Potential compatibility risk:

- Golden JSON tests that compare entire objects may need updates because generated/identity cases now include extra fields.
- Users relying on exact unsupported JSON shape may see additive `metadata`; this should be documented as a non-breaking additive field.

## Test Strategy

### Characterization Gate

Task 1 should prove:

- expression rendering strategy is stable or explicitly deferred
- identity option normalization is stable or explicitly deferred
- the same facts are available for `CREATE TABLE` and `ALTER TABLE ADD COLUMN`
- unsupported detail can carry metadata without changing existing unsupported error flow

### Production Tests

When production changes begin, tests should lock:

- `spec.Column` JSON omits new fields when absent
- generated column facts are preserved when present
- identity facts are preserved when present
- unsupported metadata contains the same generated/identity facts
- no `generated_column` / `generated_as_identity` unsupported behavior is removed

### Surface Tests

CLI, HTTP, MCP, and `pkg/deltascope` should assert:

- unsupported feature remains exact
- unsupported reason is non-empty
- metadata exists for generated/identity boundaries
- metadata contains stable keys
- no surface invents facts that the extractor did not provide

## Risks

### Overclaiming

Docs must repeatedly state that this is fact preservation and metadata surfacing, not support.

### Expression instability

Generated expression strings can become a long-term public contract. If stable rendering is not obvious, defer the field.

### Option-model instability

Identity options can have mixed value types and optional/negative forms. If the normalization contract is not clear, defer the field.

### Unsupported metadata widening

Adding `metadata` to `UnsupportedDetail` is public JSON widening. It is additive, but all public surfaces must be tested.

## Success Criteria

- PostgreSQL generated/identity facts are preserved in shared contracts for selected `CREATE TABLE` and `ALTER TABLE ADD COLUMN` statements.
- Unsupported generated/identity outcomes expose structured metadata through all public surfaces.
- Existing unsupported feature names remain unchanged.
- Existing unsupported error behavior remains unchanged.
- Expression and identity option fields are either implemented with stable tests or explicitly deferred.
- Corpus, service, CLI, HTTP, MCP, and `pkg/deltascope` tests pass.
- Release docs describe fact preservation and metadata surfacing without claiming support.
