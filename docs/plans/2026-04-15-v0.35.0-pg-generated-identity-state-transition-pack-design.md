# v0.35.0 PostgreSQL Generated/Identity State-Transition Pack Design

## Goal

Evaluate and, only if proven safe, support a narrow subset of PostgreSQL generated/identity state-transition statements that currently remain explicit unsupported boundaries.

This milestone must begin with a decision gate. Unlike the `v0.34.0` definition-form support work, these statements change existing column state and may require richer modeling than DeltaScope currently has.

## Context

The PostgreSQL generated/identity line has progressed in three product stages:

- `v0.33.0` preserved shared facts and surfaced unsupported metadata:
  - `generated_when`
  - `is_identity`
  - `identity_options`
- `v0.34.0` promoted narrow definition forms to supported behavior:
  - `CREATE TABLE ... GENERATED ALWAYS AS (...) STORED`
  - `CREATE TABLE ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`
  - `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED`
  - `ALTER TABLE ... ADD COLUMN ... GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`
- state-transition forms were deliberately left unsupported:
  - `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`
  - `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ...`
  - `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

The next obvious gap is those remaining state-transition statements. But the shape of the gap is different from `v0.34.0`: definition forms describe a new column; state-transition forms mutate an existing one.

## Problem Statement

DeltaScope now supports narrow generated/identity definition forms, but it still rejects PostgreSQL generated/identity state transitions with explicit unsupported features:

- `generated_column`
- `generated_as_identity`

Those unsupported outcomes are intentional today. The system may not yet have enough statement/state representation to describe:

- removing a generated expression from an existing column
- changing an identity mode from `ALWAYS` to `BY DEFAULT` or the reverse
- removing identity semantics from an existing column

If DeltaScope cannot express those transitions cleanly in `spec.DDL.Alter`, simply removing the unsupported gate would create misleading or under-specified output.

## Design Goal

Position `v0.35.0` as a **state-transition readiness-first milestone**.

That means:

- start with a hard decision gate
- only proceed to production support if the existing statement/alter contract can represent the transitions clearly
- stop and downgrade the milestone if the contract is not strong enough

This release must not overclaim.

## Candidate Scope

### Candidate Statements

The candidate forms for support evaluation are:

#### Generated-column transition

```sql
ALTER TABLE users ALTER COLUMN full_name DROP EXPRESSION;
```

#### Identity transitions

```sql
ALTER TABLE users ALTER COLUMN id SET GENERATED ALWAYS;
ALTER TABLE users ALTER COLUMN id SET GENERATED BY DEFAULT;
ALTER TABLE users ALTER COLUMN id DROP IDENTITY;
```

These are the forms already characterized in earlier PostgreSQL boundary work.

### Required Facts If Supported

If any of these statements become supported, the normalized output must still preserve clear facts about the target column and transition intent.

At minimum the system would need to represent:

- target column name
- transition kind
- identity mode when applicable (`ALWAYS` vs `BY DEFAULT`)
- any stable pre-existing generated/identity facts already preserved by current extractor logic

## Decision Gate

`v0.35.0` must start with a go/no-go gate. Task 1 must answer:

### Proceed

Proceed only if all of the following are true:

- AST access for `DROP EXPRESSION`, `SET GENERATED`, and `DROP IDENTITY` is stable
- current extractor already exposes enough facts to describe the transition safely
- `spec.DDL.Alter` can represent the transition without inventing ambiguous or fake semantics
- public result surfaces can express the supported transition without breaking existing contracts

### Stop

Stop if any of the following is true:

- transition semantics cannot be represented cleanly in the current shared contract
- support would require schema-state reconstruction across statements
- support would need generated-expression evaluation or full sequence-state modeling
- support would blur the line between extractor facts and semantic inference

If Task 1 returns **Stop**, `v0.35.0` should be downgraded to one of:

- explicit unsupported tightening only
- state-transition fact preservation only
- no feature release on this line yet

## Supported Scope If The Gate Passes

Only the narrowest safe state transitions should become supported.

The preferred order is:

1. `SET GENERATED ALWAYS|BY DEFAULT`
2. `DROP IDENTITY`
3. `DROP EXPRESSION`

That order is intentional:

- `SET GENERATED` may be the easiest to model as a mode-change intent
- `DROP IDENTITY` may be representable as removing a known flag
- `DROP EXPRESSION` is the riskiest, because it implies expression removal from an existing generated column without carrying the expression text itself

The milestone does not need to support all three if the gate shows only a subset is safe.

## Unsupported Scope That Must Remain Unchanged

Regardless of Task 1 outcome, `v0.35.0` must not expand into:

- generated expression text rendering
- generated expression semantic evaluation
- full PostgreSQL identity/sequence semantics
- cross-statement schema-state reconstruction
- new generated/identity-specific rules
- MySQL/TiDB behavior changes
- transport redesign

## Architecture Constraints

### Statement Model Risk

Definition forms were simple because they attach facts to a new `spec.Column`.

State transitions are different:

- they mutate an existing column
- they may not carry complete column state in the AST node itself
- they may need a transition-specific shape in `spec.Alter`

Task 1 must verify whether the current `spec.Alter` model is sufficient before any code changes are attempted.

### Extractor Risk

The current explicit unsupported mappings are safe because they avoid under-modeled results.

Removing those mappings is only acceptable if the normal extraction path yields enough stable structure to produce accurate supported statements.

### Surface Risk

CLI, HTTP, MCP, and `pkg/deltascope` all already distinguish supported statements from unsupported boundaries. If a state-transition form becomes supported, every surface must move coherently.

If a supported representation would be vague or transport-specific, the milestone should stop.

## User-Facing Outcome

If the gate passes and support ships, users should observe:

- a narrow, explicit subset of PostgreSQL generated/identity state transitions becomes supported
- those statements flow through the normal audit result path instead of `unsupported`
- the result structure remains specific enough to understand what transition happened

Users should not observe:

- claims of full generated-column support
- claims of full identity-column lifecycle support
- generated expression text evaluation
- complete PostgreSQL sequence behavior modeling

If the gate fails, users should observe no support widening in this line.

## Rule Behavior

This milestone must not introduce new rules by default.

If support ships, supported state-transition statements simply become eligible for the existing PostgreSQL DDL audit flow. Any deeper generated/identity policy should remain a later milestone.

## Compatibility

If the milestone stops at the gate, compatibility is unchanged.

If the milestone proceeds:

- supported statements will stop appearing in `unsupported`
- no existing `v0.34.0` facts should be removed
- any new contract shape must be narrow, explicit, and justified by Task 1 evidence

## Risks

### Contract Overreach

The biggest risk is forcing a transition model into a contract that only cleanly describes definitions.

### Hidden State Assumptions

These ALTER statements may imply prior state that is not present in the statement itself. DeltaScope must not fake that missing context.

### Documentation Drift

If the gate stops, docs must not describe the milestone as shipped support. The implementation plan must preserve a clear stop path.

## Success Criteria

Task 1 is the first success criterion:

- a written decision report exists
- it clearly returns **Proceed** or **Stop**
- it explains whether the current shared/alter contract is sufficient

If the answer is **Proceed**, later tasks must then prove:

- only the approved state-transition subset becomes supported
- the supported result path remains explicit and non-ambiguous
- unsupported feature mappings remain intact for any deferred transitions
- corpus, service, public surface, and docs are all aligned with the exact supported subset
