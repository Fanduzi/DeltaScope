## Task 1 Findings

### High-value candidates for explicit unsupported subtype

**ALTER TABLE OWNER TO** (`changeowner`): This is the only generic ALTER TABLE subtype that has medium user value. Ownership changes are relevant to migration reviews because they affect access control. Making it an explicit unsupported subtype with a descriptive reason string would improve user-facing error messages. However, the user value is still "medium" not "high" — most migration review tools do not audit ownership changes as part of schema safety.

**No other generic candidates qualify as high-value.** The remaining `alterSubtypeFeature` outputs are operational commands (SET STATISTICS, SET STORAGE, CLUSTER, TRIGGER management, RLS, TABLESPACE, etc.) that are not schema-structure-relevant for a DDL migration review tool.

### Candidates that should stay generic for now

All other `alterSubtypeFeature` generic outputs should stay generic. Rationale:

1. They are operational/maintenance commands, not schema definition changes.
2. DeltaScope's audit value proposition is schema-structure review, not operational PostgreSQL management.
3. Adding explicit unsupported subtypes for each would increase taxonomy surface without improving audit outcomes.
4. No corpus, service, or surface parity coverage exists for any of them, so the cost of explicit handling is non-trivial.

### Candidates that need Task 2 support-readiness evidence

None of the generic candidates need Task 2 support-readiness evidence. Task 2 is specifically about `generated_column` and `generated_as_identity` readiness, which are already explicit unsupported features (not generic). The generic candidates identified in this inventory are not candidates for real support.

### Additional finding: CREATE INDEX unsupported forms have no corpus coverage

The extractor has explicit handling for 5 unsupported CREATE INDEX variants (partial index, expression index, include clause, non-btree access method, nulls not distinct), all with explicit reasons and parser tests. However, none of these have corpus YAML coverage. This is a minor gap but not a blocking issue for the support-readiness decision.

## Generated / Identity Readiness Evidence

### AST Fact Coverage (after Task 2 characterization tests)

| Fact | CREATE TABLE availability | ALTER TABLE ADD COLUMN availability | Contract risk | Notes |
|------|---------------------------|--------------------------------------|---------------|-------|
| Generated expression (`RawExpr`) | Confirmed: `CONSTR_GENERATED.RawExpr` is non-nil `*Node` | Confirmed: identical shape | Low | Expression is available as a raw AST node. Rendering it into a stable string requires expression-tree walking or `pg_query.Deparse`, which is a contract design question, not a parser access question. |
| Generated mode (`GeneratedWhen`) | Confirmed: `"a"` for ALWAYS | Confirmed: identical | Low | Single-character stable string: `"a"` = ALWAYS, `"d"` = BY DEFAULT. Backward-compatible as long as PostgreSQL does not introduce a third mode (no evidence of such a plan). |
| Identity mode (`CONSTR_IDENTITY` + `GeneratedWhen`) | Confirmed: `CONSTR_IDENTITY` with `GeneratedWhen="a"` (ALWAYS) or `"d"` (BY DEFAULT) | Confirmed: identical shape | Low | Same `GeneratedWhen` encoding as generated columns. `ColumnDef.Identity` is empty in both cases; identity is conveyed entirely through the constraint list. |
| Identity sequence options | Confirmed: `Constraint.Options` is `[]*Node` of `DefElem` nodes with lowercase `defname` and `Integer` arg | Confirmed: identical shape | Medium | Option `defname` values observed: `"start"`, `"increment"`, `"cache"`. Values are `int32` via `GetInteger().GetIval()`. Other options (`MINVALUE`, `MAXVALUE`, `CYCLE`, `NO CYCLE`, `RESTART`) were not tested but likely follow the same pattern. The medium risk is because the full option set is not yet characterized and some options may use non-integer arg types (e.g., `RESTART` with no value, or `NO MINVALUE` as a boolean flag). |
| `CREATE TABLE` vs `ALTER TABLE ADD COLUMN` consistency | — | — | Low | Both paths produce identical `ColumnDef` shapes. `ColumnDef.Identity` is empty in both. `CONSTR_IDENTITY` constraint with `GeneratedWhen` and `Options` is identical in both. Sequence option `DefElem` nodes have the same structure. |

### Evidence Source

All facts in this table are backed by `t.Fatalf` assertions in `parser_test.go`:

- `TestParseCreateTableGeneratedStoredColumnAST` — generated expression, ALWAYS mode, `RawExpr`
- `TestParseAlterTableAddGeneratedStoredColumnAST` — ALTER TABLE generated expression (confirms identical shape)
- `TestParseCreateTableIdentityColumnAST` — identity ALWAYS mode, `CONSTR_IDENTITY`
- `TestParseAlterTableAddIdentityColumnAST` — ALTER TABLE identity ALWAYS mode (confirms identical shape)
- **`TestParseCreateTableIdentityByDefaultWithOptionsSupportReadinessFacts`** — BY DEFAULT `GeneratedWhen="d"`, sequence options (`start`, `increment`, `cache`) with `DefElem` shape
- **`TestParseAlterTableAddIdentityByDefaultWithOptionsSupportReadinessFacts`** — ALTER TABLE BY DEFAULT + sequence options (confirms identical shape)
- `TestParseAlterTableSetIdentityGeneratedAST` — `SET GENERATED BY DEFAULT` produces `DefElem` with `defname="generated"`, `ival=100`
- `TestParseAlterTableSetIdentityGeneratedAlwaysAST` — `SET GENERATED ALWAYS` produces same `DefElem` shape

### Readiness Finding

**Ready for narrow fact preservation, not full semantic support.**

Rationale:

1. All parser facts are stable and accessible through `pg_query_go/v6`. `GeneratedWhen`, `RawExpr`, and `Constraint.Options` are well-defined protobuf fields with deterministic values.
2. `CREATE TABLE` and `ALTER TABLE ADD COLUMN` produce identical AST shapes, meaning a single extraction path can handle both.
3. Identity sequence options are available but only partially characterized. The tested options (`start`, `increment`, `cache`) all use `DefElem` with `Integer` arg. Other options (`MINVALUE`, `MAXVALUE`, `CYCLE`, `RESTART`) need characterization before production support.
4. `GeneratedWhen` encoding (`"a"` / `"d"`) is stable across both generated columns and identity columns, reducing contract design surface.
5. However, **this does not equal "ready for full support"** because:
   - No shared spec fields exist yet (`spec.Column` has no generated/identity fields).
   - Generated expressions are raw AST nodes — rendering them into stable string form requires additional design.
   - Identity sequence options are a variable-length list of key-value pairs that need a schema decision (flat struct? map? list?).
   - Corpus, service, CLI, HTTP, and MCP surfaces would all need updates for any new spec fields.

### Task 3 Input

Based on this evidence, Task 3 should evaluate:

1. **Recommended**: Add fact-preservation fields to `spec.Column` in a future `v0.33.0` milestone — store `GeneratedWhen` and identity mode as stable strings, defer expression rendering and sequence option modeling to a later milestone.
2. **Not recommended yet**: Full semantic support including generated expression evaluation, identity sequence option modeling, or rule behavior changes.
3. The contract decision should consider that `CREATE TABLE` and `ALTER TABLE ADD COLUMN` share identical AST shapes, so a single extraction path can serve both DDL contexts.
