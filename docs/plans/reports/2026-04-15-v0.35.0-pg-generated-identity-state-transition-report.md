## State Model Assessment

Current `spec.DDL` / `spec.Alter` can represent all four transitions without fake semantics or hidden state reconstruction.

Each transition can be modeled as:

1. **A distinct `Action` string** — `"drop_expression"`, `"set_generated"`, `"drop_identity"` — unambiguous, no overlap with existing actions.
2. **Column name via `Name` and `AlterColumn.OldName`** — the target column is explicitly named in the AST via `cmd.GetName()`.
3. **Mode via `Options` or `Column.Definition.GeneratedWhen`** — for `SET GENERATED`, the ALWAYS/BY DEFAULT distinction maps directly to the existing `GeneratedWhen` field convention (`"a"` = ALWAYS, `"d"` = BY DEFAULT).

No new `spec.DDL` or `spec.Alter` fields are required. The `Options` map and existing `AlterColumn`/`Column` types are sufficient. No cross-statement state reconstruction is needed — each statement is self-contained. No expression evaluation is involved. No sequence semantics are required.

The key insight is that these are all **single-statement, single-column transitions** where the AST provides complete intent in the command itself.

## Task 2 Decision

**Proceed.**

All four candidate state transitions have sufficient AST-level facts and can be modeled explicitly in the current `spec.Alter` contract without new fields, fake semantics, or hidden state reconstruction.

## Approved Production Scope For Task 2

Task 2 may implement support for all four state transitions:

1. `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION` → `spec.Alter{Action: "drop_expression", ...}`
2. `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ALWAYS` → `spec.Alter{Action: "set_generated", ..., Options: {"generated_when": "a"}}`
3. `ALTER TABLE ... ALTER COLUMN ... SET GENERATED BY DEFAULT` → `spec.Alter{Action: "set_generated", ..., Options: {"generated_when": "d"}}`
4. `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY` → `spec.Alter{Action: "drop_identity", ...}`

Minimum allowed extractor change in `alterFromCmd`:

- Replace the three immediate `return unsupported` branches (`AT_DropExpression`, `AT_SetIdentity`, `AT_DropIdentity`) with proper `spec.Alter` construction.
- For `AT_SetIdentity`: parse the `DefElem` list to extract the generated mode integer (97=a, 100=d) and carry it in `Options["generated_when"]`.
- All four must populate `spec.AlterColumn{OldName: cmd.GetName()}` to carry the target column.
- No changes to `spec.DDL`, `spec.Alter`, `spec.AlterColumn`, or `spec.AlterColumnChange` structs.
- No changes to `spec.Column` fields.

## Explicit Deferrals

None of the four transitions need to remain unsupported. However, the following related capabilities remain explicitly out of scope:

- Generated expression text rendering (the expression body from `GENERATED ALWAYS AS (...) STORED`)
- Generated expression semantic evaluation
- Full PostgreSQL identity/sequence semantics (sequence options beyond what `v0.33.0` already preserves)
- `ALTER TABLE ... ALTER COLUMN ... RESTART` or other sequence-specific identity commands
- Cross-statement schema-state reconstruction
- New rule IDs for generated/identity-specific policy
