## Coverage Gaps

### Gap 1: State-transition actions have zero rule coverage

The three state-transition actions (`drop_expression`, `set_generated`, `drop_identity`) are not targeted by any registered rule. No existing PG-native forbid rule matches these action strings. The characterization test `TestPGAlterActionForbidRulesDoNotCoverGeneratedIdentityActions` proves this explicitly.

**Root cause:** These are new action values introduced in v0.35.0. No corresponding forbid/warn rules were registered for them.

**Fix:** Register PG-only forbid rules for `drop_expression`, `set_generated`, and `drop_identity` using the existing `newForbiddenAlterActionRule` + `withDialectAllowlist(PostgreSQL)` pattern. This is a direct extension of the existing 5-rule pattern.

### Gap 2: ADD COLUMN with generated/identity produces no findings

ALTER TABLE ADD COLUMN with generated/identity columns produces zero findings because:
- The PG rewrite warn rule (`ddl.pg.alter.add_column.non_null_default.rewrite.warn`) only fires when `NotNull && HasDefault` are both true
- Generated stored columns may not have `HasDefault=true` (they have a generated expression, not a DEFAULT)
- Identity columns do not have `HasDefault=true`

**Root cause:** The rewrite warn rule's applicability predicate does not account for `generated_when` or `is_identity` facts.

**Fix (optional, lower priority):** Extend the rewrite warn rule to also trigger on `add_column` actions where the column has `generated_when != ""`. This is a narrow applicability extension, not a new rule.

### Why this is NOT a parser/spec gap

- The parser already produces correct `spec.Alter.Action` values: `drop_expression`, `set_generated`, `drop_identity`
- The spec already carries `generated_when`, `is_identity`, `identity_options` on column definitions
- The facts are available in `spec.Alter.Options` for state-transition forms
- No parser or spec changes are needed to express the missing rules

## Task 2 Decision

**Proceed.**

### Justification

All four Proceed criteria are satisfied:

1. **Missing coverage is rule applicability/coverage, not parser/spec/contract.** The action values and column facts are already produced correctly by the extractor. The gap is purely that no rule checks for these action values.

2. **No generated expression evaluation required.** The rules only need to detect the action type (`drop_expression`, `set_generated`, `drop_identity`) and produce a finding. No expression parsing or evaluation.

3. **No complete PostgreSQL sequence semantics required.** The rules don't need to understand identity sequence parameters, just that an identity-related state transition is happening.

4. **No cross-statement schema-state reconstruction required.** Each rule evaluates a single statement in isolation, using only the facts already present in the statement's spec.

5. **Solvable through existing rule extension.** The fix uses the same `newForbiddenAlterActionRule` + `withDialectAllowlist(PostgreSQL)` factory pattern that already produces the 5 existing PG-native alter action forbid rules.
