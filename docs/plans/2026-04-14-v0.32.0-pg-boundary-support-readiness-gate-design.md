# v0.32.0 PostgreSQL Boundary Support-Readiness Gate Design

## Goal

Decide whether DeltaScope should keep deepening PostgreSQL explicit unsupported boundary subtyping or start one narrow real-support milestone for generated/identity semantics.

This is a decision-gate milestone. It should produce evidence, contracts, and a recommendation for `v0.33.0`. It should not ship new PostgreSQL semantic support.

## Context

Recent PostgreSQL milestones have deliberately tightened boundary contracts instead of widening support claims:

- `v0.26.0`: `CREATE TABLE` generated/identity, exclusion constraint, and partitioning boundaries became explicit unsupported outcomes.
- `v0.30.0`: `ALTER TABLE ... ADD COLUMN` generated/identity forms became explicit unsupported outcomes.
- `v0.31.0`: adjacent generated/identity alteration forms (`DROP EXPRESSION`, `SET GENERATED`, `DROP IDENTITY`) became explicit unsupported outcomes.

That work has made the generated/identity boundary family consistent:

- generated-column semantics map to `generated_column`
- identity-column semantics map to `generated_as_identity`
- all public surfaces expose unsupported behavior consistently

The next question is no longer "which immediate generated/identity boundary is missing?" The next question is "what evidence is required before any explicit unsupported boundary becomes real support?"

## Problem Statement

DeltaScope has a strong boundary discipline, but the roadmap now needs a support-readiness decision.

Continuing to add unsupported subtypes can still be valuable, but it risks turning into open-ended taxonomy work unless the project periodically asks:

- which remaining PostgreSQL generic unsupported forms are actually high value
- whether any generated/identity facts can be safely represented in the shared spec
- whether public output contracts can remain backward-compatible if support is added
- whether real support would improve audit value enough to justify the added semantic surface

The key risk is not parser access. PostgreSQL AST facts are often available. The risk is contract design: generated expressions and identity options need stable representation across corpus, service, CLI, HTTP, MCP, and `pkg/deltascope`.

## Design Goal

Ship a support-readiness gate, not a feature release.

The release should be positioned as:

- "DeltaScope now has an evidence-backed decision on PostgreSQL generated/identity support readiness"

not:

- "DeltaScope now supports generated columns"
- "DeltaScope now supports identity columns"
- "DeltaScope now supports more PostgreSQL `ALTER TABLE` forms"
- "DeltaScope now has complete PostgreSQL DDL support"

## Non-Goals

This milestone does not include:

- production extractor support for generated columns
- production extractor support for identity options
- new shared spec fields
- new public JSON fields
- new rule IDs
- new CLI flags
- new supported DDL output for generated/identity forms
- changing existing unsupported feature names
- changing MySQL/TiDB behavior
- final release/tag/push work inside implementation tasks

## Decision Space

### Option A: Continue boundary tightening

Keep generated/identity as explicit unsupported boundaries and use future milestones to improve generic unsupported subtype coverage for other PostgreSQL DDL shapes.

Pros:

- low implementation risk
- preserves current contract simplicity
- continues the proven corpus/surface parity pattern

Cons:

- delays any real PostgreSQL semantic support expansion
- may eventually provide diminishing returns

### Option B: Start a narrow real-support milestone

Choose one extremely small support target for `v0.33.0`, only if readiness evidence is strong.

Possible examples:

- preserve generated-column expression facts without applying rule semantics
- preserve identity mode facts without modeling sequence options
- support only `CREATE TABLE` identity/generation facts before considering `ALTER TABLE`

Pros:

- starts turning stable parser facts into user-visible semantic value
- creates a concrete support path after several boundary-only releases

Cons:

- requires shared spec contract changes
- increases corpus and public surface compatibility burden
- can overclaim if expression or identity option semantics are under-modeled

### Option C: Defer generated/identity support and pivot

Keep generated/identity unsupported and choose a different high-value PostgreSQL coverage area.

Possible areas:

- additional `ALTER TABLE` generic unsupported inventory
- schema-aware FK policy expansion beyond explicit cross-schema advisory
- supported fact preservation for simpler PostgreSQL DDL constructs

Pros:

- avoids complex generated/identity contract design
- may produce higher user value faster

Cons:

- leaves the generated/identity support question unresolved

## Recommended Direction

Use `v0.32.0` as a support-readiness gate with a default bias toward **no production support changes**.

The milestone should produce one of three explicit outcomes:

1. **Proceed to narrow support in `v0.33.0`** if shared spec, corpus, and surface compatibility are clear.
2. **Continue boundary tightening in `v0.33.0`** if generated/identity support remains contract-risky.
3. **Pivot to a different PostgreSQL coverage pack** if another area has clearer user value.

This is the right moment to pause because `v0.31.0` closed the generated/identity boundary gap that was explicitly left by `v0.30.0`.

## Evidence Required

### Inventory Evidence

Task 1 should list remaining generic PostgreSQL unsupported features found in current tests/corpus and classify them by:

- syntax family
- current unsupported feature
- whether AST subtype is stable
- whether the form is close to an existing supported path
- whether the form has corpus coverage
- likely user value

### Generated/Identity Readiness Evidence

Task 2 should determine whether the parser exposes enough facts for a minimal support contract:

- generated expression availability
- generated kind or storage mode availability
- identity mode (`ALWAYS` vs `BY DEFAULT`) availability
- identity sequence option availability
- whether facts are stable for both `CREATE TABLE` and `ALTER TABLE`

### Contract Evidence

Task 3 should decide whether a support path would require:

- new fields on `spec.Column`
- new fields on `spec.AlterColumn`
- corpus expected YAML schema changes
- finding metadata changes
- rule behavior changes
- public API compatibility notes

## Success Criteria

- No production support behavior changes are shipped.
- Remaining generic PostgreSQL unsupported boundary candidates are inventoried.
- Generated/identity parser facts are summarized with enough detail to decide whether they can enter shared contracts.
- A concrete `v0.33.0` recommendation is produced.
- Docs/roadmap describe the decision without claiming support expansion.
- All checks pass and the repository remains releasable.

## Expected Deliverable

The main deliverable is a committed decision report and updated roadmap/release documentation for `v0.32.0`.

The implementation tasks may add characterization tests or testdata only when they are needed to prove readiness facts. Any production code change should be treated as out of scope unless the user explicitly approves a new milestone design.
