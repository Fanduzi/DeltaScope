# v0.35.0 PostgreSQL Generated/Identity State-Transition Pack Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Determine whether PostgreSQL generated/identity state-transition statements can move from explicit unsupported boundaries to narrow supported behavior, and only implement support if the current contract can represent those transitions safely.

**Architecture:** Start with a hard decision gate. Characterize the existing AST and normalized extractor shape for `DROP EXPRESSION`, `SET GENERATED`, and `DROP IDENTITY`; assess whether `spec.DDL.Alter` is expressive enough; then either stop or proceed with the smallest support widening that keeps state transitions explicit. If the gate fails, no production behavior changes should ship.

**Tech Stack:** Go, `pg_query_go/v6`, DeltaScope PostgreSQL extractor, audit corpus YAML, CLI/HTTP/MCP/public Go API tests, Markdown release docs.

## Milestone Scope

**Candidates for support evaluation:**
- `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ALWAYS`
- `ALTER TABLE ... ALTER COLUMN ... SET GENERATED BY DEFAULT`
- `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

**Always out of scope unless Task 1 proves otherwise:**
- generated expression text rendering
- generated expression semantic evaluation
- full PostgreSQL identity/sequence semantics
- schema-state reconstruction across statements
- generated/identity-specific rules
- MySQL/TiDB changes
