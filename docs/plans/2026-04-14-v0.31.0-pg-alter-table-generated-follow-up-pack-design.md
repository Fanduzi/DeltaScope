# v0.31.0 PostgreSQL ALTER TABLE GENERATED Follow-up Pack Design

## Goal

Tighten the remaining PostgreSQL `ALTER TABLE` generated/identity boundary forms that `v0.30.0` deliberately left as generic unsupported outcomes.

The release should turn stable PostgreSQL generated/identity alter-table subtypes into explicit unsupported feature tags:

- `DROP EXPRESSION` -> `generated_column`
- `SET GENERATED ...` -> `generated_as_identity`
- `DROP IDENTITY` -> `generated_as_identity`

This keeps DeltaScope's unsupported boundary contract searchable and consistent without claiming real generated-column or identity-column support.

## Context

`v0.26.0` locked PostgreSQL `CREATE TABLE` generated/identity boundaries:

- generated stored columns return unsupported feature `generated_column`
- identity columns return unsupported feature `generated_as_identity`

`v0.30.0` extended that discipline to PostgreSQL `ALTER TABLE ... ADD COLUMN` forms:

- `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS (...) STORED` -> `generated_column`
- `ALTER TABLE ... ADD COLUMN ... GENERATED ALWAYS AS IDENTITY` -> `generated_as_identity`

`v0.30.0` intentionally did not tighten adjacent generated/identity alteration forms. Those forms are currently unsupported, but the feature names are generic AST subtype names such as `dropexpression`, `setidentity`, and `dropidentity`.

That generic behavior is safe, but it is less useful than the stable feature tags already used elsewhere in the PostgreSQL generated/identity boundary family.

## Problem Statement

DeltaScope already rejects these PostgreSQL statements, but the unsupported feature contract is not yet aligned with the rest of the generated/identity boundary story:

```sql
ALTER TABLE users ALTER COLUMN full_name DROP EXPRESSION;
```

```sql
ALTER TABLE users ALTER COLUMN id SET GENERATED BY DEFAULT;
```

```sql
ALTER TABLE users ALTER COLUMN id DROP IDENTITY;
```

Today these statements remain generic unsupported outcomes. That means users and tests must reason about AST subtype names rather than product-level feature classes.

The problem is not support coverage. The problem is contract quality: if DeltaScope can safely identify generated/identity semantics at the PostgreSQL extractor boundary, the unsupported feature should use the same names as the rest of the generated/identity boundary family.

## Design Goal

Ship a small boundary follow-up release.

The release should be positioned as:

- "DeltaScope now maps additional PostgreSQL generated/identity `ALTER TABLE` forms to explicit unsupported feature tags"

not:

- "DeltaScope now supports generated-column alteration"
- "DeltaScope now supports identity-column alteration"
- "DeltaScope now models generated expressions"
- "DeltaScope now has complete PostgreSQL `ALTER TABLE` support"

## Non-Goals

This milestone does not include:

- real generated-column support
- real identity-column support
- generated expression extraction
- identity option modeling
- `ALTER TABLE` semantic diff support
- PostgreSQL catalog checks
- search-path behavior
- MySQL/TiDB behavior changes
- public API type changes
- new rule IDs
- new CLI flags

## Boundary Candidates

### Candidate 1: `ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION`

Expected contract:

- parse succeeds
- extractor returns unsupported feature `generated_column`
- reason is non-empty and says the generated-column alteration is unsupported

Reason:

- `DROP EXPRESSION` removes generated-column behavior
- DeltaScope does not model generated-column state transitions
- the existing product-level unsupported feature for generated columns is `generated_column`

### Candidate 2: `ALTER TABLE ... ALTER COLUMN ... SET GENERATED BY DEFAULT`

Expected contract:

- parse succeeds
- extractor returns unsupported feature `generated_as_identity`
- reason is non-empty and says identity-column alteration is unsupported

Reason:

- `SET GENERATED` changes identity-column generation behavior
- DeltaScope does not model identity-column state transitions
- the existing product-level unsupported feature for identity columns is `generated_as_identity`

### Candidate 3: `ALTER TABLE ... ALTER COLUMN ... SET GENERATED ALWAYS`

Expected contract:

- characterize before widening tests
- if the AST subtype is the same stable `AT_SetIdentity` shape, return unsupported feature `generated_as_identity`

Reason:

- this is the sibling form of `SET GENERATED BY DEFAULT`
- it should not require a separate feature name if `pg_query_go/v6` exposes the same semantic subtype

### Candidate 4: `ALTER TABLE ... ALTER COLUMN ... DROP IDENTITY`

Expected contract:

- parse succeeds
- extractor returns unsupported feature `generated_as_identity`
- reason is non-empty and says identity-column alteration is unsupported

Reason:

- `DROP IDENTITY` removes identity-column behavior
- DeltaScope does not model identity-column state transitions
- the existing product-level unsupported feature for identity columns is `generated_as_identity`

## Technical Design

### Extractor location

The expected production change is in the PostgreSQL extractor's `alterFromCmd` switch.

The minimal behavior is to add explicit cases for stable `pg_query.AlterTableType` values:

- `AT_DropExpression` -> unsupported `generated_column`
- `AT_SetIdentity` -> unsupported `generated_as_identity`
- `AT_DropIdentity` -> unsupported `generated_as_identity`

The implementation should not touch the supported `ADD COLUMN`, `DROP COLUMN`, constraint, default, nullability, or type-change branches.

### Unsupported feature naming

Use existing names:

- `generated_column`
- `generated_as_identity`

Do not introduce:

- `drop_expression`
- `set_identity`
- `drop_identity`
- `alter_generated_column`
- `alter_identity`

Reason:

- the user-facing concept is the unsupported generated/identity feature class, not the PostgreSQL AST subtype
- the names stay aligned with `v0.26.0` and `v0.30.0`

### Parser assumptions

Known facts from `v0.30.0` characterization:

- `DROP EXPRESSION` parses as `AT_DropExpression`
- `SET GENERATED BY DEFAULT` parses as `AT_SetIdentity`
- `DROP IDENTITY` parses as `AT_DropIdentity`

Task 1 should still confirm whether `SET GENERATED ALWAYS` uses the same stable subtype before deciding whether to include it in tests. If it does, the implementation can naturally cover it through the `AT_SetIdentity` branch.

## User Value

### Maintainer

- closes the open follow-up explicitly documented in `v0.30.0`
- reduces future churn from generic AST subtype feature names
- preserves the boundary-first PostgreSQL strategy

### User

- sees stable unsupported features for generated/identity semantics
- can search and filter unsupported outcomes by feature family
- does not get misleading support claims

### Release

- small, honest release narrative
- clear continuity from `v0.26.0` and `v0.30.0`
- no dependency on larger generated-column support work

## Risks

### Churn risk

Changing unsupported features from generic subtype strings to stable product-level features changes expected output. This is intended, but it must be locked across corpus and public surfaces.

### Overclaiming risk

Docs must not say "support". They should say "explicit unsupported boundary", "unsupported feature mapping", or "boundary tightening".

### Scope creep risk

Generated/identity semantics can invite expression and identity-option modeling. Those are out of scope for this milestone.

## Success Criteria

- `DROP EXPRESSION` returns unsupported feature `generated_column`.
- `SET GENERATED BY DEFAULT` returns unsupported feature `generated_as_identity`.
- `DROP IDENTITY` returns unsupported feature `generated_as_identity`.
- If `SET GENERATED ALWAYS` is included, it also returns `generated_as_identity`.
- Corpus and service tests lock the selected boundaries.
- CLI / HTTP / MCP / `pkg/deltascope` tests cover the same contracts.
- Docs describe boundary tightening only.
- No public API types, rule IDs, CLI flags, parser dependencies, or non-PostgreSQL behavior change.
